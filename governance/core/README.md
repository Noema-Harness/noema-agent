# 治理内核契约

这里的语义与具体项目无关：任何宿主（本仓库、其他仓库、独立工具）都用同一套条目模型、状态机与门契约。本文件只写契约；实现与适配在下游，批次三评估抽离成独立项目。

## 模块

| 模块 | 职责 |
|---|---|
| `persist.mjs` | 条目持久层：`parseDecisions`/`renderDecisions`（幂等）、`loadStore`/`saveStore`、`validateStore`、`ensureStore`（命令入口引导） |
| `entries.mjs` | 条目正文操作（读/写字段、轮次、待裁、阶段事件） |
| `lifecycle.mjs` | 阶段、合法转移、重开与偏差修复边 |
| `packs.mjs` | 规则包 gate 校验与恢复卡文本 |
| `transitions.mjs` | 过渡文档模板结构校验与就地更新判定 |
| `edits.mjs`/`history.mjs`/`acceptance.mjs`/`handoff.mjs`/`interface.mjs` | 编辑、历史只增、验收覆盖、交接/报告、命令路由 |

数据格式与视图约定：`governance/data/decisions.json` 是唯一真相；`docs/DECISIONS.md` 是它的渲染产物，任何直接改文件的做法都应被 `docs:check` 拒绝。

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `entries.mjs` | 条目文本模型：定位、读取四块、写阶段/轮次/已定 | 不读盘、不认识仓库路径、不跑门 |
| `lifecycle.mjs` | 阶段、阶段标记、前进/退回/重开的合法转移 | 不写门的命令，不写项目语汇 |
| `packs.mjs` | 规则包 gate 提取与校验、恢复卡文本装配 | 不知道规则包文件在哪 |
| `transitions.mjs` | 过渡文档的节、占位符、待确认项检查与骨架 | 不知道模板路径与文档落点 |

适配层（`scripts/decision.mjs`、`stage.mjs`、`transition.mjs`、`scripts/lifecycle.mjs`）只做路径、IO、门命令与 CLI 接线。内核文件里出现项目专名或仓库路径时，`npm run docs:check` 报错。

## 条目模型

一条条目承载**一个待定问题**，不是一轮工作。

- 标识：`D-<YYYYMMDD>-<短名>`，短名用小写连字符。
- 固定字段（只有四个，实际是文档首部的四个条目级字段）：阶段 / 结构 / 来源 / 阻塞。状态由阶段表达，不另写状态字段。
- 四态：`决策中 → 执行中 → 待验收 → 已收口`；任一阶段可退回 `决策中`，必须写原因与重开轮次。
- 来源必须是用户：写清用户在哪一轮提出。agent 不自行开条目，也不把候选写成决定。

决策层四块（顺序固定）：

1. `要定`：当前要向用户问清什么；无则写「无」。
2. `待裁`：滚动且唯一；普通待裁项积压，草案是升格的待裁项（收口后消失）。
3. `已定`：`E<编号>` + 内容 + 原话 + 日期；已确认草案的完整内容作为「已定细则」并入本块。
4. `轮次记录`：每轮一行索引——结论 + 待裁变化；中断时追加 `- 中断：<情况>，返回后继续第 N 轮`，返回后覆盖该行、继续同一轮次。

执行层与验收层在决策期各留一行 `- 未开始：…`；进入执行后执行层只允许两样：批次指针（`- 当前批次：<change>（commit <sha>）` 与只增的 `- 批次历史：`）与影响决定的发现。进度属于 change 与看板。

## 状态机

| 从 | 到 | 条件 |
|---|---|---|
| 决策中 | 执行中 | 设计方案获批 + 条目收口重构 + 开工清单获批；执行层已有批次指针 |
| 执行中 | 待验收 | 切片全绿或明确阻塞；生成执行交接数据 |
| 待验收 | 执行中 | 偏差修复：决定没变、实现不对；写原因（≥10 字），记在验收层「- 偏差：」，工具拒绝改动已定决定 |
| 待验收 | 已收口 | 用户逐项验收并给出确认原话与日期 |
| 待验收 / 执行中 | 决策中 | 重开：必须写原因（≥10 字），记在发生它的阶段（验收层或执行层） |
| 任意 | 决策中 | 设计遗漏、决定被推翻；写原因，旧结论标「已被重开」 |

收口重构（决策中 → 执行中 的第二步）：决策层压成决定行 + E 一览 + 关键不变量（≤10 行）+ `- 设计：<指针>`；完整轮次移出条目，留在 git 历史与设计文档附录；待裁清空；草案并入已定。

## 操作与行为门

| 操作 | 写什么 | 行为门 |
|---|---|---|
| `accept` | 新条目落库 | 必须有用户批准原话（≥10 字）与日期 |
| `round` | 追加一轮记录 | 必须带待裁变化行（`+…` / `已解除…` / `继续…`） |
| `settle` | 待裁项转已定 | 必须带原话与日期 |
| `advance` | 阶段推进或重开 | 只允许向前一步或重开回决策中；向前必须有原话（≥2 字（明确的「可以」「可以通过」即可；单字「好」仍拒绝）），进执行中前必须有批次指针；重开必须写原因（≥10 字） |
| 例外落地 | `- 例外落地：<slice>（用户确认：「原话」，日期）` | 讨论期落地物必须声明；change 抬头写 `Decision: <id>（例外落地）`；会议总结逐条回顾 |

写前先跑结构校验；校验失败不落盘（文件 hash 不变），并打印原因与修法。所有操作支持 `--dry-run`：只打印将写的内容。

## 门契约

三类挂载，按可绕过程度选择：

| 类别 | 位置 | 保证 | 反馈 |
|---|---|---|---|
| 行为门 | 内核命令写盘前 | 不可绕过（拒绝写盘） | 检查清单 + 修法 |
| 产物门 | 提交 / CI / 里程碑 | 不可绕过（非零退出） | 报错 + 修法 + 规则 id |
| 阶段注入 | `stage` 等命令 | 只要跑命令就一定看到 | 不阻断 |

选型判据：

1. 失败不可逆或代价差一个量级 → 必须做门；做不成门就不要假装它是规则。
2. 只是规程、参考、范例 → 技能；技能里不写「必须 / 禁止」这类需要执行的约束。
3. 进入阶段前必须知道的事实（当前阶段、待裁编号、过渡文档结构、恢复卡）→ 阶段注入。
4. 模板注入归门与阶段注入，不归技能：技能只能解释为什么，不能保证用上了。

规则登记要求：每条门规则写清 `id | 支撑的不变量 | 防的失败 | 触发证据 | block/notice | 执行位置`。新门先 notice 并标「观察期：…」，两个里程碑无触发再转 block；没有触发证据的规则删掉。

## 规则包契约

每个阶段一份规则包，描述该阶段允许什么、默认面、禁止项、出口与检查项：

- 检查项带 `gate:` id，且该 id 必须在规则登记表里（防止规则与门脱钩）。
- 规则包只读；`stage` 打印它并附带当前条目、待裁编号与恢复卡，末尾打印文件路径与 sha256 便于比对是否过期。
- 规则包过期（门改了、规则没改）由 `stage` 的 id 校验发现。

## 恢复卡

中断后回来，第一件事是跑 `stage`，不是凭记忆继续。恢复卡固定四项：

1. 当前阶段（由产物推断：有待裁 ⇒ 决策中；有批次指针 ⇒ 执行中；有验收项 ⇒ 待验收）。
2. 条目与待裁编号（多活动条目时列全部，用 `--entry` 指定，不自动挑最新）。
3. 上一轮结论一行（带轮次号，不复制正文）。
4. 下一步动作一句。

仓库有新提交时多一行提示。只保证提示出现，不保证被读；不做常驻注入、不缓存。

## 审计

每条治理行为留一条可查询的记录：谁（用户 / agent / 命令）、基于什么证据、做了什么决定、写到了哪里。审计只追加，不改历史；条目轮次与提交信息是它的主要载体。

## 过渡文档

决策 → 执行走三步，不合并、不跳过：设计方案 → 条目收口重构 → 开工清单。执行 → 验收产出执行交接；验收 → 收口产出验收报告。后两者只保留结构与数据，不写成新叙述。通用规则：

1. 每份文档只有一个读者任务：批 / 收口 / 验收；完成后定格。
2. 每份都能回答「谁、基于什么证据、做了什么决定」。
3. 不复制正文，用「文件 + 行号 / commit / 命令」指针。
4. 没有待确认项时写「待确认：无」。
