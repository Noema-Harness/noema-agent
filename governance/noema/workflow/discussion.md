# 讨论态规则包

进入讨论、做取舍时先读这份。讨论只产出证据与结论，不把仓库变成半成品。

## 进入与记录

- 状态是 `讨论`（`npm run state` 显示；切换用 `npm run state -- set 讨论 --reason "…"`）。
- 会话自动开始；主题取第一轮的原话摘要，之后可改。切走会自动归档，回来自动恢复并续轮次。
- 一轮一行：`npm run state -- round --conclusion "这一轮的结论" --change "+新增 / 已解除"`。只写结论与差分，不复制正文。
- 待裁项滚动：`npm run state -- wait add --item "T1 要定什么"`，解决后 `-- wait drop --item T1`。待裁是唯一入口，新问题先进清单。
- 用户确认的结论要落成记录（进账本）：`npm run governance -- record settle …`；账本只收已定内容。
- 中断时追加 `- 中断：<情况>，返回后继续第 N 轮`；返回后覆盖该行、继续同一轮次。

## 默认面：只产出证据

讨论期只允许两类产物：

- **证据**：调研（脚本、查询、抓取结果）、架构图、探针、截图、实验数据、会话记录。放在 `.work/` 或 `.archify/`。
- **落地物（默认禁止）**：任何进 `main` 的实现——产品代码、机制脚本、规则文档、门。需要提前落地时先问用户，得到明确同意再开执行。

## 两种结束

- **定案**：产出设计文档（单份，就地更新）+ 开工清单 → 该范围成为执行范围；`npm run state -- set 执行 --reason "…" --scope changes/<name>`，会话自动以「定案」归档。
- **搁置**：不需要操作，切走即归档；历史和轮次仍在，可恢复继续。

不设「取消」：取消不指向任何状态。

## 产出边界

- 讨论期改动 `apps/desktop/src/` 或治理机制 → 会被提交门拒绝；先把范围谈清楚再进执行。
- 设计文档与开工清单用现有模板（`npm run transition -- design|kickoff --entry <id> --write`），结构校验不过不能作为批准依据。

## 检查项

- `gate:code-needs-plan`：产品代码改动要有活动变更与规格增量。
- `gate:governance-no-product`：治理变更不能夹带产品代码。
- `gate:decision-shape`：落账本的条目保持四字段与三层的结构。

## 边界

- 讨论是探索，不是承诺；没有定案就不算批准。
- 不要为了对齐而制造分歧，也不要因为怕越权而只做收口回应：判断是 agent 的职责，取舍是用户的。
