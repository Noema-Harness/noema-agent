# 验收态规则包

进入方式：`npm run state -- set 验收 --reason "…"`（必须所有验收单元已完成）。

## 这个状态做什么

- 对照**范围**判断做出来的东西对不对，不重做执行者做过的事。
- 四层，逐层判：
  - **D 确定性检查**：命令/测试/构建，能复现 pass/fail。
  - **C 判据对照**：和进入执行前写定的判据比；判据是执行者写、这里复核。
  - **R 审查发现**：另一双眼睛看风险。R 不判「通过」，但每条必须处置（已修 / 延期 / 接受，后两者写理由），
    未处置不能完成单元、也不能签收。
  - **H 人签收**：阶段里的 H 项由用户的原话判定（`accept human --id P1-A4 --text "用户原话"`），agent 自己判会被拒绝；
    整条范围是否符合预期，用 `state -- sign "用户原话"` 收口。
- 判定只有三种：通过、不通过、预期有问题。不通过→回执行修；预期有问题→回讨论改范围。

## 怎么记

- 验收项：`state -- accept add --phase P1 --text "…" --layer D|C|R|H`；
  判定：`accept set --id P1-A1 --status 通过|不通过`（D/C）；H 项用 `accept human --id P1-A4 --text "用户原话"`；
  发现处置：`accept resolve --id P1-A3 --decision 已修|延期|接受 --note "…"`。
- 一个单元最多拉锯一次；第二次不通过就回讨论，别在原地反复修。
- 用户只需要看：范围、改了什么、证据、没验证的、风险；不需要跑命令。

## 怎么结束

- 全部单元通过、发现全部处置 → `state -- sign "<用户原话>"` → 回到待定/讨论（`state -- set 讨论` 或收口归档）。
- 签收只认用户原话，不设超时自动通过。

## 边界

- 验收只读：不改代码、不改范围（要改就退回执行/讨论）。
- 检查项：`gate:status-today`（交付记录当天事实）、`gate:source-boundary`。
