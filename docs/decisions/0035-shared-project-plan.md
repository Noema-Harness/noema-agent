# ADR 0035：项目共享计划与成员直接协作

- 日期：2026-10-27
- 状态：用户确认阶段化计划结构；本 ADR 的数据、权限与实现细节由助手在开发授权内选择
- 关联：#119（共享计划）、#120（公开协作）、#118（体验验收）、ADR 0029
- 部分取代：ADR 0029「上下文、路由与控制」第 4 条中“无 @ 时由 Noema 或首位活跃成员回应”的回退规则；未点名消息进入共享未读，不自动指定回应者。

## 问题

当前组队工具将成员创建、首轮全部分工和顺序回答捆在一起。群内记录虽然公开，团队没有共同计划，仍需 Noema 逐个推动。另设协调 agent 即使不增加人数，也可能增加强制中转层。

普通分享、倾诉与漫谈不以澄清需求为默认目的。只有已成立的委托才需要工作状态。群聊与执行服务于持续 Noema，而非完整产品定位；本决策不把意识、人格或主观成长作为工程承诺。

## 决定

1. 项目是共享目标、计划、成果和成员会话的归属；预研究与实施可在同一项目演进。近期交付详细分解，远期保留粗粒度，研究允许缩小、改变或终止实施。
2. 不新增固定经理层。Noema 对用户目标与关键判断负责；团队成员可直接交流与交接。规划负责人是一项责任，不是消息必经通道，也不垄断成果与进度。
3. 先交付共享计划，后接自动协作。#119 提供用户与模型共同维护的持久计划；#120 接共同启动、显式 @、未读与依赖接续。每个模块独立验证，不能因计划已存储就宣称自主团队已完成。
4. 共享计划采用三层结构：项目结果 → 阶段（阶段成果、退出条件、阶段依赖）→ 团队工作项（负责人、依赖、状态、完成条件与成果依据）。近期阶段可细化，远期阶段允许先保留结果与退出条件、在进入前再拆工作项。工作项提交与验收分开；阶段也须经用户或 Noema 核对成果依据后单独验收，未验收的前置阶段不得启动后续阶段。
5. 项目进度按阶段汇总：已验收阶段数 ÷ 未取消阶段数；各阶段另显示工作项验收情况。提交不计作验收，已取消阶段/工作项不进入各自的比例；没有可统计的阶段时不显示百分比。所有比例仅描述计划内验收状态，不代表整体产品成熟度、剩余工期或完成日期。不得凭空补入工时、点数、日期或完工预测；只有出现可靠估算依据时才另行设计。
6. 用户与 Noema 可修改阶段范围及验收；专业成员只能更新自己负责事项的执行状态、阻塞与成果，不能自己验收、改目标或重分配其他成员。模型工具的操作者来自实际运行会话，不能由工具参数自称。
7. 复用 SQLite 与既有项目域，计划按事务保存版本和操作者，写入要求期望版本，冲突提示重读而非覆盖。项目归档保留计划，等待用户时暂停计划工作修改；不以聊天中一句“完成了”改状态。
8. 公开消息先持久化，再按显式点名产生投递；群共享记录与成员模型调用分开。管理员（用户、Noema）可以 @所有人；普通成员可公开发言和点名其他成员。未点名消息在成员下一工作边界合并提醒，不为每条公开消息启动全员推理。当前运行在安全边界接消息，不杀掉执行中的工具。
9. 扩展已有项目 inbox 支持一条消息多位接收者，投递留去重记录；同一成员项目会话串行。计划就绪按版本与交付项去重唤醒。自动接续有持久的链路次数上限，失败/中断不自动重试，达到上限公开说明并等待明确继续，避免相互 @ 的无界费用。
10. 创建团队仅建立共同背景与职责，不隐含顺序咨询。后续发消息、制定计划和执行分别发生。普通回复只留在群/项目会话；显式 @Noema 或阶段验收/阻塞等重要计划事件才进入 Noema 连续主聊，复用已有持久报告通道。
11. 他人的公开发言以带来源的外部资料进入上下文，不放进当前成员的 assistant 历史。当前事件单独放在输入末尾，尤其不能让系统事件被历史过滤掉。就绪交付在领取时由运行时标记进行中；完成后成员自行提交依据。只做了一次工作却未更新状态时，补交提醒最多一次，再交给 Noema 协调，不通过无限提醒或自然语言推断完成。
12. 工具响应可包含少量多个操作，顺序处理并逐项返回结果，仍按实际操作者和期望版本校验；部分成功不会回滚已经发表的成果。群里已通过工具发表完整消息后，结尾说明留在项目会话，避免同一成果再次群发。
13. 群聊不按用途拆成不断增长的房间类别。项目协作与共同讨论发生在同一种共享群空间；共同讨论是可选互动行为，不是另一种群。
14. `@所有人`表达接收/调用范围，不自动表达讨论意图。全员通知、计划变更、共同讨论与项目结束后的成长处理可能都需要触达全体，但各自的回应要求由消息或生命周期事件本身决定；模型被调用不等于必须公开回复。
15. 不把某种固定讨论脚本写成模型必须遵守的产品协议。共同讨论的消息投递、合并、结束和费用边界在工程实现阶段按成熟协作/agent 实现与当前运行架构校准；流程图只表达用户可理解的行为边界，不预设轮次或强迫成员表演式发言。

## 参考与适用差异

- OpenCode 固定源码 `24b5ed8bcc60aa9a20cf4e3edf1444470e0e6464`：`packages/core/src/tool/plugin/todo.ts` 的结构化状态、工具返回与可见摘要。复用其简洁计数思路；其 session todo 并不提供 Noema 所需的跨成员责任、依赖与验收，不能直接拿完整框架替代本域。
- [NASA WBS 说明](https://science.nasa.gov/wp-content/uploads/2023/04/Walyus_Keith_WhatisaWBS.pdf)：按可交付结果分解工作范围。Noema 采用适合协作的轻量结果—阶段—工作项层级，不宣称完整 WBS 工具。
- [PMI 滚动规划](https://www.pmi.org/-/media/pmi/documents/public/pdf/certifications/practice-standard-scheduling.pdf)：近期细、远期粗。
- [Kanban Guide](https://kanbanguides.org/the-kanban-guide/2025.5/)：显式工作流与容量约束支持拉取。不为采用这些原则引入 Sprint 会议、角色层级或完整方法论认证声明。
- [AutoGen Core 群聊示例](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/group-chat.html)：收到共享消息和实际运行发言分开；不照搬其管理者轮流选人。
- 群聊互动的后续实现需继续源码级核对成熟协作/agent 系统中的消息可见性、收件路由、运行边界和终止方式；单一项目里的轮次设计不应直接提升成所有群聊的固定规则。

## 后果与重审

### 成果引用补充（2026-10-28）

项目文件执行结束须回到发起成员，而不是仅刷新用户卡片。任务保存所属工作包及待通知标记，只有新启动且明确关联本项目会话的任务进入此链；旧任务不批量重放。终态通知复用公开消息和持久收件箱，成功交给原成员核查提交，失败交给 Noema 协调；主动中断不自动唤醒。发布消息与清除待通知标记在同一事务内完成，等待用户或应用重启后可恢复未投递结果。通知只带任务标识和实际状态，完整结果按需读，不能让执行输出中的 @ 文本产生额外投递。

在工作包的既有版本快照内保存类型化来源，不建立第二份成果数据库。消息引用以本项目公开群消息为边界；执行引用指向本项目成员会话中的实际任务；文件引用必须依附该任务已授权的工作区，解析真实路径后限制在其中。模型只提交来源标识，运行时生成内容指纹、作者和采集时间。文字依据继续兼容，缺结构化引用不伪装为已核对。

引用保存的是采集时版本，不是随源文件变化的链接保证。显式核对和验收时重新读取来源，报告一致、变化或不可用；变化需重提交，不能在验收动作中悄悄刷新指纹。已验收记录保留原结论与来源版本，后续检查显示需重核及计划中的直接/间接依赖，不自动重写历史或启动模型。常驻监控与自动撤销已完成状态暂不引入。读取来源、内容一致与成果正确是不同判断：系统只能证明来源和版本，业务验收仍由实际操作者负责。

参照 OpenProject 的 [Attachment 模型](https://github.com/opf/openproject/blob/dev/app/models/attachment.rb) 对归属、作者、Journal 和内容摘要的职责划分，未移植其 GPL 实现。Noema 直接复用已有消息、任务及计划快照；不复制外部文件存储层。文件指纹采用 Node SHA-256，限制单文件 16 MiB、每工作包最多 10 个引用；超限明确失败，不默认为核验通过。若真实交付需要大型文件，后续改为异步流式取证，而非在主进程无限同步读取。

### 节点更新与追溯补充（2026-10-28）

整份计划替换与阶段验收仍严格检查全局期望版本。单工作包更新可使用读取时的计划版本作为基础：只有目标节点、项目目标、阶段定义、祖先分组及其依赖节点均未变化时，才在同一事务内将局部修改应用到最新计划；任何相关变化都返回冲突位置，要求重读，不进行字段级猜测合并。权限、依赖与状态校验仍针对最新计划执行。

复用既有追加式版本快照，不新增工作流引擎或独立日志表。版本保留实际操作者、来源回合、原因和最初读取版本；按需由相邻快照计算字段变化与受影响节点，默认历史只返回摘要，指定版本才读取详细前后值。既有快照无需迁移。

参照 OpenProject [工作包 PATCH 与 lockVersion 契约](https://www.openproject.org/docs/api/endpoints/work-packages/)、[UpdateService](https://github.com/opf/openproject/blob/dev/app/services/work_packages/update_service.rb) 的关联更新及 [WorkPackage](https://github.com/opf/openproject/blob/dev/app/models/work_package.rb) 的版本/Journal 归属。此处借鉴资源级冲突与追溯职责，未移植其 GPL 代码。Noema 继续存储项目快照，因此以旧快照核对局部变更范围，而非新建独立工作包版本表。若大计划使快照比对成本成为瓶颈，再考虑存储拆分。

共享计划是 Noema 项目的产品数据，不等同于开发 Noema 使用的 GitHub 看板。界面和模型工具读取同一版本；历史可追溯，未来可接外部任务工具。首模块不新增通用工作流引擎或定时轮询。

结构校验不保证计划质量。各专业成员仍需核对自己的交付与依赖；主观验收或新价值取舍仍由用户把关。阶段化结构用于呈现跨阶段目标和明确验收门，不应扩展成通用项目管理套件；只有真实协作反复暴露缺口后，才增添更深的分解或估算机制。
