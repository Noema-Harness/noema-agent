# ADR 0038：成员成长批次与常驻会话简报

- 状态：服务闭环已实现；客户端生命周期待 #113；真实模型效果待评
- 日期：2026-10-27
- 关联：Issue [#103](https://github.com/c3115644151/noema-agent/issues/103)、[#113](https://github.com/c3115644151/noema-agent/issues/113)、ADR 0029、0034

## 决定

项目生命周期在确认工作完成后发出一个可恢复的完成事件；成长模块把该事件转成一批有稳定 ID 的成员自审工作。每位成员在自己的项目会话中复核这段经历，自己判断是否值得修改资产；可选择不改。资产继续使用既有 SQLite 修订、来源和回滚机制，Noema 不代写。

批次与成员结果按项目和完成事件持久化，单个成员成功后即记录完成，进程重启或其他成员失败时不得重复调用已完成成员。失败/中断保留状态并允许显式续接；任何不确定的资产副作用先按来源轮次核对，不盲目重放。

每位成员的简报留在可追溯的项目经历中，并作为有界内部材料提供给该成员的常驻会话；不为“通知常驻会话”再调用一次模型，也不把简报伪装成用户发言或公开群消息。面向用户的项目总结由项目生命周期闭环负责，避免每名成员分别唤醒 Noema。

项目恢复后的轻量续接不自动产生新一轮成长调用。是否需要新的成长批次由项目完成边界结合自上次完成以来的实质贡献判断，而不是每条消息或每项细小修订都触发；相同完成事件必须幂等。

当前触发入口是 Noema 主聊中的 `complete_project`，服务端要求共享计划有至少一项已验收交付、未取消事项全部验收、没有待用户评审或运行中的项目工作。成员顺序自审，系统只在每位常驻私聊下一次成功回复时注入未读简报，并在该回复完成后标记已读。正常情况下每位成员至少一次推理；成员选择写资产时会再用一次推理整理工具结果。模型连接暂不可用时保留批次，恢复后继续，不自动消费重试额度。

中断成员若对应的原轮次已经产生资产修订，显式重试会先拒绝，要求核对来源修订，避免把不确定副作用盲目重放。客户端尚未呈现批次进度与重试入口，最终汇报、归档和恢复由 #113 接入；这版只通过合成服务测试验证，不代表真实模型产物质量已验收。

## 复用与边界

- 复用现有成员项目会话、资产读写与版本记录、SQLite 事务、工具调用状态及项目报告队列。
- 新增状态只表达“哪个完成事件、哪些成员、各自是否已审、简报是什么、如何续接”；不引入后台常驻调度器或新的 agent 框架。
- 成长调用仅开放当前成员自己的资产工具。它不能继续派发项目工作、改共享计划、向群发消息或扩张工具权限。
- 项目关闭、用户可见的最终总结和归档由 #113 管理；成长批次完成是归档前置条件之一，但不是产品层“项目完成”的同义词。

## 依据与重审

用户明确要求成员自己复盘和修改自己的资产，常驻身份与项目上下文分离；小改不机械增加总结调用，项目归档与成长完成相连。实现采用本地 SQLite 的模块化单体边界，不引入 LangGraph/Temporal 作为运行依赖。对照 LangGraph 的持久化实践，只复用 thread/run 作用域状态、边界检查点和原始状态按需组装的思想；Noema 已有业务表及会话模型更贴近本项目，不照搬其图执行框架。[LangGraph.js persistence](https://github.com/langchain-ai/langgraphjs/blob/main/docs/docs/concepts/persistence.md)

若实测表明每成员一次自审的费用与体验不成比例、简报会污染常驻上下文，或恢复流程可能重复成长写入，重新审视触发粒度、简报注入时机和重试边界；不得以新增提示词掩盖状态模型问题。
