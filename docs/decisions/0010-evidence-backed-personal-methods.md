# ADR 0010：把“个人方法”作为可验证的能力候选，而非另一种记忆笔记

- 状态：提议；不是已接受的产品承诺或实现规格
- 日期：2026-10-15
- 决策范围/依据：Noema 生命周期委托范围内的助手决定

## 问题与背景

当前 Noema 能保存用户对交流方式的明确纠正，并记录它是否被组装进后续请求。但如果最终只把这些纠正重新写进 prompt，Noema 仍只是更细致地告诉通用模型“这次应该怎么答”。这不证明 agent 因经历形成了稳定、可迁移的个人能力。

另一种候选状态是“个人方法”：从真实任务中的工具轨迹、失败原因、修正动作和独立结果中提炼出一套可复用的程序，例如某类模型处理任务前置检查什么、失败时使用哪个工具、怎样验证结果。它与交流偏好不同，必须能在实际执行中改变动作并留下结果证据。

## 依据与假设

- 用户明确要求 Noema 成为一个由经历逐渐塑造的个人 agent，不是固定角色 prompt，也不应把成长等同于累积越来越多的记忆文档。
- 用户举过一个真实例子：模型难以从 Minecraft 模型数据推断碰撞箱，最终通过体素化工具解决。它展示了“学会一项可复用能力”可能比“再加一条行为规则”更有实际价值；但当前没有这次经历的可重放任务、工具轨迹或独立测试产物，不能据此把某一技能规格直接写入 Noema。
- Microsoft Research 的 SkillGen 研究把生成技能视为一种需要实测的干预：在同一任务实例上比较有/无技能的结果，同时计算修复与回归；产物保持可读、可审计。[论文摘要](https://www.microsoft.com/en-us/research/publication/skillgen-verified-inference-time-agent-skill-synthesis/)
- Microsoft / 复旦 / 上海交大的 SkillLens 全流程研究覆盖经验生成、技能提取和技能消费。其结果显示技能平均可能有益，但会负迁移；同一技能对不同目标模型可能一正一负。LLM judge 仅凭技能文本判断优劣只有 46.4%，而具体失败机制与可执行补救措施更有预测价值。[论文摘要](https://www.microsoft.com/en-us/research/publication/from-raw-experience-to-skill-consumption-a-systematic-study-of-model-generated-agent-skills/) · [研究结果与代码](https://github.com/microsoft/SkillLens)
- Voyager 展示过可组合、可执行的程序性技能如何在 Minecraft 的探索、失败反馈与验证闭环里累积；它证明了一种可行机制，但它的游戏环境和目标不能直接外推为通用个人 agent。[论文与项目](https://voyager.minedojo.org/)
- ACE 展示增量整理经验可减少上下文折叠问题，但最终仍属于上下文演化；它单独不足以证明行为改变或 Noema 的独立价值。[论文](https://arxiv.org/abs/2510.04618)

这些研究证明“个人方法值得作为候选来评估”，不证明它就是 Noema 的差异化产品，也不证明 Noema 应直接复制上述框架。

## 提议

将个人状态明确分成两类，而不是放进一个通用记忆库：

1. **互动约定**：用户明确纠正 Noema 如何交流或协作；继续沿用 ADR 0006 的来源、适用范围与撤回边界。
2. **个人方法**：来源于任务经验、能改变实际操作的程序化能力。候选方法至少要包含适用条件、复现出的失败机制、可执行补救步骤、来源经历、目标模型/执行器以及已观察到的成功与回归；“已生成”不等于“已学会”。

Noema 可能承担的独立责任不是托管一组 `.md` 技能文件，而是拥有这些方法从来源经历到跨模型/执行器应用和结果反馈的生命周期。若成熟的外部技能管理组合能以更少维护提供同一用户结果，或 Noema 只是在每次请求前插入一段说明，这项独立产品假设应被撤回。

## 首个验证门（尚未达到开工规格）

当前“创建 README 并由 Noema 文件 verifier 检查”的 E2E 只能证明委派与文件验收链路。因为确定性 verifier 会独立阻止错误完成，它无法证明模型是否吸收了某条方法；不同模型路由的两次成功也不能作因果比较。不得把这类通过当作 Noema 学会了方法。

Noema 已增加一个受限的观测基础：后台任务可持久保存 DSH 发出的工具类别顺序，最多 32 项；不保存参数、文件内容、返回值或推理。一次真实隔离的合成任务记录到“写入、读取、读取”，且 Noema 文件核验通过；但 Noema 对该后台事件的单独模型总结因 `provider_unavailable` 失败。工具轨迹证明 Noema 捕获到哪些操作调用，不证明调用成功、模型遵循了某条经验或经验改善了结果；独立 verifier 只证明列明的文件条件当前满足。

在增加持久方法状态前，需要找到一个真实、重复出现且具备可观察结果的用户任务族，并确认日志能看到相关行动。然后：

- 从实际失败与修正中写出一条候选方法，而非虚构一个“理想提示词”。
- 在相同任务实例、相同模型、相同执行器条件下比较有/无方法的行动与独立结果；若测试多个目标模型，分别记录兼容性，不做跨模型泛化。
- 同时记录修复和回归；不使用 LLM 对方法文本的自我评分代替任务结果。
- 只有当证据改变了“当前模型会采取什么行动”和“实际结果如何”时，才考虑进入产品实现；仅能证明方法被保存或发送，仍不足以成立。

## 主要替代项

- **继续仅做互动纠正**：实现成本低，可验证来源和是否进入上下文；但它不能证明复杂任务能力成长，也不能单独解决模型执行惯性。
- **直接建通用技能/记忆库**：可复用性高，但与已有 harness、skill manager 重叠，且没有效用验证会增加维护负担与负迁移风险。
- **直接改模型或做在线强化学习**：研究资源、训练数据、反馈回路和安全审计远超当前个人桌面项目范围。

## 后果与重审触发条件

- 不新增表结构、自动技能生成器、技能市场或后台学习进程；等待真实任务族和可运行的比较路径。
- 若找不到真实的重复任务或独立结果信号，暂停“个人方法”候选，转向更直接的日常使用价值，不用合成成功结果代替产品证据。
- 若同一方法跨目标模型出现显著回归，必须限定支持范围或由用户显式选择，不能因为文本看起来通用就全局注入。
- 若经验到行为的差异最终只能用 prompt 改写解释，或外部工具组合已能以更低成本实现同一效果，则撤回 Noema 的独立拥有理由。
