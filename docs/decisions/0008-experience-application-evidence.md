# ADR 0008：把互动状态的“被带入”与“有效”分开记录

- 状态：历史 M1 可撤回实验，仅描述现有互动调整原型；不是未来持续好友成长的默认数据/学习架构
- 日期：2026-10-14
- 决策者：助手，在用户委托的 Noema 生命周期自主决策范围内

## 问题

ADR 0006 保存用户对 Noema 的明确互动纠正，并将其带入后续根对话或 DSH 任务；ADR 0007 则能对少量文件目标独立核验。但系统目前无法回答两个不同的问题：某条纠正究竟有没有进入本轮上下文？本轮的可观察结果是什么？没有这条链路，Noema 只能说“已记录”，不能证明未来行为曾参考它；也不能把一次通过归因于那条纠正。

这正是“记忆增长”与“agent 真的发生变化”之间的空档。PLUR 等现有系统已经提供跨 harness 的可读记忆；其公开维护记录同时显示，已存储的经验可能在真实行动前未被找回。记忆内容存在、检索命中、模型收到内容、行动改变和结果改善是不同状态，不能混为一谈。

参考： [PLUR 的具体检索失败记录](https://github.com/plur-ai/plur/issues/871)、[MIB 的经验—行动—结果评价框架](https://github.com/ldclabs/mib)、[Letta Code MemFS](https://github.com/letta-ai/letta-code)、[OpenClaw memory](https://github.com/openclaw/openclaw/blob/main/docs/concepts/memory.md)、[Hermes memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)。关于选择性介入的预印本见 [Remember When It Matters](https://arxiv.org/abs/2607.08716)；这是 benchmark 结果，不是个人 agent 产品效果的保证。

## 决定

1. **记录每轮请求组装时列入的互动纠正来源。** `root_turns` 与 `background_tasks` 保存调整的稳定 ID。数据来自 Noema 实际构造的模型/DSH 输入，而非模型事后声称“参考了记忆”；这不证明上游已成功接收。
2. **把提供证据和效果判断严格分开。** 根对话只记录“本轮上下文包含这条纠正”；它不具备普遍、客观的自然度 verifier，因此效果保持未判定。后台任务可以显示其机器验收状态，但“规则被发送 + 文件检查通过”仍不证明规则导致了成功。
3. **在原时间线提供按需来源检查。** 用户可以看到纠正适用于何种情境、原始引文与期望行为；在后台任务卡片中可查看本任务带入了哪些纠正，并与 Noema 独立验收状态并列。默认不额外生成记忆卡片或打断对话。
4. **失败不是再叠一条提示词的证据。** 若同一调整已带入但任务验收失败，界面只记录“纠正已发送、目标未通过”；不能自动扩写规则、归因模型不遵循或宣称学习成功。用户可据此继续纠正、撤回或重写。
5. **第一版复用现有持久状态。** 只为 root turn 与后台 task 增加有界 ID 列表；不建立通用 experience database、自动画像系统、向量记忆或额外后台 agent。调整本体仍由 ADR 0006 的记录管理，任务结果仍由 ADR 0007 管理。

## 为什么由 Noema 持有

Noema 的产品假设是一个用户拥有、跨交流与外部 harness 延续的 agent。单独的 memory plugin 可以跨应用搬运内容，却不拥有 Noema 自己的交互回合与任务验收结果；Noema 可以把“已带入什么”与“观察到什么结果”保存在同一条用户时间线。这个边界可能仍可由现有插件组合满足，不能据此认定独立产品价值成立。

## 后果与局限

- 用户能看见一个经验状态究竟只被保存、是否被 Noema 放入请求，以及后台任务是否碰上了可独立检查的结果；不会再把“记忆写入成功”误当作“agent 已经改变”。
- root conversation 的调整效果仍是未知；不把单次用户满意或单次模型回复转成客观成功指标。
- 文件 verifier 只检查列明的文件条件；不能评价代码设计、视觉质量、游戏行为或完整任务正确性。
- 这条链路先让“个体化是否真正起作用”变得可观察；尚未证明应自动从普通聊天提取经历，也没有确认 agent 的人性化或长期陪伴价值。

## 重审条件

- 用户认为追踪“带入了什么”增加了理解成本，或信息没有帮助其判断是否信任 Noema。
- 记录证明某条调整常被带入却无法改善相关结果；届时先改写/撤回规则或触发方式，不增加更多同类记忆。
- PLUR、Letta、OpenClaw 或其他用户已经使用的组合能以更少维护成本提供同等的来源、跨工具应用和结果验证。
- Noema 需要支持自动学习、冲突治理或长周期经历档案；这些超出当前实验范围，必须另做生命周期与权限设计。

## Amendment（2026-10-15）：互动调整可编辑后，历史应用必须冻结快照

ADR 0006 现在允许用户修订当前互动调整。仅保存 adjustment ID 会使旧 assistant attempt/task 在用户编辑后显示新的 scope/situation/behavior，造成时间线倒写；ID 只能证明关联了同一条逻辑调整，不能说明当时实际组装的是哪个版本。根 turn 可能重试并使用了不同版本，所以快照的粒度必须是 assistant attempt，而不是只记 turn。

- 每次组装根模型 attempt 或新建/续接 DSH 任务上下文时，随 assistant message/task 持久化一个有界值快照：调整 ID、scope、情境、期望做法、来源短引文及是否经用户修订。
- 未来上下文使用当前 adjustment 值；旧 attempt/task 的“带入记录”始终从当时的快照渲染，不回查可变的最新值。
- 在首次启用用户编辑的 schema migration 中，只为已有 turn 的最后一次 attempt 和已有 task 的调整 ID 尽可能从不可编辑时期的现存记录回填快照；更早 retry attempts 的准确上下文无法由旧 turn 级 ID 还原，旧记录明确显示“当时的调整文本未保留”，不把最后一次 attempt 的值复制给更早尝试。
- 这些快照证明 Noema 本地组装了什么，不证明 FreeLLMAPI/DSH 成功接收、模型遵循或行为结果由其导致。

这增加少量 SQLite 存储，用于保证用户编辑不会篡改历史证据；不保存完整 transcript 副本或模型隐藏推理。若快照在真实使用中显著增加存储或理解负担，再按有证据的保留周期收敛。
