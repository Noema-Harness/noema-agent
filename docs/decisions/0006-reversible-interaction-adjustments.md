# ADR 0006：把明确的互动纠正变成可撤回的个人状态

- 状态：接受为 M1 可撤回原型；不是已验证的 Noema 核心或“灵魂”实现
- 日期：2026-10-14
- 决策者：助手，在用户委托的 Noema 生命周期自主决策范围内

## 问题

用户在长期使用 AI 时反复纠正交流和协作方式，但这些修正会随着会话截断、模型切换或任务转交而丢失，用户被迫重新训练每一个会话。当前 Noema 只保存一条完整根对话，每次最多向模型发送近期 8 轮；这保留了短期上下文，却没有一个跨根模型与后台编码任务生效、由 Noema 持有的互动状态。

本原型只处理“用户明确指出 Noema 应如何改变某类互动”的纠正，不尝试建立完整个人传记、自动汇总所有经历或模拟模型拥有主观人格。它能不能比提示词/Skill/外部记忆插件更有用，仍待真实使用检验。

## 决定

1. 新增 Noema 本地 `interaction_adjustments` 状态。每条记录是一个短的“适用情境 → 期望行为”变化，包含用户原话中的精确短引文、来源根对话 turn、适用范围（`conversation`、`coding` 或 `both`）、创建/撤回时间及状态。用户原话仍保存在根对话；状态记录只保留必要归纳与短引文，不复制整段历史。第一版最多 12 条同时生效，撤回记录仅保留最近 20 条；超限时不静默丢弃旧规则。
2. 只有模型通过结构化工具明确提出调整，且该工具调用来自真实用户 turn 时，主进程才写入状态。主进程要求模型附带的短引文必须是本轮用户原话的精确子串。工具说明限定为用户对 **Noema 自身行为**提出的具体、面向未来的纠正；关于其他 AI 的例子、抽象愿望、普通用户事实或观点不得被升级为长期互动状态。措辞不清时不记录。
3. Noema 根对话读取 `conversation` / `both` 调整；新建的后台 DSH 编码任务读取 `coding` / `both` 调整。它不回写正在运行的任务或外部 harness 的原生会话；已有 DSH session 继续遵循其原始任务上下文。每次只带入有界的小型状态集合，并作为有来源的用户互动上下文，不获得 system 权限，不覆盖用户当前消息、系统安全规则或外部来源的权限边界。
4. 新调整以一条轻量时间线事件显示：记录了什么、适用在哪类情境、来源原话是什么，并提供撤回操作。界面说“已记录”，不宣称模型已经学会或一定遵循。撤回只停止后续使用，不会撤回已发送到上游的请求，也不删除原始对话。除非用户原话本身要求澄清，否则记录调整不额外弹窗打断对话。
5. 调整和撤回由 Electron 主进程中的 `RootStore` 写入 SQLite；renderer 只能经受信 IPC 查看/撤回。写入失败时不应声称“已经记住”，当前对话仍保留并可继续。版本 1 不新增云端记忆库、独立模型调用、自动外部学习或后台周期任务。

## 为什么由 Noema 持有

一条项目 `AGENTS.md` 或单个 DSH Skill 能改变某个宿主的行为，但其作用范围和生命周期受该项目/宿主控制，无法自然覆盖 Noema 的主对话和其他后台 harness。若 Noema 要成为用户拥有的根 agent，它至少需要持有少量跨这些边界的互动状态。这个所有权理由是产品假设，不是现有实现天然不可替代的证据；若用户只需要静态配置，Noema 不应为此增加持久状态。

## 后果与验证

- 这是关系连续性的窄切片，不是通用记忆管理器；它不会自动学习用户背景、从聊天生成日记或声称模型发生了训练/权重更新。
- 结构化记录本身不会保证模型按要求行动。交付原型只证明“明确纠正可以跨最近上下文预算并在两个 Noema surface 上被选择性带入”；是否减少重复纠正、是否让后续交流更像同一个 agent，必须由真实使用判断。即使一次合成场景中输出符合记录，也不能据此宣称交互自然或产品价值成立。
- 错误归纳会让用户觉得 Noema 自作主张；因此来源可见、适用范围狭窄、可撤回是这一切片的必需机制，而不是可选的 UI 装饰。
- 避免把它变成一个记忆仪表盘：记录只在实际发生调整时进入对话时间线；详细状态通过该事件查看，而不常驻主视图。

## 重审条件

- 一个真实后续场景显示记录反而导致 Noema 机械重复、错误泛化或忽略当前指令。
- 用户仍需一遍遍重复同一类纠正，说明结构化状态并未改变后续行为。
- DSH 或其他现有宿主已能无额外搬运地共享并执行同一份用户拥有、可撤回的互动状态。
- 记录/撤回流程比直接纠正 Noema 更繁琐，或主动状态对用户没有可感知收益。
