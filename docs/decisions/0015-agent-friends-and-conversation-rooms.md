# ADR 0015：以持续好友和独立聊天空间组织 Noema

- 状态：接受为第一轮开发架构（助手在用户明确委托的产品生命周期内决定）；不是已验证的最终市场定位
- 日期：2026-10-18
- 关联：Issue #2 / M1；[持续型好友与聊天空间](../design/persistent-agent-social-model.md)；[个人 Agent 产品版图](../research/personal-agent-landscape.md)；[经验到专业实践](../research/experience-to-practice.md)

## 问题

Noema 的现有原型把用户交流和后台 worker 建在一条根对话上。这种模型能验证“聊天不中断，后台任务可返回”，但无法体现用户近期确认的产品关系：Noema 是长期核心伙伴，专业 agent 是可持续联系的好友；同一好友能与用户私聊，也能参与群聊或协作。

外部对照同时提高了 standalone-app 的门槛。OpenAI Dots 已提供个人主 agent、后台任务、连接器以及 Codex 任务委派；Gemini Spark、Meta Muse 和其他服务也覆盖跨应用的个人助理工作；OpenClaw/Hermes 可自托管多个 agent。Noema 不能仅因拥有统一 UI、agent 列表或后台调度就宣称独特价值。

## 决定

第一轮开发将 Noema 作为**用户拥有的持续 agent 关系与聊天空间**来构建，而不是单一 agent 配置、任务看板或应用聚合壳。

1. **Noema 拥有 agent 身份。** Noema 本身和专业好友各有稳定的 Noema 身份记录；身份围绕核心关系或一门可积累实践的专业范围，而不是单个任务。Codex、DSH、模型、skill 和工具是可替换的执行 runtime/capability，不是好友身份。
2. **Noema 拥有聊天空间。** 私聊和群聊是独立、有成员的上下文；同一好友可以加入多个房间。每条消息归属于一个房间。创建/恢复某个 runtime session 不改变 agent 身份。
3. **房间历史默认不合并。** agent 每次响应至少接收当前房间内容及必要的 agent/user profile；不能因为它参加过另一个房间就把另一房间 transcript 自动灌入。跨房间事实检索必须作为单独、可追溯且受权限控制的操作；本 ADR 不要求首个切片实现通用跨房间搜索。
4. **当前界面以社交聊天为骨架。** 联系人、私聊、群聊是产品结构；执行任务若发生在某个房间内，应在该房间保持可见、可介入，而不是全部塞进一个全局 task dashboard。用户应可继续与 Noema 或其他好友交流，不被一个长任务锁住。
5. **经验的三条生命周期保持分离。** 房间事件保留事实来源；用户明确的互动偏好服务于该用户如何与 agent 配合；专业实践变化服务于好友如何工作。一次事件查询、一次用户纠正、一次任务成功不是同一个 learning signal。首轮不实现模型自动把经历提升为永久专业规则；相关证据门槛继续由后续设计决定。
6. **执行能力通过 replaceable adapter 接入。** 第一轮优先复用现有模块化单体、SQLite、FreeLLMAPI chat client 和现有 DSH/Codex 适配器。身份/房间/消息状态由 Noema 持有；后台 harness 只持有其 native execution session。除非接入失败证明需要，否则不建新 daemon、微服务、插件市场或云记忆层。
7. **旧根对话安全迁移，不清理用户数据。** 原 root transcript 与 worker history 可映射到 Noema 私聊/活动历史或保留为只读归档；任何迁移都保留可恢复副本与来源，不覆盖原始记录。

## 第一条可运行切片

从现有桌面应用演进一条真实、可使用的社交 agent 路径：

- 用户能在联系人中看到 Noema 和至少一位专业好友，并与各自开启私聊。
- 用户能创建一个包含同一好友的群聊；agent 身份与 profile 不因房间变化而复制，房间消息上下文彼此隔离。
- 消息通过真实模型/runtime 生成，而非静态 mock；当前使用的 provider/runtime 与失败状态可见。
- 用户可从当前房间控制本轮发送给哪些 agent；多个 agent 不应仅因身处同一群聊就无条件同时发言或执行。
- 旧 root 对话在迁移后仍可查看；迁移过程可回滚。

该切片验证核心交互与状态所有权，不声称已实现自我成长、跨房间自动回忆、自动主动服务或产品已适合日常使用。它是后续评估 Noema 差异价值的真实产品试验，不是完整愿景的削弱版替代。

## 替代方案

- **单一 personal agent + 任务/项目空间。** Dots、Spark 等已有产品明显覆盖这一路线；其实现更简单，但不能表达用户已确认的“同一位专业好友被单独联系并在群里继续合作”的关系模型。
- **多个 agent 作为 prompt/persona 配置。** 易实现，但若身份、房间、实践和 runtime 状态未分离，换一个任务或会话就可能退化为重复配置的 disposable agent。
- **将 Noema 直接作为 OpenClaw/Hermes 插件。** 可快速获得 runtime 能力，但 Noema 的用户身份/房间/好友状态会依附宿主；除非未来证据显示宿主已能以相同控制权跨 runtime 管理好友，否则不作为当前产品 owner。
- **继续扩展根对话 + 隐藏后台 worker。** 保留现有一条纵向切片，但继续把协作关系编码成单房间事件，无法支持独立好友私聊、群成员和每房间上下文。

## 后果与重审条件

- 需要新增 Noema-owned agent/room/message 领域边界和数据库迁移；复杂度是本次决定接受的成本，必须通过薄 schema 和兼容旧数据控制。
- 社交聊天 UI 是用户已确认的交互语法；具体视觉风格与每个回复何时触发仍由真实运行迭代确定，不从竞争产品直接拷贝。
- “个人 agent 网络”是助手为第一轮开发采用的产品假设，不代表用户已确认所有 specialist/群聊语义；所有首次出现的产品主张都须通过可运行应用和用户最终核验。
- 若 Dots/Work、OpenClaw/Hermes 或低成本组合能提供相同的好友身份连续、房间隐私边界与可演进专业实践，Noema 的独立应用理由必须重审；若用户更常使用单一 assistant 而非多好友房间，应缩小或改写产品定位。
- 若 agent roster/群聊带来噪音、身份混乱或维护成本高于收益，保留单个 Noema 核心但不强制创建或使用好友。
