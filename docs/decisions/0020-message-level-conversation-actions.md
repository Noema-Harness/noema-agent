# ADR 0020：按消息对象组织回复与跨房间分享

- 状态：接受为可撤回的交互决定（助手在用户委托范围内修正）；用户明确指出旧方案反直觉并给出转发/回复区分
- 日期：2026-10-19
- 关联：Issue #87；ADR 0015；WhatsApp 官方 [转发消息](https://faq.whatsapp.com/887468535575482/?cms_platform=web) 与 [回复消息](https://faq.whatsapp.com/3240283752856917/?cms_platform=web) 交互文档

## 问题

Noema 的房间历史彼此独立。用户需要把另一私聊或群聊的消息带入当前房间时，先前设计把当前草稿当搜索词，让用户在输入框附近搜索、勾选，再把片段隐藏注入模型。这个做法将“消息转发”“当前消息回复”和“agent 长期记忆”混为一谈，既不符合熟悉的消息应用操作，也让跨房间数据进入模型而没有成为当前聊天中可见的事件。

## 决定

保持房间隔离，并把跨房间分享设计为消息级转发；把“回复”限定为当前房间的具体消息。

1. **动作附着在消息，而不是 composer。** 每条可操作消息提供清楚的“回复”和“转发”动作。移除常驻或按草稿触发的跨聊天检索入口。成熟消息应用也把回复/转发作为消息菜单中的动作，并在目标消息上标明回复关系或转发来源；Noema 借用交互语法，不复制其品牌视觉。
2. **回复关系留在同一房间。** 用户回复当前房间某条消息时，composer 显示简短引用预览；发送后，时间线上的新消息标明被回复的原消息。跨房间消息不作为“回复”对象。
3. **跨房间内容只能显式转发。** 用户从来源房间选择一条或多条已完成、可见的 user/assistant 消息，进入目标房间选择和发送流程。第一版只允许同一来源房间的多个消息构成一个合并转发；system、失败、中断、streaming、工具参数和隐藏内容不可转发。
4. **转发是一条可见的新消息。** 目标房间时间线保存来源房间、原发言者、时间和发送时的内容快照；多条消息呈现为一个可展开的合并转发卡片。来源之后编辑或变化不改写该副本；源房间保持不变。
5. **转发的模型可见性来自目标房间本身。** 目标消息作为普通用户可见历史参与目标房间后续上下文，不以隐藏引用参数附加在模型请求中。发送前明确显示目的 room 和其参与者；用户发送即是在该 room 分享，不把此动作说成 agent 自动记忆或长期学习。
6. **失败与取消不产生半转发。** 取消选择不会写入任一房间；目标 room 不存在、来源消息不再符合条件或快照校验失败时，保留来源时间线，不静默降级成另一个动作。

## 外部交互依据

WhatsApp 官方 Web 指引把转发设计为“来源消息菜单 → Forward → 选择目标聊天 → Send”，转发内容带有 Forwarded 标记；回复则是来源消息菜单 → Reply，回复链显示被回应的具体消息。该证据支持动作对象与交付目的地分离，也支持区分“在当前对话回复”和“把内容分享去另一个对话”。它不证明 Noema 的多智能体产品价值，仅作为成熟消息交互的基线。

## 替代方案

- **按当前草稿搜索并勾选历史片段：**已被用户否定；把输入意图误作检索查询，动作脱离消息来源，增加输入区常驻 UI，并隐式混入模型上下文。移除。
- **每轮自动合并房间历史：**违反默认隔离，来源不可控，扩大无关上下文和隐私暴露。拒绝。
- **把长期记忆当转发替代品：**一次内容分享不等于 agent 专业成长；不将转发内容自动提升为 profile、memory 或 skill。
- **要求用户复制粘贴：**能够工作但会丢失来源信息，仍将消息整理负担留给用户。只作为手动 fallback。

## 后果与重审条件

- 需要在社交消息模型中区分回复关系与转发快照，并在窄屏下采用按需显示的消息操作，避免常驻工具栏或搜索面板压缩聊天区。
- 转发到群聊会让该群成员及本轮回应模型看到选定内容；发出前必须明确目的地和参与者。凭据检测可作为额外警告/过滤，不能替代用户对分享范围的确认。
- 如果用户主要需要让 agent 跨房间理解某个事实，而不是让房间成员看到那条消息，再另行研究“记忆”对象的权限与交互；不得偷偷把转发演变回隐藏上下文注入。
- 当前设计是消息应用基础交互的产品假设，尚未由用户最终体验验收；若消息操作过密或转发对 Noema 日常协作无帮助，优先删减，而不是增设常驻面板。
