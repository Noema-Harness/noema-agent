# ADR 0007：后台 Agent 自述不等于任务验收

- 状态：接受为 M1 文件任务原型；2026-10-16 加入最多三次的有界续做；尚未证明足以覆盖真实编码项目
- 日期：2026-10-14
- 决策者：助手，在用户委托的 Noema 生命周期自主决策范围内

## 问题

真实 scratch 测试要求 DSH 创建指定内容的 `README.md`。DSH 进程正常结束，但其唯一文件工具调用只是 `glob`；它报告没有找到该文件，Noema 的本地文件检查也确认文件不存在。随后 Noema 的根模型却总结说文件“已创建”。这不是简单的措辞瑕疵，而是把 Agent 的自述错误地提升成用户目标已完成。

随后一条隔离的真实 Noema → FreeLLMAPI → DSH 合成任务暴露了互补的错误：DSH 做了 2 次文件操作并写出了完全匹配的 `README.md`，但上游额度耗尽后 worker 以 `dsh_process_failed` 退出；旧逻辑因进程失败而跳过文件 verifier，记为 `verification_unavailable`。因此，只把非零进程结果视为失败同样会隐藏真实文件状态。两次相邻重放分别在 `auto:noema-free` 与 `free-router` 的根模型调用阶段失败；FreeLLMAPI 日志确认 BlockRun/Kilo/OVH 连接经本机代理重置。这些额外失败未启动 DSH；未修改 FreeLLMAPI 或代理设置。

用户此前多次指出，模型无法仅凭自己的最终报告验证代码、文件或游戏产物。这个实际失败证明，仅加一条“验证结果”提示或让 Noema 再总结一次，不足以解决问题。

## 决定

1. **把进程终态与条件核验作为两条独立轴。** DSH 的 `completed` 只表示进程结束，`failed` / `interrupted` 也不代表已有文件改动全部无效。DSH session 已启动后，不论进程以何种终态结束，Noema 都对已有产物执行明确的只读检查（若有检查计划）；UI 分别显示“worker 是否完整结束”和“列出的文件条件当前是否通过”。这不自动把一个失败/中断的 task 改标为 completed，也不把文件检查外推为整体验收。
2. **委派请求携带显式、机器可检查的验收条件。** 第一版只支持工作区相对路径的 `file_exists`、`file_contains`、`file_equals`，每项任务最多 16 项。根 Agent 从用户明确要求中抽取；无法确定时传空列表，不编造条件。验收条件和 DSH 的原生执行会话分开存储，用户可查看具体检查项。
3. **Noema 主进程独立执行只读检查。** 检查只允许在本次任务已授权的 workspace 内访问普通文件，不跟随逃出 workspace 的符号链接，不执行 shell、脚本或网络请求；文件尺寸有上限，实际内容不会被复制到验收记录或日志。workspace 以外的产物和游戏画面不在第一版能力范围内。若 DSH session 从未启动，Noema 不用预存文件状态声称任务检查通过。
4. **验收修复与可安全续接的 worker 失败共享一个有界后续运行预算。** `completed` worker 后，若只读检查明确证明文件条件未通过，Noema 将失败项交回同一 DSH session 修复；若 worker 以明确的 `RATE_LIMIT` 结束，且提示的冷却时间不超过 120 秒，或以 `dsh_process_failed` 结束，则只有在 session ID 已持久化、Noema 的检查全部通过或仅有可修复缺项、用户没有停止任务或关闭应用时，才在同一 session 中续做。worker 失败后的续接先检查原任务与现有工作区，只完成明确未完成的要求并返回最终状态；所有验收修复与失败续接共用最多三次后续运行，每次后都重新检查。缺少 session、限流提示超出等待上限、核验不可用/不可修复、工具循环、超时、启动失败、用户停止或预算耗尽时，保留失败状态和证据，交给用户决定；不得一般性重发任务。
5. **worker 不完整时，结果事件使用确定性说明。** 文件检查通过只表示列出的文件条件当前满足；若 DSH 失败/中断，事件仍说明 worker 未完整结束、其他要求可能未完成。文件检查失败/不可用也由确定性事件报告，不交给 LLM 润色成成功。只有正常 worker 结束且核验结果可用时，才交给根 Agent 总结。
6. **验收状态随后台任务记录持久化。** SQLite 记录检查计划、结果、尝试次数和状态；DSH 继续拥有原生执行 session。删除/清理后台任务时，这些核验元数据与任务一同处理，不额外保存完整文件内容。

## 为什么属于 Noema

DSH、Codex 或其他 worker 负责执行，不能成为 Noema 判断自身目标是否完成的唯一来源。Noema 是用户的根 Agent 和任务所有者，保存验收契约、对比客观本地状态、决定是否继续同一执行 session。这是跨 harness 的责任边界，不是再造一个代码 worker；但它是否比用户直接打开 DSH 查看更有价值，仍需使用验证。

### 2026-10-16 修订：瞬时限流后的有界续做

隔离的多文件任务曾只写出 `src/slug.mjs`，缺少测试与说明文件；DSH 明确返回 `RATE_LIMIT`，提示最早冷却约 31 秒，Noema 已持有同一 session ID，文件验收可安全定位缺项。旧边界会核验并标失败，但只等用户手动续接，这与 Noema 应跟进未完成任务的目标不符。

因此只为**明确限流 + 有界冷却时间 + 可续接 session + 可修复的文件核验失败**开启自动续做。等待期间任务保持运行状态，用户可以停止；每次重试使用原 session 和原工作区，先依核验缺项修复，再重新核验；所有后续运行合计最多三次（累计等待不超过三分钟）。一般进程失败、中断、路径/权限问题、不可用的核验条件不自动续做。若 FreeLLMAPI/DSH 的冷却提示格式变化，此判定应当失败关闭并保留人工续接路径。

> 修订：上文记录的是首次实现时的预算，后续单次冷却上限调整为 120 秒；若三次续做均等待完整冷却，理论累计上限为六分钟。后续边界以第 4 条为准。

### 2026-10-16 后续修订：核验通过但 worker 未终止

无纠正的隔离基线曾在 DSH 限流退出前写出全部列明文件，Noema 核验为 `verified`，但 worker 仍未正常结束。即使列明文件条件通过，Noema 也不能把失败进程直接标为整体完成；限流且 session 可续接时，应再进入同一 session，要求先检查现有工作区和原任务，只完成可能尚未结束的明确要求，并返回最终状态。此修订扩展了上文的限流续做条件：核验状态可为 `verified`，也可为 `failed` 且 `repairable=true`。等待和续做预算以本修订为准：每次最多 120 秒、续做最多三次、累计等待最多六分钟；其他错误仍失败关闭。

### 2026-10-16 再修订：非限流进程失败后的安全续接

无纠正基线曾完成两个文件并通过内容检查，但 DSH 在返回最终结果前以普通非零退出结束。仅对 `RATE_LIMIT` 自动续接会让这类“产物已写、执行状态未收尾”的任务仍等用户手动操作。因此，除了限流外，也允许对 `dsh_process_failed` 做一次同 session 续接；前提仍是 session 已持久化、文件检查结果为全部通过或仅有可修复缺项、用户未停止。若检查已通过，续接提示只要求检查工作区并返回最终状态；若检查失败，只修复列出的缺项。明确的工具循环、任务超时、启动失败、不可修复核验错误不自动重试。仍与限流续做共用最多三次后续运行预算。

### 2026-10-17 修订：只修复明确被参数校验拒绝的文件工具循环

一次隔离的真实 Noema → FreeLLMAPI → DSH 合成运行中，DSH 在没有创建任何验收文件的情况下触发了 `dsh_tool_loop`。会话轨迹显示：前两次 `glob` 只读调用成功；随后同一 `edit` 调用多次因 `replace_all` 被模型序列化为字符串而返回 `INVALID_ARGS`，没有文件写入成功。工作区 verifier 对 8 项内容条件全部报告缺失。当前安装的 DSH headless JSON 协议将工具结果的错误状态与文本发出；随装 DSH `dsh-tools` 实现先校验参数，校验通过后才调用工具 handler。根因证据足以区分这类“写入尚未执行”与一般循环，但不足以证明免费路由稳定或任意工具循环都安全。

因此把“工具循环一律停止”收窄为以下唯一例外：同一任务的本地执行记录必须证明，循环保护触发前重复的**同一个文件 `write`/`edit` 参数**已至少两次收到明确的参数校验失败结果；当前触发停止的调用必须与它完全相同；此前同一任务没有成功的文件写/编辑调用，也没有无法分类的文件写结果；且 Noema 本地验收仍是全部通过或仅有可修复缺项。满足时，Noema 可在同一个 DSH session 中进行**一次**额外纠错续接，并沿用总计最多三次后续运行预算。纠错提示指出先前文件操作在参数校验阶段被拒绝，列出未通过的验收项，要求修正 JSON 参数类型并避免对不存在的文件调用 `edit`。本次额外续接后仍失败、再次循环、状态不可分类、缺少 session、验收不可修复/不可用、用户停止或应用关闭，均维持失败/中断并保留证据；不做一般性任务重发。手动“在原 DSH 会话中继续”路径仍保留。

### 2026-10-17 修订：多文件验收计划上限

一次真实隔离的根对话试验中，任务明确要求 8 项文件内容核验；模型生成的 `verificationChecks` 数量超过 Noema 的 8 项上限，根 Agent 因此在 DSH 派发前拒绝该计划，实际 worker 完全没有启动。这是本地可验证的 schema 容量边界问题，不是文件 verifier 误报或 DSH 失败。将硬上限与根工具 schema 同步提高到 16 项，仍拒绝超过上限的计划；不静默截断，不降低已有验收条件。该 E2E 暴露的上限失配本身不证明提高上限即可完成任务，后续端到端仍需观察。

## 后果与局限

- 这只证明文件层面的简单条件，不能证明代码设计正确、测试充分、游戏画面/模型正确或用户体验良好；这些需要对应的运行/视觉证据源。即使 worker 进程失败而文件条件通过，也不能把 task 状态改为“整体完成”。自动续做共用三次上限；工具循环例外仅适用于能证明重复文件写操作在参数校验阶段被拒绝、且此前没有文件写入成功的情形。
- LLM 可能抽取错验收条件，因此界面须展示 Noema 实际检查的目标和结果；验收计划本身不能被隐藏在 prompt 里。
- 没有可验证条件的任务仍可委派，但完成态必须明确为“未独立核验”，不能靠根模型的自信措辞补足。
- 真实 DSH 测试曾因 E2E main bundle 未重建而把合成 session 写入 Noema 自有 `userData/dsh-home`。后续复测使用 `NOEMA_E2E_DSH_USER_DATA_PATH`，并将 root DB、DSH userData 和工作区限制在同一个隔离目录；用户的 `.dsh` profile 与真实项目工作区保持不变。

## 重审条件

- 一次自动修复后仍反复失败，或修复造成超出原授权范围的副作用。
- 瞬时限流错误无法可靠识别、冷却时间不准确，或同 session 自动续做引入重复副作用。
- verifier 检查的只是路径/字符串，却让用户误以为软件功能或业务目标已证明。
- DSH 提供成熟、独立且可重现的结构化验收证据，使 Noema 无需自己扫描 workspace。
- 用户真实使用中更看重对未结构化产物的视觉验收；届时应先增加对应证据源，而不是扩大字符串检查范围。
