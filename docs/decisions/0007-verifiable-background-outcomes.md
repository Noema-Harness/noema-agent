# ADR 0007：后台 Agent 自述不等于任务验收

- 状态：接受为 M1 文件任务原型；尚未证明足以覆盖真实编码项目
- 日期：2026-10-14
- 决策者：助手，在用户委托的 Noema 生命周期自主决策范围内

## 问题

真实 scratch 测试要求 DSH 创建指定内容的 `README.md`。DSH 进程正常结束，但其唯一文件工具调用只是 `glob`；它报告没有找到该文件，Noema 的本地文件检查也确认文件不存在。随后 Noema 的根模型却总结说文件“已创建”。这不是简单的措辞瑕疵，而是把 Agent 的自述错误地提升成用户目标已完成。

用户此前多次指出，模型无法仅凭自己的最终报告验证代码、文件或游戏产物。这个实际失败证明，仅加一条“验证结果”提示或让 Noema 再总结一次，不足以解决问题。

## 决定

1. **区分进程终态和用户目标验收。** DSH 的 `completed` 只表示进程结束。Noema 只有在自身可重复执行的验收条件通过后，才标记对应产物“已核验”；无确定性检查的任务显示“Agent 已结束／Noema 未独立核验”，不能把 Agent 自述标成已验收。
2. **委派请求携带显式、机器可检查的验收条件。** 第一版只支持工作区相对路径的 `file_exists`、`file_contains`、`file_equals`。根 Agent 从用户明确要求中抽取；无法确定时传空列表，不编造条件。验收条件和 DSH 的原生执行会话分开存储，用户可查看具体检查项。
3. **Noema 主进程独立执行只读检查。** 检查只允许在本次任务已授权的 workspace 内访问普通文件，不跟随逃出 workspace 的符号链接，不执行 shell、脚本或网络请求；文件尺寸有上限，实际内容不会被复制到验收记录或日志。workspace 以外的产物和游戏画面不在第一版能力范围内。
4. **确定性缺失/内容不符时允许一次自动修复。** 若安全检查明确证明文件不存在或文本不符，Noema 把失败项交回同一个 DSH 原生 session，最多自动修复一次，并重新执行同一验收。Noema 不重放原始任务、不覆盖原 workspace 授权，也不无限循环。第二次仍失败时标为未验收，保留报告和 DSH session 供用户继续或检查。
5. **核验失败不由 LLM 改写成成功。** 若独立检查未通过或无法安全执行，Noema 用确定性的时间线事件说明状态与失败项，不调用模型来润色这条失败；DSH 原始报告仍可展开查看。核验通过后才把检查结果与 DSH 报告一起交给根 Agent 形成回流说明。
6. **验收状态随后台任务记录持久化。** SQLite 记录检查计划、结果、尝试次数和状态；DSH 继续拥有原生执行 session。删除/清理后台任务时，这些核验元数据与任务一同处理，不额外保存完整文件内容。

## 为什么属于 Noema

DSH、Codex 或其他 worker 负责执行，不能成为 Noema 判断自身目标是否完成的唯一来源。Noema 是用户的根 Agent 和任务所有者，保存验收契约、对比客观本地状态、决定是否继续同一执行 session。这是跨 harness 的责任边界，不是再造一个代码 worker；但它是否比用户直接打开 DSH 查看更有价值，仍需使用验证。

## 后果与局限

- 这只证明文件层面的简单条件，不能证明代码设计正确、测试充分、游戏画面/模型正确或用户体验良好；这些需要对应的运行/视觉证据源。
- LLM 可能抽取错验收条件，因此界面须展示 Noema 实际检查的目标和结果；验收计划本身不能被隐藏在 prompt 里。
- 没有可验证条件的任务仍可委派，但完成态必须明确为“未独立核验”，不能靠根模型的自信措辞补足。
- 真实 DSH 测试曾因 E2E main bundle 未重建而把合成 session 写入 Noema 自有 `userData/dsh-home`。本决策的继续实现必须使用 `NOEMA_E2E_DSH_USER_DATA_PATH` 的隔离测试路径；用户的 `.dsh` profile 与真实项目工作区保持不变。

## 重审条件

- 一次自动修复后仍反复失败，或修复造成超出原授权范围的副作用。
- verifier 检查的只是路径/字符串，却让用户误以为软件功能或业务目标已证明。
- DSH 提供成熟、独立且可重现的结构化验收证据，使 Noema 无需自己扫描 workspace。
- 用户真实使用中更看重对未结构化产物的视觉验收；届时应先增加对应证据源，而不是扩大字符串检查范围。
