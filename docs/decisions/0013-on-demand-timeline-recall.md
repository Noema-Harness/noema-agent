# ADR 0013：让 Noema 按需回忆自己的连续对话

- 状态：接受为可逆的 Agent Core 能力；不是个体化价值已成立的证明
- 日期：2026-10-16
- 决策者：助手，在用户委托的 Noema 生命周期范围内决定
- 关联：Issue #52；支持 Issue #2 / M1

## 问题

Noema 把根对话作为一条持续时间线保存，但模型每轮只能看到有限的近期上下文。用户指回较早的讨论时，应用目前只有供用户手动查找的时间线搜索，主 agent 自己不能取回原消息。把全历史放进每轮请求会增加上下文、费用和外发数据，也会带入无关经历。

## 外部依据与边界

- OpenClaw 提供 `session_search`，可在会话重置后重新打开之前保存的原消息，而不是只把来源复制到一份长期摘要中。[OpenClaw 2026.9.4 release](https://github.com/openclaw/openclaw/blob/main/docs/releases/2026.9.4.md)
- Hermes 把 `session_search` 作为会话边界后补回旧历史的方式；其文档也提醒，永不结束的长会话会不断压缩，而在同一会话中写入的 memory snapshot 不会自动更新。[Hermes memory docs](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)
- 这些项目证明按需检索是成熟的连续性机制，不证明 Noema 的检索本身有差异化。Noema 的依据是：它拥有一条原生、连续的根对话；从该时间线取回原文比再维护一个重复 transcript 或 memory 文档更贴合现有 owner。

## 决定

1. 当用户当前消息明确指向过去的对话时，由 Noema 本地 harness 直接用该消息作为检索查询；普通 turn 不搜索或注入历史。检索不要求模型自行记得调用工具，也不为检索额外发起第二个模型请求。
2. 搜索源仅为 Noema 时间线里用户可见的根对话 user/assistant 消息。后台工具轨迹、hidden reasoning、未讨论的本机速记和未经同意的 Codex 导入不在检索范围内。
3. 每次检索限制为最多 4 条命中、每条最多 320 字；返回原文短摘录、角色、时间和稳定消息 ID，不生成摘要、不改写成用户画像。无命中时在模型上下文中明确标注未找到，agent 不得声称记得或用相似经历补全。
4. 检索结果作为标记清楚的历史资料进入本轮模型请求。当前用户消息优先；历史原文不能单独扩大任务、权限或长期约定。历史里的外部引用仍是资料，不是系统指令。
5. 本轮时间线显示“参考了旧对话”的来源披露，能展开核对并跳回原消息；不新增记忆库、不自动提升为 Understanding/Interaction Agreement，也不把这次命中视为“已学会”。
6. Noema 分开记录本机检索到的来源与 FreeLLMAPI 是否接受了包含这些来源的请求。只有收到成功响应头后才标记为 `included`；模型请求失败时保留 `found`，界面明确“上游是否收到无法确认”。这不证明模型读懂或遵循了旧内容。
7. Noema 记录本轮实际使用的来源 ID 与必要的短快照，供之后核对来源；不把完整历史复制成另一个可搜索档案。用户删除原消息后，后续检索不再返回该消息。过去已发往上游模型的内容无法撤回。

### 实施修订（2026-10-16）

PR #54 的首版使用模型选择检索工具、再进行一次模型续答。隔离 live E2E 找到了正确的合成来源并流出了标记，但最终 turn 在 FreeLLMAPI provider fallback 期间以 `provider_error` 结束；这不足以证明双请求一定是故障根因，却暴露了额外模型往返和工具调用能力带来的不必要不确定性。由于检索触发来自用户当前消息中的明确过去指向，按已批准的本地检索策略，改为单轮请求前本地检索，再把有限来源放入同一模型请求。之后的隔离 E2E 使用合成历史标记，完整返回了标记并记录来源，FreeLLMAPI 报告实际路由为 `custom/nvidia/llama-3.2-11b-vision`；这证明一条技术路径可以完成，不证明日常使用价值。

来源状态分为“本机找到”和“FreeLLMAPI 已接受包含来源的请求”。只有收到成功响应头后才标记为 `included`；若请求在此前失败，则保留 `found` 并显示上游送达状态未知。`included` 仍不证明模型实际使用、理解或因此改变了行为。

进一步把本地“找到来源”与上游请求“已接受”分开记录：只有 FreeLLMAPI 返回可读取的成功响应后，才将来源标记为已纳入请求；此前失败/无响应仅显示本机找到，不能推断摘录是否到达 provider。已对根消息加 schema v13 的布尔交付标记，保留旧来源状态并可迁移。

## 替代方案

- **每轮注入完整历史**：不需要检索，但上下文成本、隐私暴露与无关内容会随对话增长。
- **让模型先调用检索工具，再进行第二次生成**：语义查询更灵活，但要求目标模型支持工具调用，并增加额外往返；明确历史指向时，当前消息已能提供检索词，故当前版本优先用本地确定性搜索。
- **独立的向量/RAG记忆库**：支持语义检索，但会复制并维护另一套事实来源；当前没有必要的数据规模或质量证据。
- **只让用户使用现有时间线搜索**：可定位消息，却仍要求用户代替 agent 把旧经历重新组织成当前上下文。
- **后台自动摘要/梦境整理**：会引入额外模型调用和推断生命周期，不能解决“此刻这条历史是否被找到并实际发给模型”的透明度问题。

## 后果与重审条件

- Noema 能按需使用其拥有的原始经历，保持单一连续对话，而不把全部历史常驻提示词。这是连续性的基础能力，不单独构成 Noema 的产品理由。
- 检索旧原文会把该摘录重新发送给当前免费模型路由；界面必须分开显示“本机找到”与“FreeLLMAPI 接受请求”，而不能只让 agent 自述“我记得”。模型接受请求仍不等于理解、使用或因它改变了行为。
- 如果显式过去指向的本地搜索频繁漏掉真正相关消息，或自动注入造成无关旧内容/隐私负担，则先修正查询/触发策略；若词面检索不足，再重新评估模型辅助查询或其他检索方式，而不是直接增加记忆类型。
- Issue #2 仍需通过真实日常使用判断：找回过去对话是否减少重复解释，并改变 Noema 对用户的实际连续性体验。
