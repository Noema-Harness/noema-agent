# ADR 0029：持久成员、隔离执行会话与项目协作

- 状态：目标边界已接受；分阶段实现，不能据此宣称能力已交付
- 日期：2026-10-23
- 依据：用户在本线程中明确澄清的产品模型；下述数据库与投递边界为助手在开发授权内作出的实现选择
- 关联：[总规划 #109](https://github.com/c3115644151/noema-agent/issues/109)、[#110](https://github.com/c3115644151/noema-agent/issues/110)、[#112](https://github.com/c3115644151/noema-agent/issues/112)、[#113](https://github.com/c3115644151/noema-agent/issues/113)
- 取代：ADR 0015 中“群房间即执行上下文”的目标解释，以及 ADR 0025 中继续新增 Noema 独立主题会话的方向；保留已有数据和兼容访问。ADR 0016 的 DSH 路径继续说明当前实现，不再作为永久依赖。

## 问题与决定

用户不应反复把背景、阶段报告和后续指示搬运于多个执行窗口。Noema 保有一条连续主会话，承担理解、澄清、协调和结果把关；实际执行由专业成员完成。普通交流、思考与创作仍然可以直接在 Noema 对话中发生，这不是只面向编程的任务管理器。

成员是长期身份，不是一次调用。不同项目的执行上下文必须隔离，否则保留身份就等同于无限堆叠历史。项目群则承担共享交流与项目状态，不是所有成员共用的模型窗口。

| 对象 | 唯一职责与生命周期 |
| --- | --- |
| 成员身份 | 稳定 ID、当前资料、自己的工作区与能力资产；名字和初始专业范围不构成永久枷锁，也不等同于工具权限 |
| 成员常驻会话 | 同一成员的日常交流与短委托上下文；用户和 Noema 可向其投递，消息仍有来源和可见范围 |
| 成员项目会话 | 一个成员在一个项目中的独立上下文；与身份关联，归档后保留，恢复原项目时续接；不复制常驻私聊原文 |
| Noema 主会话 | 用户连续交流与内部协调的主线；不为每个项目再创建一个 Noema。内部报告可进入协调上下文，但不是用户主聊中的原始消息 |
| 项目 | 目标、成员、工作状态、待评请求与成果的持久归属；关联一个共享群空间，不从普通旧群自动推断出项目 |
| 共享消息 | 群中所有成员可查的交流；不是工具日志，也不自动等于每位成员都要再运行一次模型 |
| 执行请求与报告 | 指向明确成员会话、来源和权限范围；保留实际状态、结果与失败，使用稳定 ID 防止重启或重试重复派发 |

## 上下文、路由与控制

1. 所有模型请求都由应用明确选择一个执行会话。身份相同不是加载其他私聊或项目历史的理由。项目内的成员详情/私下交接，仍路由到该项目会话；不能误投到成员常驻会话，也不另建一套无归属的“私聊线”。
2. 交流房间、上下文会话与执行事件分别建模。用户界面读取经过范围过滤的消息投影；隐藏的内部报告不先发送给用户 renderer 再靠 CSS 隐藏。Noema 默认不旁听用户与成员的私人交流。
3. 一个会话同时只有一个活动执行循环。发消息、队列、取消和反馈携带请求/代际标识；中断在安全边界投递，不能把“收到新消息”实现为盲杀可能正在写入的工具。必要时先核对副作用，再恢复。
4. 所有群消息，包括 @ 消息，都公共可查。被 @ 的成员优先收到；其他成员保留未读，在适当边界获知并按需读取。普通成员请求重大共同调整时向 Noema 反馈；Noema/管理员可 @所有人。避免逐工具调用唤醒 Noema，避免无意义的全员轮询与模型相互回复。
5. 成员的阶段报告或完成/阻塞事件唤醒 Noema，附必要结论、证据、变更与未决事项；完整执行记录按需查阅。Noema 默认继续安排下一步，并把有意义的进展转述给用户。必要人类判断暂停对应项目，收到明确反馈后恢复；不能把用户的普通聊天当成批准。
6. 单人成员足够的短委托不建群。复杂项目才组织团队；从现有成员中匹配，确无合适成员时再创建。新安装仅有 Noema，不预填演示成员或伪造项目进展。

## 资产、成长与归档

成员的工作区由稳定身份定位，包含自己的指令、记忆、技能及经历产物。应用负责作用域、版本通知与可靠读写；成员决定如何修订自己的资产，Noema 负责评议和协调，不替成员编写成长内容。工具权限是独立状态，改资料或新增 skill 不扩大权限。

新会话组装该成员当前资产；已有会话在下一安全调用边界感知版本变化，不依赖等待上下文压缩。项目成员完成有价值的经历后，可自行总结、修订资产及定位，并给常驻会话留下简报；产物保留来源和撤回路径。成长不是每次小改强制追加一次总结调用，也不是必须改名。

项目完成、必要成长处理后归档，隐藏活跃列表入口而保留群、成果和成员项目会话。新相关需求恢复原项目；恢复后的小修订不机械重复完整成长。待评审、归档和实际执行中断是不同状态。

## 持久化与迁移

维持 Electron 模块化单体、主进程服务与 SQLite；成员身份、会话、项目和报告由 Noema 自己拥有，不依赖外部 harness 的 session ID 定义。复用当前模型、密钥、搜索、工具适配与核验模块；自有执行层逐步接管，DSH 等仅保留兼容路径。

按真实调用闭环增量引入领域表，不为本 ADR 一次预建整个平台。升级前建立可校验的版本快照；迁移保持事务和外键约束。已有成员、群、主题、消息、旧任务和撤销的权限保留，不靠删除演示数据来清理用户历史。旧群不自动变成项目；旧主题继续可访问，但不作为新 Noema 分支的默认入口。

## 取舍、来源与重审

放弃“每个成员永远只用一个上下文”：它虽接近人的直觉，却会混入多个项目的执行噪声。也不采用“每个项目都是完全独立的新成员”：这会丢失身份与能力资产的长期连续性。共享资产可能污染未来任务，因此必须有来源、版本和可撤回性，不能只相信模型复盘文本。

已追读固定版本源码：OpenCode `d93568f3344e1a93297d56bc1dc71892104856d0` 的 `packages/core/src/session/sql.ts`、`store.ts` 将项目、会话、消息及执行 claim 分开；Goose `b89ab563a034ab9ff323a916fd1aef7be6ea8d67` 的 `crates/goose/src/session/session_manager.rs` 使用事务迁移并处理并发初始化。这些是存储/恢复实践的参考，不证明它们实现了 Noema 的组织和成长模型，也不要求照搬其框架或全部表。

若真实使用显示项目隔离严重损害协作、报告唤醒仍使 Noema 上下文/成本失控，或资产共享持续造成回归，应重审具体隔离、检索和投递策略；不能以新增总结调用掩盖问题。主动关切回访的价值已获用户认可，但触发与调度尚未定，本 ADR 不顺带实现常驻模型轮询。
