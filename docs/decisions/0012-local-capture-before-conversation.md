# ADR 0012：允许用户先保存一个念头，再决定是否与 Noema 交谈

- 状态：接受为可逆的日常使用切片；不是 Noema 独立价值已成立的证明
- 日期：2026-10-16
- 决策者：助手，在用户委托的 Noema 生命周期内决定
- 关联：Issue #45；支持 Issue #2 / M1，不替代其验收

## 问题

用户明确希望能把日常遇到的痛点、感悟和发现随手放进 Noema，之后再讨论或吸收。但当前唯一输入路径会立即启动模型：一条只是想留下的想法，也会变成一次外部请求，并触发一条 AI 回复。模型服务暂不可用时，这个捕捉入口也随之失效。

需要区分两种意图：**现在想与 Noema 交流**，以及**先把这件事留在自己的 Noema 里**。不要求用户把每条碎片先包装成完整需求，也不把“记录已保存”说成“agent 已理解或记住”。

## 外部参照与边界

- Apple Notes 的 Quick Note 允许用户从任意 app/屏幕快速保存文字、链接和其他内容；这证明跨应用低摩擦捕获是成熟模式，但其目的仍是个人笔记。[Apple Quick Notes](https://support.apple.com/en-lamr/guide/iphone/iph9e04f3be2/26/ios/26)
- Notion 把 Quick Notes 作为存放想法的单一入口，同时明确提醒持续堆积会变得杂乱；Notion Agent 的 Inbox 流程也保留 Inbox 为来源，而不是把 agent 的整理结果当成原始记录。[Notion Quick Notes](https://www.notion.com/en-gb/help/guides/quick-notes) · [Notion Agent Inbox](https://www.notion.com/help/manage-your-inbox-with-notion-agent)
- Noema 不复制完整笔记应用或引入自动整理流水线。候选增量是：速记和唯一持续的 Noema 对话共享时间线；用户可以明确决定何时把一条速记变成模型交互。这个连通是否值得单独使用仍需 M1 真实场景检验。

## 决定

1. 在现有对话输入框提供并列的 **“发送给 Noema”** 与 **“只记下来”** 动作。第二项将文本写入本机 SQLite，不请求模型、不委派 DSH、不加载 Codex 上下文，也不进入之后的常规模型请求。
2. 速记作为独立时间线事件，显示明确的 **“本机保存 · 未发送给模型”** 状态；不伪装成普通对话 turn，不生成空的 assistant 回复。它与根消息共享一个按时间排序的主时间线，不创建另一个笔记仪表盘。
3. 用户点击 **“与 Noema 讨论”** 才会把该速记原文作为新的根对话用户消息发送到当前所选 FreeLLMAPI 路由，并在本地记录这轮讨论来源于该速记。速记仍是来源记录，不自动被其他请求看到。
4. 速记可以在尚未讨论时编辑或删除。讨论已启动后，原速记内容冻结，以保留“当时实际发送了什么”；删除速记不会删除已进入根对话的副本，也不能撤回已发送给上游模型的内容。界面在讨论按钮旁说明发送去向，在已讨论的记录上说明删除边界。
5. 数据 owner 是 Noema 本机 SQLite。保存速记的写事务失败时保留编辑框内容并给出错误，不得清空草稿或宣称已保存。应用重启后未删除的记录继续存在。FreeLLMAPI 断开不影响保存和删除；只有“与 Noema 讨论”依赖模型服务。
6. 不新增固定期限的自动清理，不自动把速记转成偏好/理解/互动约定，不建立背景 agent。未来若需整理，必须单独设计来源、确认/修订、注入和删除行为。

## 最小数据边界

首版只新增一个本机 `captured_moments` 表：稳定 ID、正文、创建/更新时间、可空的 `discussion_turn_id`、删除/讨论状态。`discussion_turn_id` 只表示 Noema 创建过关联根 turn，不证明模型成功收到、理解或改变行为。讨论 turn 的用户消息仍保存在现有 transcript 中；不复制 hidden reasoning、harness 日志或外部内容。

候选状态流：

```text
编辑草稿 ──只记下来──> 本机速记（不进模型上下文）
                           │
                           ├──删除──> 记录移除
                           │
                           └──与 Noema 讨论──> 新根对话 turn + 来源链接
```

速记本身可被本地搜索定位。普通对话仍只带入其既有上下文规则；速记只有在用户选择讨论时，才作为当前消息进入模型请求。捕获内容不能改变权限、系统规则或 Noema 的长期理解。

## 界面取舍

- 使用现有 composer 与时间线，不增加侧栏、列表页、agent 状态面板或“AI 日记”隐喻。
- “只记下来”与“发送给 Noema”并列，避免把一个复合按钮藏在菜单里；用户可在发出前明确选择数据去向。
- 速记事件应容易区分于模型对话，但共享同一时间线位置和视觉节奏。已讨论速记提供跳转到对应讨论 turn 的操作；仅保存不发送时不得显示“已理解”“已记住”。
- 操作状态包括保存中、保存成功、保存失败、空草稿、编辑、未发送、已讨论、删除。小窗口中 composer 的两个主要动作仍需完整可见。

## 替代方案

- **每条内容都立即发给模型**：现有行为；会把记录和交谈意图混为一谈，增加外发数据与不想要的回复，也依赖免费路由可用。
- **另做一个“速记箱”页面**：容易成为第二个不相关的状态面板，用户仍要把内容复制/转述进 Noema 对话。
- **保存后自动做摘要或永久画像**：超出已确认机制，可能把一次性情绪、算法推荐或模型推测升级为用户事实。
- **继续使用独立笔记 app**：是有力的低维护替代；如果 Noema 无法把“本地捕捉 → 用户选中的讨论 → 可追溯的后续理解”连成实际体验，这个功能不构成独立产品理由。

## 后果与重审触发

- 用户即使不准备好向 AI 提问，也能把 Noema 当作一个本地、持续的个人入口；这让 Noema 在模型网关故障时仍有有限实用性。
- 速记可能只是重复系统笔记功能；先观察真实使用，不预设自动学习，也不把使用条数当作 agent 成长。
- 若用户很少使用、捕获记录很快变成另一堆待整理文档，或独立笔记工具以更少步骤满足同一需求，则移除或收敛此切片。
- 若用户频繁选中速记与 Noema 讨论，并且后续出现可追溯的理解变化，再把这一来源纳入 ADR 0011 的经历—理解生命周期；在此之前不自动总结或注入。
