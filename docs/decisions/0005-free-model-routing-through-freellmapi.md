# ADR 0005: Route Noema model calls through FreeLLMAPI free models

- Status: Accepted as the current provider boundary; selected after the user's explicit direction
- Date: 2026-10-13
- Replaces: ADR 0003 decision 7's local Ollama choice, and ADR 0004 decision 6's local Ollama worker route

## Problem

Noema's only root model route was Ollama. The user has now explicitly directed that model calls use FreeLLMAPI free models and not local models. This changes the data path: conversation content leaves the machine through the local FreeLLMAPI gateway to its upstream provider. The app must disclose that boundary and must not silently fall back to Ollama or a paid route.

## Evidence

- The installed FreeLLMAPI desktop gateway is running locally on the configured port in `%APPDATA%\\FreeLLMAPI\\config.json`; its local API implements OpenAI-compatible `/v1/models` and `/v1/chat/completions` endpoints.
- `GET /v1/models?available=true` returns canonical identifiers and availability flags, but does not expose a reliable price field. Therefore the app must not treat every gateway model as free merely because it is listed.
- A no-personal-data request to `nvidia/nemotron-3-super-120b-a12b:free` returned HTTP 200 through the FreeLLMAPI OpenAI-compatible endpoint. A second request with a required tool definition returned a structured `tool_calls` result, also HTTP 200.
- A no-personal-data request to FreeLLMAPI's `free-router` alias returned HTTP 200 and reported `openrouter/free` as the routed model; the real Electron root conversation also streamed `READY` through this route.
- An earlier isolated DSH attempt through FreeLLMAPI performed one file write, then failed before returning a final result because the selected free route was in cooldown. This is a historical failure; the later real desktop DSH path is verified below, with cooldowns still handled as recoverable failures.
- FreeLLMAPI's curated named chain `noema-free` now contains eight no-cost, tool-capable models: six BlockRun-hosted models plus keyless Kilo and OVH routes. `auto_include_new_models=0` keeps its membership explicit. The DSH adapter is restricted to the alias `auto:noema-free`.
- The local `noema-free` profile includes Kilo's `cohere/north-mini-code:free` route; a local FreeLLMAPI record showed one earlier success, while later attempts ended as `terminated`. The 2026-10-15 `smoke:freellmapi` probe did not include it in FreeLLMAPI's `available=true` response. An earlier user-authorized direct chat-completion request to Kilo, through the local 7890 SOCKS5h proxy, ended before an HTTP status (`curl` reported Schannel's missing `close_notify`); a read-only `/models` call then returned HTTP 200 and listed the model as free. On 2026-10-15, the user authorized one additional no-personal-data direct generation attempt. The request again failed before an HTTP status (`curl` reported Schannel's abrupt TLS close); a read-only catalog request through the same local proxy also failed during TLS negotiation. A control HTTPS GET to `api.github.com` through the same HTTP proxy returned HTTP 200, so the observed failure is specific to the Kilo host/route or its TLS path, not a general outage of the local HTTP proxy. These attempts do not establish Kilo authentication, model availability, or generation capability; they show that the current direct Windows-curl/proxy path did not yield an HTTP response. The route stays out of Noema's picker, and no further generation retry is authorized without new user direction. Kilo's current official docs still describe anonymous access for `:free` models, rate-limited to 200 requests/hour/IP; they also say free prompts/outputs may be logged for training. [Kilo API reference](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/gateway/api-reference.md) · [Kilo authentication](https://github.com/Kilo-Org/kilocode/blob/main/packages/kilo-docs/pages/gateway/authentication.md) · [FreeLLMAPI provider notes](https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/providers/01-supported-platforms.md)
- BlockRun's official docs say its `nvidia/*` free models require no payment, and the live public catalog via the local 7890 proxy reports `nvidia/nemotron-3.5-lightning` at $0 input/output. The installed FreeLLMAPI `noema-free` profile already contains this model and marks it tool-capable. This is provider/catalog evidence, not proof that the route is currently available or that tools work end-to-end. One isolated Noema E2E selection returned `model_unavailable` before any provider request; keep it hidden until FreeLLMAPI reports it available, then validate with an isolated generation. [BlockRun SDK docs](https://blockrun.ai/docs/getting-started/sdk-developers) · [BlockRun live model catalog](https://blockrun.ai/api/v1/models)
- The local FreeLLMAPI app (v0.13.10) had outbound proxy URL `http://127.0.0.1:7890`, mode `forward`, enabled, with an empty bypass list. HTTP CONNECT and SOCKS5h read-only probes to provider hosts both succeeded; the app's draft SOCKS5h connectivity test to Kilo returned success in 783ms. Under an assistant-selected temporary protocol change to `socks5h://127.0.0.1:7890` (same proxy port; no Noema code changes), one isolated root-only request through `auto:noema-free` returned its exact synthetic marker from `custom/nvidia/nemotron-3-ultra-550b`.
- A subsequent full isolated Noema → FreeLLMAPI → DSH run also succeeded under that local SOCKS5h setting: root routed via `custom/cohere/north-mini-code`, delegated the scratch task, DSH made three tool calls, Noema's file verifier confirmed the exact marker, and the result event returned to the root timeline. This is a successful synthetic closure, not a paired HTTP-vs-SOCKS causal test and not evidence that the user's general conversation or personal work is reliable. The exact Cohere route's live BlockRun catalog price is $0 input/output; BlockRun documents its zero-payment free model class. [BlockRun SDK docs](https://blockrun.ai/docs/getting-started/sdk-developers) · [BlockRun live model catalog](https://blockrun.ai/api/v1/models)
- A second full isolated run without an interaction correction also completed and was independently verified; its root response used `custom/nvidia/llama-3.2-11b-vision` and the DSH task made five tool calls. Because the actual root model differed from the corrected run, this is not a controlled comparison and proves neither that the correction helped nor that it was irrelevant. BlockRun's official docs state `nvidia/*` free models require no payment, and the live catalog lists this model at $0 input/output.
- In a real isolated Noema desktop run, the selected named chain produced a structured `delegate_task` call; DSH headless edited only a scratch README, reported four file-tool calls, and returned a final event into the Noema chronology. Noema then summarized that event after one rate-limit failure and explicit retry. A separate fresh DSH process resumed the same persisted session and read back the exact file marker.
- An additional ordinary root turn initially exhausted the free pool, then succeeded on explicit retry. The worker return path is verified; free-tier availability remains intermittent and retries are part of the product's visible failure behavior.
- A request to Gemini returned HTTP 403 stating that the Google project was denied access. The gateway's broad auto route also exhausted its candidate providers. These routes are not considered verified for Noema merely because the gateway lists them.
- The FreeLLMAPI desktop API key is separate from its dashboard session token. Noema receives only an inference API key; it does not receive the dashboard token or permission to administer the FreeLLMAPI database.

## Decision

1. Use the local FreeLLMAPI OpenAI-compatible API as Noema's only model provider. The base URL must be a loopback address; reject non-local hosts before sending a credential.
2. Store the unified API key in Electron `safeStorage`-encrypted app data, never in renderer state after save, logs, SQLite, source files, or command-line arguments. Renderer IPC exposes only connection status and endpoint, never the stored key.
3. Expose only reviewed no-cost routes in the root picker: FreeLLMAPI `free-router`, Kilo's `nvidia/nemotron-3-super-120b-a12b:free` (surfaced through its catalog alias), BlockRun's zero-priced `nvidia/nemotron-3.5-lightning`, `cohere/north-mini-code`, `nvidia/llama-3.2-11b-vision`, and the curated `auto:noema-free` named chain. The BlockRun models are optional, appear only when FreeLLMAPI marks them available, and are not defaults. Do not pass arbitrary `/v1/models` entries to the picker; that endpoint has availability information but no trustworthy price metadata. The named chain remains the only route offered to the DSH worker. On first connection, select `auto:noema-free` if it is available, otherwise the first reviewed free route; preserve any explicit saved selection even while unavailable so refresh never silently changes a user's chosen model.
4. Use the OpenAI-compatible chat-completions API for Noema's root streaming and tool-call protocol. DSH's headless DeepSeek provider is pinned to the same loopback FreeLLMAPI `/v1` endpoint and `auto:noema-free` model alias. Noema persists tool dispatch, DSH task state, and result events separately from user messages; provider exhaustion keeps an event retryable rather than switching billing class.
5. Every user-visible connection state names FreeLLMAPI. Disclose that messages are saved locally but sent upstream through FreeLLMAPI. On provider error, preserve the user turn and show a recoverable error; never switch to Ollama, a paid model, or another external destination silently.
6. Treat free routing as a runtime capability, not a permanent catalog fact: a route is selectable only when it is both on Noema's allowlist and currently reported available by FreeLLMAPI. A route failure remains a failure; it does not authorize a different billing class.

## Consequences

- The user no longer needs Ollama for Noema. The existing SQLite conversation remains local, but model requests are external; the UI and docs make this explicit.
- Free provider quotas and health are upstream dependencies. The gateway may be reachable while every upstream free provider is exhausted or unavailable; a larger curated chain reduces single-provider cooldown risk but cannot guarantee availability.
- Kilo's free routes are not private by default: FreeLLMAPI records that prompts/outputs may be used for training. The root conversation discloses that third-party free-provider policies differ; the separate workspace consent continues to name Kilo specifically before background file content is sent.
- The app intentionally exposes a small verified free-model subset rather than all models in the gateway. Expanding the list requires evidence of both zero-cost routing and compatibility with the particular feature (text or tool use). A route may be usable for a single root reply but still be unsuitable for multi-turn agent work under its cooldown. The curated chain's membership is local FreeLLMAPI state; inspect it if the route is retargeted or expanded.
- The FreeLLMAPI URL and key are per-device settings. Endpoint discovery uses the installed desktop app's local port configuration where available, with the documented default as fallback.

## Reconsider when

- A currently configured route no longer has a free/no-cost guarantee, or its catalog ID/API behavior changes.
- BlockRun changes the live price or the installed FreeLLMAPI custom endpoint stops routing `nvidia/nemotron-3.5-lightning` as a no-payment free model; remove the optional picker entry without changing the default chain.
- BlockRun changes the live price or FreeLLMAPI reports either BlockRun candidate unavailable; hide/remove that optional picker entry without changing the default chain.
- FreeLLMAPI exposes a reliable authenticated cost-classification contract that can replace the app's small allowlist.
- A second provider class is explicitly authorized and its cost boundary can be enforced without silent fallback.
- A supported desktop credential storage mechanism is unavailable; in that case, do not downgrade to plaintext persistence.

## Amendment（2026-10-16）：有限恢复已提交后的流中错误

**证据：**在同一 Windows 主机、同一 `auto:noema-free` 选择下，5 次隔离根请求中 4 次完整返回，1 次在已有部分文本后以 `provider_error` 结束；成功响应头报告的实际模型都是 `custom/nvidia/llama-3.2-11b-vision`。这是小样本的运行时信号，不代表长期可用率。FreeLLMAPI 的官方流式管线文档说明：首个有效响应头发送前的上游故障会在网关内 failover；发送响应头后，错误会作为已提交的流错误返回，网关不再切换上游。[FreeLLMAPI streaming pipeline](https://github.com/tashfeenahmed/freellmapi/blob/main/docs/en/architecture/03-streaming-pipeline.md)

**决定：**Noema 仅对根对话的流式请求中明确归类为 `provider_error` 的故障自动重试一次，保持相同的用户所选模型 ID/免费链；FreeLLMAPI 自己负责链内的上游路由。`rate_limited`、鉴权失败、模型不可用、请求/网关超时、无效响应、用户中断、工具处理失败以及后台 DSH 事件均不触发这项自动重试。重新发送发生在另一个有序 attempt 中：已输出的部分文本保留并标为未完成，下一 attempt 的实际路由仍照常记录；第二次仍失败就停止并保留现有手动重试路径。模型工具调用只有完整流结束后才执行，因而中途失败不会重放已提交的外部操作。

**代价与重审：**客户端重试会把同一轮内容再次发给用户选择的 FreeLLMAPI 路由，可能被上游再次记录；Noema 不改选付费模型，也不改变用户选择的数据去向。若真实运行表明重试大多再次失败、造成明显重复内容/等待，或用户不接受重复外发，则移除此自动恢复，保留失败片段和手动重试。一次失败最多增加一次请求，不存在无限循环。

## Amendment（2026-10-17）：恢复首个响应前的上游不可用

**证据：**PR #65 的完整 Noema → root → DSH 隔离运行在根模型请求阶段收到 `provider_unavailable`，没有产生任何文本或任务。FreeLLMAPI 的本地适配器把 HTTP 502/503 映射为此错误，而把 429 单独映射为 `rate_limited`；FreeLLMAPI 官方项目中的“all models exhausted”记录也是 HTTP 429，不应把额度耗尽误当成可重试的上游暂时不可用。[FreeLLMAPI exhaustion issue](https://github.com/tashfeenahmed/freellmapi/issues/470)

**决定：**根对话对 `provider_unavailable` 仅在本 attempt 尚未输出任何可见文本时，最多自动重试一次，保持同一用户所选模型 ID/免费链。已输出文本后的 `provider_error` 仍按前一 amendment 重试一次并保留未完成 attempt。`rate_limited`、`gateway_unavailable`、超时、鉴权、模型不可用、用户中断和工具处理错误不重试；不切换模型、计费等级或服务商设置。若 `provider_unavailable` 在首段文本之后出现，保留失败片段而不重放。

**代价与重审：**重试会把相同的用户上下文再次发送给同一 FreeLLMAPI 路由，增加一次免费额度消耗和一次第三方传输；必须在隔离测试中验证“空失败可重试、部分文本不重放、429 不重试、最多一次”。若真实运行显示 502/503 通常代表整条链已耗尽、重试不带来恢复，则撤销此分支。
