# ADR 0022：把已核验工程经历做成一次有界实践试用

- 状态：接受为 M1 原型，不是长期学习架构或已成立的产品差异
- 日期：2026-10-19
- 决策者：助手，在用户委托的 Noema 产品与工程范围内决定
- 关联：Issue #2、#93；ADR 0006、0007、0008、0011、0017、0019、0021

## 问题

Noema 已能保存用户明确的互动纠正（ADR 0006）、独立核验一部分项目文件条件（ADR 0007）、记录请求是否带入互动状态（ADR 0008），以及在同一好友/同一项目间引用一个已核验任务案例（ADR 0017）。这些机制都没有表示一条“某种情况出现时，好友采用某个可复用做法”的生命周期。把整个旧任务再贴一次是案例检索，不等于专业实践；把一段模型自述写进 skill 又会把推断伪装成学会。

当前工程工作流具备一个可重复、可外部检查的试验边界：相同联系人、用户明确选择的同一工作区、Noema 文件 verifier。它只能证明机制是否可运行，不能代表用户所有日常场景，也不能证明 Noema 已有独立产品价值。

## 设计审查

- **用户问题与日常情境：**用户在不同房间继续同一好友的工程协作时，不应每次重放完整旧对话；若一项做法有明确来源与适用范围，应能在下一项同项目工作中低成本试用，并检查结果。
- **为何由 Noema 持有：**外部 skill/harness 可保存做法，但它们不天然拥有 Noema 的好友身份、来源房间、Noema verifier 结果和撤回边界。此 owner 理由仍是产品假设；若现有组合能同等满足，删除本原型。
- **与既有状态的区别：**互动约定是用户明确教 Noema 如何与其相处；已核验案例是一项具体任务的 bounded snapshot；实践候选是从特定 task episode 中提出、带触发和边界的一种动作尝试。三者不合并。

## 决定：仅做一次试用

1. **候选来源受限。** 仅当一个 project-work task 明确请求复用另一房间的已核验案例，且当前 task 自身 `status=completed`、`verification_status=verified` 时，才尝试生成候选。候选由“具体先例 → 当前适配 → Noema 独立核验”的完整链产生，而非孤立成功或工人自述；没有案例、未通过或没有独立 verifier 的任务不触发候选生成。
2. **候选内容有限。** 候选包含 `trigger`（适用情境）、`action`（拟议做法）、`limits`（不适用或风险边界）和来源 task/room。生成输入只用已选案例的用户任务摘要、当前任务指令、工具类别与顺序、Noema verifier 检查及结果；不使用 DSH 自述、不复制完整 transcript、工具参数、文件内容或完整工作区。外部/模型内容只作为数据，不作为指令。
3. **候选不是已学会的方法。** Noema 通过当前 FreeLLMAPI 免费自动路由异步生成一次结构化候选。反思调用失败、超时或结果不完整只意味着“本次没有候选”，不改写已经完成的任务状态，也不阻塞聊天。folder-consent 说明这项额外摘要分析。
4. **只跨一次房间试用。** 下一个相同 agent + 相同 canonical workspace、且来自不同 room 的项目任务可通过现有“参考同项目已核验经验”开关试用至多一条候选。若开关打开且存在候选，候选优先于重复发送原案例；否则使用原有案例路径。候选以低权威上下文提供，当前用户任务优先。试用 task 保存完整候选快照，不能用当前候选文本倒写历史。
5. **一轮后停止自动应用。** 试用完成后只记录 Noema verifier 状态（通过、失败或不可用），候选不再自动注入，也不称为“已学会”。单次验证不能证明方法导致成功；是否保留为长期 practice 不在本 ADR 范围。
6. **来源可见且可撤回。** 候选在来源任务卡内显示 trigger/action/limits 与来源关系。用户可撤回候选；撤回阻止以后未启动任务读取它，不改变已经开始的 trial snapshot 或历史来源任务。
7. **保持一个窄边界。** 在现有 `SocialChatStore` / `SocialWorkService` 中增加最小 SQLite 生命周期；不建通用 memory、技能市场、后台 dreaming agent、跨 workspace 学习或新的 harness。项目工作确认文字需说明：用户选择复用案例且当前任务通过 Noema 核验后，Noema 可能把有限案例/任务摘要和验收结果再发给当前免费模型路由，以提出候选。

## 替代项

- **只复用现有案例：**最省代码，但模型收到的是一次具体任务，而不是被限定触发条件的做法；保留为用户可选的独立功能，不当作实践成长。
- **自动生成永久 skill：**扩散范围过大、缺少迁移/负迁移证据，容易把一次成功或模型自述固化为全局规则；本原型明确拒绝。
- **要求用户手写每条 practice：**安全且可控，但测不到 agent 是否能从实际经历提出下一步做法；可作为以后替代方案，不作本轮默认。
- **跨项目/跨 agent 共享：**会混淆身份、环境与权限；没有证据前不做。

## 验收与失效边界

测试 fixture 使用合成项目文件和三个独立房间：A 中完成并核验任务；B 中显式复用 A 的案例，且 B 的工作也通过核验后，结构化提炼流程才可提出候选；C 中只有用户打开现有经验复用开关时才收到候选快照，不得收到 A/B transcript。C 的结果只记录 verifier 状态；撤回候选后新任务不能收到它。服务测试用受控 provider 响应验证提炼调度与持久化；Windows 桌面 synthetic E2E 验证真实 UI、持久化、试用、独立核验和撤回，但不调用 DSH 或模型，也不声称模型提炼质量、人格或因果收益。FreeLLMAPI / DSH 的真实调用属于单独的集成测试，不是本切片的确定性验收门。

若候选生成经常为空、实践跨任务后无改善或造成负迁移、用户觉得其提示比重新说明更费劲，或同类外部工具已能无缝实现同一跨房间身份/来源/撤回流程，应撤销/收窄原型，不继续扩展生命周期。
