# BEHAVIOR

本文件描述用户可观察的行为标准。当前实现与目标不一致时，以 [STATUS](STATUS.md) 标注的实际状态为准；不能把目标行为说成已完成。

## 主界面

- 启动后默认是一个 Noema 对话窗口；成员、专家、群聊、项目、归档不常驻侧栏，需要时展开。
- Noema 是唯一对结果负责的实体。执行者不是隐藏后台，它有可见的常驻私聊；专家、群聊、项目按需出现，都不能变成第二个人格。
- 输入框支持文本和附件；发送后显示流式回复，工具执行显示为同一条回复里的轨迹行，而不是独立任务卡或诊断窗口。

## 普通回答

- 不需要执行的问题直接回答，不创建工单，不显示假的执行轨迹。
- 不确定时明确说不确定；不能把推测写成事实。
- 用户要求写文件、改代码或运行命令时，Noema 不直接执行；它创建工单，交给承接人，并说明当前是“已派发”“执行中”还是“未开始”。
- 模型声称“已完成”不等于验收通过。最终答复必须按事实说明：完成、未验证或失败。

## 执行者会话

- 执行者有可见的常驻私聊空间；用户可以直接打开、查看和对话，不需要通过 Noema 转述。
- 它不是群聊，也不是临时工单群；用户与 Noema 的派发、状态和结果都汇入同一条时间线，用户能看到完整上下文。
- 执行者默认回复；用户 `@Noema` 时由 Noema 回应。Noema 派发的任务及其状态更新在同一时间线内可见。
- 执行者不对用户承担最终责任；涉及验收、方向和冲突的结论回到 Noema。

当前 0.7.1 仍把执行者放在后台，用户不能直接打开它的私聊；这是未完成项，不能作为验收通过。

## 会话分层

- 每个执行者只有一条常驻会话；私聊和团队空间都对接这条常驻会话，不因私聊或群聊复制出第三条。
- 团队有自己的共享上下文；它是团队共同的讨论、决定和交付记录，不替代成员的常驻会话，也不是每个成员的第三份会话。
- 项目是独立上下文：项目创建后，参与执行者从最新常驻会话分叉出项目会话；项目结束后归档，并做一次整体自我复盘，沉淀到个人能力层和一条经历记忆。
- 团队负责人同样按项目分叉：项目 fork 承载该项目的计划、决策和证据；常驻会话保留组合管理、跨项目优先级和团队标准。项目结束后归档项目 fork，只把验收后的经历/摘要回写常驻会话。
- Noema 只有自己的常驻会话，不分叉，不加入团队或项目；它只与团队、项目对接。
- 用户始终只看到一条当前线；项目归档可读，不把分支树或第三份会话暴露给用户。

## 岗位、团队与项目

- Noema 维护岗位库；一个现实岗位对应一个长期 Agent，不按单次任务临时造岗，也不为同一岗位按人数复制 Agent。
- Agent 创建时是岗位通用型；领域精通靠长期经历、技能和工具积累。个人与团队共用一条常驻会话，只有项目创建独立 fork。
- 复杂需求先由 Noema 从岗位库产生/指派团队负责人；负责人先于团队存在，不从团队内部选举。
- 负责人分析需求、提出团队配置和招聘，Noema 批准后组建团队；团队按能力/部门命名，长期保留，不设项目专属团队，不外包。
- Noema 不直接创建项目；负责人/团队与 Noema 对齐后建立临时项目；项目负责人默认由团队负责人继承，按 D-012 只协调。
- 同一 Agent 可被多个团队复用；团队是协作/授权视图，不拥有 Agent 本体。Agent 可读成员名册，但不能直接创建 Agent。
- MVP 阶段一个团队同一时间只推进一个项目；多项目并行不进入 MVP，等核心链路可用后再评估。
- 当前 0.7.1 没有岗位库、团队负责人和临时项目模型，仍是旧 room/branch 结构；这些行为属于目标，不是已实现。

## 个体能力如何变化

- Noema 和执行者共用六模块：Core、Policy、Competence、Tool Grants、Memory、Context。角色、团队、项目是外部关系，不改变这套结构。
- 能力以“能力条目”为单位积累：适用条件、步骤、工具、失败模式、检查/证据、范围和状态；没有检查或失败模式的内容只是资料，不是可用能力。
- 项目结束先生成回写提案，不回写原始过程：项目归档保留完整轨迹、草稿、失败尝试和未验证内容；常驻 Agent 只接收验收通过的结论、能力候选、失败教训摘要和项目指针。
- 项目验收不等于常驻可用，单项目证据不等于跨任务证据。能力候选要经过检查、与无能力基线对比、影子运行和版本化后才能启用；没有证据就不进入常驻能力。
- 当前 0.7.1 没有这套能力模型，仍是提示词、工具和旧 room/branch 结构；这是未完成项，不能作为验收通过。

## 项目负责人

- 项目负责人是项目内的协调角色，不是成员岗位；项目结束后角色解除，成员保留原岗位、技能和经历。
- 默认只做计划、依赖、风险、验收和向 Noema 汇报，不直接承接工作项，不写代码、内容或文件。
- 小项目可以显式兼任一个工作项；兼任必须记录，仍按工单和证据验收，不能用负责人身份跳过验证。
- 成员向项目负责人报进度、阻塞和交付证据；Noema 不越过负责人直接指挥成员。涉及方向、范围和最终验收的判断回到 Noema。

## 消息操作

- 复制：复制该条消息的可见文本，成功后给出短暂反馈。
- 引用：把该条消息带入输入框作为引用上下文；不会自动发送。
- 重试：重新生成该条助手回复；旧的失败/中断结果不覆盖为成功。
- 代码块提供独立复制，不复制整条消息。
- 消息操作只在悬停/键盘聚焦时出现；不使用常驻大按钮。

## 编辑与回退

目标行为：

- 编辑用户消息：截断这条消息之后的对话并重新发送，不新建用户可见的平行会话。
- 编辑助手回复：允许任意一条助手回复原地修改；修改直接进入模型上下文，后面的消息保留。不会重新发送，也不要求用户理解分支。
- 分支只作为内部恢复结构；常规界面不显示分支栏，也不要求用户选择分支。
- 编辑助手回复可能让后续消息与修改后的内容不完全一致；这是用户主动改写上下文的已知代价，不做静默修正。
- 编辑用户消息或回退前，先把当前线保存为不可变存档；恢复存档时它成为新的当前线，原当前线也进入存档，界面始终只有一条线。
- 回退同时恢复工作区到对应检查点：Noema/执行者造成的改动自动回退；若检查点之后检测到用户手动改动（含外部进程），停止回退并列出冲突文件，由用户选择，不静默覆盖用户工作。
- 操作前必须确认不可逆影响；确认后不能悄悄保留旧回复造成双写或重复副作用。

当前 0.7.1：仍显示实验性的分支栏；编辑用户消息会创建分支，而不是同一对话截断重发；助手回复不可编辑。这不符合目标行为，属于已知未完成项，不能作为验收通过。

## 历史

- 历史对话可打开查看；旧对话默认只读，避免在旧上下文上意外继续。
- 目标形态不是“新对话/历史”两套入口，而是同一长期时间线中的检查点与必要分叉；旧对话仍可查看和导出。
- 标题来自对话内容，不能由模型随意改写已确认的历史。

## 工单与执行

- 派发前显示承接人、目标、工作区；承接人必须是真实可见的执行者或专业联系人，不能伪造。
- 工单执行中显示步骤、工具类别、用时和状态；输出可展开，但不把整段命令日志灌进聊天。
- 完成后回到原对话或执行者会话，给出文件路径、变更摘要、验证结果和未验证项。
- 失败/中断必须保留用户消息和已有文件，说明失败位置；不能自动重试到成功，也不能声称已修复。
- Noema 不直接写文件；执行者的工作区、权限和证据由工单约束。

## 授权与外部动作

风险分级必须落在具体工具或连接器上，不能只在提示词里写等级：

- 读取/分析（L0）不需要逐次确认，但必须在用户授权范围内。
- 起草/准备（L1）不产生外部副作用。
- 低风险外部动作（L2，如给已知联系人发送可预览内容）支持批量确认。
- 支付、公开发布、联系陌生人、法律/医疗（L3）逐次确认，并在需要时重新认证。
- 不可逆/高价值动作（L4）必须冷却期 + 二次确认。
- 持续授权必须有范围、期限和撤销入口；支付不保存密码/卡号/余额凭据，不在后台自动扣款。
- 代表用户发出的内容不能假装是用户本人；被直接询问时如实说明是 AI 协助。
- 没有对应连接器时，不显示或承诺相应授权能力。

## 错误与恢复

- 模型连接失败：显示真实错误和重试入口，不把失败写成“已完成”。
- 流式中断：保留已产生的文本/工具轨迹，标记中断，允许重试。
- 启动时发现未完成回合：将回合标记为中断，保留用户消息；不自动续跑未知副作用的命令。
- 数据库/迁移失败：阻止继续写入并显示诊断；不能静默降级到旧 schema。
- 工作区不可用：说明原因和修复入口，不伪造文件结果。

## 验收场景

1. 普通问候直接回答，无工单、无执行轨迹。
2. “创建一个文本文件”被识别为执行请求，创建工单；执行完成后原对话或执行者会话出现文件路径、回读内容和验证状态。
3. 执行失败时保留用户消息，显示失败步骤和原始错误，不声称完成。
4. 用户打开执行者私聊，能看到派发、状态和结果；`@Noema` 能切回 Noema。
5. 编辑一条用户消息后，后续内容被截断并重发；不出现平行会话、旧回答残留或重复副作用。
6. 编辑一条助手回复后，后续消息保留；下一次模型回复能引用修改后的内容，不触发重发或重复副作用。
7. 旧对话只读；切换/导出不破坏现有数据。
8. 关闭再打开应用，历史、设置和未完成状态按预期恢复。
9. 敏感动作按具体工具/连接器的授权规则确认；拒绝授权时不执行。

当前哪些场景已通过、哪些未通过，见 [STATUS](STATUS.md)。
