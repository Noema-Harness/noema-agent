# DECISIONS

Authority: 本文件是 Noema 长期决定、替代方案、理由与重新审视条件的唯一权威来源。
Update when: 做出、替代或撤销长期决定时追加。
Does not own: 产品定义与验收（见 [PRODUCT](PRODUCT.md)）；系统结构与数据边界（见 [ARCHITECTURE](ARCHITECTURE.md)）；当前版本、证据与下一步（见 [STATUS](STATUS.md)）；命令与发布步骤（见 [OPERATIONS](OPERATIONS.md)）；维护规则（见 [AGENTS](../AGENTS.md)）。

长期决定按时间追加。每条记录决定、替代方案、理由和重新审视条件；已撤销的决定不删除，追加说明替代关系。

## D-001 一个可见的 Noema，执行结构不对用户承担最终责任

- 状态：部分被 D-009 取代（执行者不再隐藏；Noema 仍是唯一最终责任方）
- 决定：Noema 是唯一对用户承担最终责任的人格；执行者、专家、群聊、项目、团队、工单不产生第二个责任主体。执行者的可见性由 D-009 更新。
- 替代：让用户直接管理多个 Agent/群聊/项目；或让 Noema 自己执行文件。
- 理由：用户的目标是完成事情，不是维护组织图。执行身份与产品身份分离，失败和权限边界才清楚。
- 重新审视：如果内部结构开始要求用户理解分支、成员或工单才能正常使用，说明抽象泄漏，应简化而不是增加 UI。

## D-002 编辑分两种：用户消息截断重发，助手回复原地改上下文

- 状态：采用，实现待完成
- 决定：编辑用户消息时，截断该消息之后的对话并重新发送；编辑助手回复时，允许任意一条助手回复原地修改，修改直接进入模型上下文，后面的消息保留。两者都不新建用户可见的平行会话；分支只作为内部恢复结构，不常驻 UI。
- 替代：所有编辑都新建分支；把分支选择变成用户必须理解的常规操作；只允许编辑最后一条助手回复。
- 理由：用户明确选择 Google AI Studio 式的助手回复编辑；助手回复是模型上下文的一部分，改它等于改上下文，不是重发。用户消息编辑保持发送语义，避免旧消息改写已发生的证据。保留后续消息是用户明确选择，即使它们可能与修改后的回复不完全一致，系统不静默修正历史。
- 重新审视：如果保留后续消息在实际使用中造成不可解释的矛盾，再讨论是否在编辑点截断；不能默认恢复分支栏。

## D-003 连续时间线用 SQLite 检查点，不用可变聊天记录

- 状态：采用，Phase 1 基础已实现
- 决定：每个完成的回合形成不可变检查点；对话头、分支和检查点存 SQLite（schema 37 的 `conversation_branches`/`conversation_turns`/`conversation_active_branch`）；消息正文保留在 `social_messages`。
- 替代：直接改写/删除消息；或只用 JSON 文件保存会话。
- 理由：需要可恢复、可审计、可 CAS 切换的连续状态；直接改写无法区分“修正”和“篡改”。
- 重新审视：如果 schema 迁移无法可靠回滚，或跨设备同步需要事件日志，再评估追加式事件存储。

## D-004 DSH 是首选执行内核，但不是产品身份

- 状态：采用
- 决定：表单执行优先 DSH headless；native 执行器作为回退。产品对象、工单、工作区和证据属于 Noema，不随执行内核改变。
- 替代：把 DSH 直接嵌入产品核心；或只维护自研执行器。
- 理由：执行内核可以替换，产品责任不能外包。打包/分发和模型兼容问题应留在适配层。
- 重新审视：如果 DSH 成为不可替代的协议/生态依赖，需重新评估分发、许可和故障边界。

## D-005 Windows 先支持，本地优先，当前不承诺云

- 状态：云部分被 D-009 取代（当前只做本地；未来云/多设备是单独决定）
- 决定：当前正式支持 Windows；macOS/Linux 后续。数据在本机；当前只做本地，不承诺云。未来云/多设备是单独决定。
- 替代：一开始做跨平台云服务；或永久只做本地单机。
- 理由：本地优先符合数据主权和当前工程能力；云端不是当前承诺，未来若做也必须是用户自己的运行位置，不是 Noema 的托管业务。
- 重新审视：跨设备同步/云部署进入实现阶段时，必须重新定义数据迁移、密钥和离线行为。

## D-006 功能核心，关系表面

- 状态：采用
- 决定：不做情感陪伴、虚拟恋人、独立社会人格；关系来自可靠记忆、判断、交付和承认不确定。
- 替代：用拟人化、情绪价值或依赖设计提高留存。
- 理由：制造依赖与“用户仍是生活作者”的第一原则冲突；也会让产品责任和事实边界变得模糊。
- 重新审视：不得以增长指标为由推翻；如引入表达风格，只能增强清楚和可靠，不能伪装情感。

## D-007 文档固定为八份仓库文档加一份用户约定

- 状态：已被 D-015 取代（2026-11-13）；原八份文档不再有效
- 决定：仓库只保留项目 AGENTS、README 和六份 `docs/` 文档；用户级约定在 `C:\Users\NUC\.dsh\AGENTS.md`。不再新增 ROADMAP、INDEX、架构历史、ADR 树或永久 OpenSpec 规格。
- 替代：继续按主题增加文档、阶段总结和索引。
- 理由：文档失效的根因是缺少所有权和清理，不是数量不足；固定入口、单一职责、过期即改，才能保持可读。
- 重新审视：只有当现有八份无法回答一类长期问题时才增加文件，并必须同时删除/合并旧内容。

## D-008 代表用户行动使用分级授权

- 状态：采用
- 决定：L0 读取、L1 起草、L2 低风险批量确认、L3 逐次确认+重新认证、L4 冷却期+二次确认；支付不保存凭据、不后台自动扣款；公开社交优先平台 API。
- 替代：默认全自动；或所有动作都逐次确认导致不可用。
- 理由：风险与可逆性不同，授权粒度必须不同；用户必须能撤销持续授权。
- 边界：等级必须落在具体工具或连接器上；当前没有外部连接器，不能用提示词里的 L0–L4 代替工具级授权。
- 重新审视：真实外部动作上线前，需用审计记录和失败案例校准分级。

## D-009 一个账号；执行者可见；项目是任务容器

- 状态：部分被 D-013 取代（项目改为临时输出；其余仍有效）
- 决定：
  - 产品按一个账号服务，不要求账号只对应一个自然人，也不做家庭共享身份。
  - 执行者不再隐藏：用户可以直接打开它的常驻私聊并对话；它不是群聊、不是临时工单群，也不对用户承担最终责任。
  - 执行者默认回复；用户 `@Noema` 时由 Noema 回应。用户与 Noema 的派发、状态和结果汇入同一条时间线，用户能看到完整上下文。
  - 专业联系人默认收起、按需可见；群聊、项目和团队按需可见、可操作，不常驻侧栏。
  - 项目是任务容器；其长期/临时属性由 D-013 规定（当前为临时复杂输出）。创建时绑定工作文件夹并形成对应群组，可以只有一个执行者。普通任务交给已有执行者或团队，不自动升级成项目。
  - 当前只做本地：桌面是主端，手机是桌面的远程界面；数据和执行留在电脑上，手机不建立独立数据库；不承诺云。
  - Noema 仍是唯一对用户承担最终责任、拥有长期记忆和判断的实体。
- 替代：继续隐藏执行者，只让用户面对 Noema；或把执行者、专家、项目都做成常驻组织架构。
- 理由：用户需要知道谁在做、做到哪一步，也需要直接沟通；但产品责任不能分散给多个“人格”。可见执行与单一责任主体可以同时成立。
- 重新审视：如果执行者私聊开始要求用户维护成员、工单或分支才能使用，说明抽象泄漏，应简化交互而不是增加组织 UI。

## D-010 回退采用单 HEAD + 不可变存档，工作区冲突即停止

- 状态：部分实现（2026-11-13）。对话单 HEAD、不可变存档、恢复为新 HEAD 已交付；工作区文件回滚待执行者工作区阶段。
- 决定：当前线始终唯一；编辑/回退前的旧线进入不可变存档；恢复存档时它成为新的 HEAD，原 HEAD 也进入存档。回退同时恢复工作区到对应检查点；Noema/执行者造成的改动自动回退，检查点后检测到用户手动改动（含外部进程）时停止并列出冲突文件，由用户选择，不静默覆盖。
- 替代：每次编辑新建用户可见分支；静默强制覆盖工作区；只回退消息不回退文件。
- 理由：沿用 Git reflog、编辑器本地历史等成熟模式，用户只面对一条线；存档保留可读/可恢复能力，不把分支概念暴露给用户。
- 重新审视：如果逐检查点快照成本过高，改为差异/快照分层存储，不改变“单 HEAD、不可变存档、冲突即停止”的语义。

## D-011 执行者单常驻会话 + 项目 fork；Noema 不加入

- 状态：采用，实现待完成
- 决定：每个执行者只有一条常驻会话；私聊和团队空间都对接它。团队有共享上下文/记录，但不是每个成员的第三份会话。项目创建后，所有参与执行者（含团队负责人）从最新常驻会话分叉出项目会话；项目结束归档项目会话，做一次整体自我复盘，沉淀到个人能力层和一条经历记忆。团队负责人保留常驻会话做组合管理，不在常驻会话里承载单个项目的完整上下文。Noema 只有常驻会话，不分叉，不加入团队或项目，只与它们对接。
- 替代：每个团队/项目为每个成员创建独立会话；负责人不分叉、所有项目共用常驻会话；Noema 加入团队或项目。
- 理由：项目需要独立上下文，但也不该切断执行者的长期连续性；负责人同样需要项目隔离，常驻会话只保留跨项目统筹；Noema 只做接口，不成为执行成员。
- 重新审视：MVP 一个团队同一时间只有一个活跃项目，负责人只需一个项目 fork；多项目并行后再评估 fork 数量、组合视图和归档回写，不退回多会话人格。

## D-012 岗位与项目角色分离；项目负责人默认纯协调

- 状态：采用，实现待完成
- 决定：Agent 的成员名和长期身份使用现实职业岗位；项目负责人、技术负责人、内容负责人等只是项目内角色，不改变岗位名、技能或成长路径。项目负责人默认只做计划、依赖、风险、验收和汇报，不直接承接工作项；小项目可显式兼任一个工作项，但必须记录为兼任，仍不能以角色替代工单、证据或验收。
- 替代：把项目负责人/技术负责人作为成员名；项目负责人默认承担主要执行；角色与岗位合并。
- 理由：岗位决定长期能力和成长，项目角色只描述本次责任；混在一起会让成员一创建就被抽象身份限制，也会让负责人变成全能执行者。
- 重新审视：小项目没有独立协调者时，可由成员兼任项目负责人；兼任是角色，不是改名。

## D-013 岗位库、团队与项目：一个岗位一个长期 Agent，负责人先于团队

- 状态：部分被 D-016/D-017 取代（2026-11-13）；保留原始理由作为历史，当前实现以 D-016/D-017 为准。
- 决定：
  - 组织隐喻：Noema 是对用户负责的公司接口和最终责任方；执行 Agent 是员工；团队是长期能力器官；项目是临时输出。用户仍是目标、取舍和最终验收的决定者。
  - 岗位库由 Noema 维护；每个现实岗位对应一个长期 Agent，不按任务临时造岗，也不为同一岗位按人数复制 Agent。岗位库是系统级基础配置（专属提示词、基础工具、行为标准），不是招聘 JD；原“不拆成 JobTemplate/AgentInstance 两层”已被 D-016 取代，模板与个体分层。
  - 同一 Agent 可被多个团队复用；团队是协作/授权视图，不拥有 Agent 本体。需要并行时使用项目 fork，不复制第二个同岗位员工。
  - Agent 创建时是岗位通用型，领域精通靠长期经历、技能和工具积累；原“基础配置的优化会改动这个 Agent 的核心”已被 D-016 取代，模板层更新不覆盖个体核心。个人与团队共用一条常驻会话，只有项目 fork。
  - 团队长期存在，按能力/部门命名（如“内容部”），不设项目专属团队；项目结束团队保留。缺岗位时招进公司，不外包；团队负责人可提出招聘，Agent 可读成员名册，但不能直接创建 Agent。
  - 复杂需求由 Noema 从现有/岗位库招募并指定团队负责人；负责人先于团队存在，不从团队选举。负责人是团队头衔而非岗位库条目，一个管理 Agent 可负责多个团队；负责人分析需求、提出成员/章程/项目，Noema 批准或附理由拒绝后按默认 A 请用户最终确认（D-017）。
  - Noema 不直接创建项目；它把需求/第一个项目交给负责人，负责人和团队对齐后建立项目。项目负责人默认由团队负责人继承，默认只协调（D-012）。
  - 当前不设 guild；岗位库由 Noema 维护，等岗位库稳定后再评估职业共同体。工具/技能按任务检索是后续实现方向，具体 RAG/清单/权限未定。
- 原始替代：按任务临时生成岗位/Agent；拆分岗位模板与 Agent 实例；先有团队再选负责人；让 Noema 直接开项目。其中“拆分岗位模板与 Agent 实例”后来由 D-016 采纳，其余仍为被否方案。
- 理由：需求驱动的岗位会造成粒度漂移；一个岗位一个长期 Agent 让岗位库成为静态基础工程，成长发生在同一个 Agent 上。负责人先于团队，避免先拼人再找责任。
- 范围：MVP 阶段一个团队同一时间只推进一个项目；多项目并行不进入 MVP，等核心链路可用后再评估。如果单岗位 Agent 成为瓶颈、工具/技能堆积不可控，或真实吞吐需要并行多个项目，再评估岗位拆分/项目负责人分身。

## D-014 个体 Agent 六模块与能力条目

- 状态：采用（2026-11-12），框架层；实现待完成；成长事务与回写细节待实现评审。
- 决定：
  - Noema 和每个执行者使用同一套六模块：Core（身份、责任、运行时契约）、Policy（判断、拒绝、升级）、Competence（能力库）、Tool Grants（工具、权限、副作用边界）、Memory（情节、语义、程序记忆）、Context（每轮工作集）。Compiler 是组装过程，不是第七个模块。
  - 六模块是职责，不是六个文件或六张表；system prompt、skill 文件、工具函数、知识库只是载体，不能替代职责划分。
  - Competence 的最小可执行单位是“能力条目”：包含适用条件、前置条件、步骤/判断、工具、失败模式、检查/证据、范围、来源和状态。没有检查或失败模式的内容只是资料，不是能力。
  - 判断规则属于 Policy；记忆条目属于 Memory；工具授权属于 Tool Grants；岗位包（JobProfile）是组织层组合，不属于个体六模块。
  - Context 是这一轮编译/检索后的工作集，不是全部六模块的打包；Core/Policy 的硬约束常驻，Competence/Tools/Memory 按任务选择并受预算限制。
  - Noema 和执行者同构不同重心：Noema 偏 Policy、编排、治理和用户关系；执行者偏 Competence、岗位/团队/项目工具和领域记忆。
  - 成长不直接改写常驻 Agent：经历先形成候选能力/规则/记忆，经证据、评估、影子运行和版本化后再启用；项目验收不等于常驻可用，单项目证据不等于跨任务证据。
- 替代：把 system prompt 当 Core；把 skill 当完整 Competence；把工具函数当 Tool Grants；把知识库当全部 Memory；把六模块全量塞进 Context；把岗位包当个体框架。
- 理由：避免模块名和实现载体混淆；让能力可执行、可验证、可回滚；让 Context 有预算和选择，而不是无限堆积。
- 范围：这是个体 Agent 的框架决定，不定义团队/项目/岗位的组织规则；组织规则见 D-011/D-012/D-013。
- 重新审视：如果真实任务中能力条目过细导致维护成本高于收益，可合并为更大的能力包，但不能取消检查、证据和版本；如果 Context 编译无法稳定选择，先退化为显式白名单，不做全量注入。

## D-016 统一 AgentRuntime、不可变核心与岗位模板分层

- 状态：采用（2026-11-13）；部分取代 D-013 的“不拆模板/实例”和“基础配置会改动核心”；实现待完成。
- 决定：
  - 所有 Agent（Noema、执行者、专业联系人、管理 Agent）都是同一个 `AgentRuntime` 的实例。角色差异只体现在岗位模板、工具授权、记忆范围、工作区、运行时和问责关系，不建立并列的 Agent 子类。
  - 每个 Agent 有独立完整的个体环境：私有会话/上下文、记忆命名空间、Agent Home、工作区绑定、工具授权、追加式事件日志、生命周期。跨 Agent 只通过消息、任务和证据协作；调用链是事件日志的投影，不是核心结构。
  - 不可变核心包括：稳定 `agentId` 与生命周期、私有个体环境、授权边界、事件日志、运行时适配契约、证据/来源、模板来源和版本。核心只能显式 schema 迁移，不能被岗位模板或框架静默改写。
  - 分层：不可变核心 → 岗位模板层（岗位提示词、默认工具/技能、评估、UI 元数据）→ 个体层（记忆、会话、工作区、用户覆盖）。官方模板更新只作用于模板层；个体身份、会话、记忆和工作区不回退、不被覆盖。
  - 招募不是克隆：个体保留模板来源/版本和自身连续历史；模板优化继续到达已招募个体，但以模板层更新呈现，不替换个体。
  - 核心不导入岗位库、团队、项目、六模块或 renderer；大框架组合核心，反向依赖禁止。
- 替代：每类 Agent 一套类；每次招募复制模板；所有 Agent 共用一个提示词/会话；把岗位库、团队、项目直接写进核心。
- 理由：用户要求个体框架下可解释、与未来大框架解耦；模板可持续优化，个体可积累和问责，二者不互相覆盖。核心边界稳定后，团队/项目/六模块可以逐步叠加而不反复迁移个体。
- 范围：只定义 Agent 个体的核心与分层，不定义团队/项目审批、岗位库运营或六模块实现。团队/项目见 D-011/D-012/D-017；六模块见 D-014。
- 重新审视：如果真实任务证明“个体层覆盖”仍无法隔离模板更新，或核心边界导致团队/项目必须侵入个体，先修分层和迁移，不把业务逻辑塞回核心。

  - 规划只允许存在一处：GitHub Project 看板。能力清单（编号、名称、可观察结果、验收方式）、排序、阶段、状态、版本全部在卡片上；`docs/PRODUCT.md` 不再有「V1 能力清单」，只写产品定义与可观察行为。
  - 常驻文档库（5 份 docs）的改动应当是工程硬需：机制、边界、命令、已发生的行为变化。规划这种高频变化的内容不进常驻文档，否则每次规划调整都要改文档，时间一长必然两份计划打架或文档过期。
  - 执行惯例由 OpenSpec 承担：一轮怎么走写在 `openspec/changes/<name>/` 的 proposal/design/tasks 里，本轮的连接方式写在 `AGENTS.md` 的循环与五道门里，不新增常驻文档。
  - 门槛跟着收窄：`docs:check` 发现 PRODUCT 出现能力清单即失败；`plan:check` 只要求 proposal 有 `Plan: <卡片链接>`，不再校验能力编号（编号只在看板）。
- 替代：把能力清单留在 PRODUCT 并只删状态列（2026-11-15 被用户否定：规划一变就要改文档，且规划只在看板一处才成立）；给能力清单单独建一份常驻文档（多一份高频维护项）；把规划写进 OpenSpec specs（specs 是可观察行为的回归合同，不是路线图）。
- 理由：用户原话是“如果未来整个规划结构有变，改的只是 github…不要注入越来越多的维护项，尤其是把规划这种可变性很强的内容也放进常驻文档”。判据是维护成本归属：变一次只该改一处。
- 范围：规划载体与门槛校验；不改产品行为。
- 重新审视：若看板无法承载验收口径（例如需要版本化的详细验收合同），把那部分放进 `openspec/specs/` 的可观察行为，而不是回到 PRODUCT 建清单。

## D-024 安装包构建固定临时目录与 NuGet，不依赖机器策略

- 状态：采用（2026-11-15，用户点名“安装器经常生成失败是工程问题”后修复）；已落地。
- 决定：
  - `npm run make:desktop` 走 `apps/desktop/scripts/make.mjs`：构建时把 `TEMP`/`TMP`/`TMPDIR` 固定到 `apps/desktop/.tmp`，把 `SQUIRREL_TEMP` 固定到 `.tmp/squirrel-temp`，并把 `apps/desktop/vendor/squirrel/nuget.exe`（NuGet 6.11.1）铺进临时 vendor 目录交给 MakerSquirrel。
  - 不依赖系统的 `%TEMP%`、`%LOCALAPPDATA%\SquirrelTemp` 或 electron-winstaller 自带的 NuGet 2.8；受限进程令牌下这三处都可能不可写或自带缺陷。
  - 默认输出 `out/` 若被外部句柄锁住（无法改名 `out/Noema-win32-x64/resources/app.asar`），脚本自动改在 `.tmp/forge-out` 重建并打印提示，命令不失败；`out*` 与 `.tmp` 都是构建产物，不提交。
- 替代：继续要求“先关应用/别开编辑器再打包”（把工程问题转嫁给操作者，且无法解释 0.7.4–0.7.6 的连续失败）；升级 electron-winstaller/maker-squirrel 版本（deps 更新面更大，且 NuGet 版本仍不可控）；在 CI 里打安装包而本机不验证（本地无法复现就等于没有修）。
- 理由：根因是可定位的工程缺陷——NuGet 子进程被拒绝写 `%TEMP%`；NuGet 2.8 的 `System.IO.Packaging` 对高压缩率 part 抛 `ObjectDisposedException`（`app.asar` 必触发）；Squirrel 自建 `SquirrelTemp` 与锁文件同样受策略限制。固定输入比要求环境干净更可靠。
- 范围：打包与发布链路；不改运行时行为与用户数据。
- 重新审视：若上游 maker 修复了 NuGet 依赖与临时目录处理，可删掉 vendored NuGet 与 vendor 拷贝；若 `out/` 锁成为常态而非偶发，改为默认输出到独立目录并更新发布说明。

## D-025 安装包先按未签名发布，签名留作后续选项

- 状态：采用（2026-11-15，用户选择 **B**）；本轮落文档，发布演练归 C12。
- 决定：
  - 不购买代码签名证书；0.7.6 及后续一段时间按未签名安装包发布。
  - 安装说明必须写清：安装包放在带 Low 完整性标签的目录时，区内运行时以 Low IL 被拒绝写 `%LOCALAPPDATA%`（2026-11-15 实测根因是工作区完整性标签，不是签名或安全软件）；把安装包复制到 `%TEMP%` 等普通目录再运行，或使用 portable 目录。不签名时应用仍可用 portable 方式运行。
  - 签名是可选项：对外分发规模扩大、或用户无法接受放行步骤时，再购买证书并回到签名发布；届时同步更新构建与发布流程。
- 替代：立即购买 EV/标准代码签名证书（要支出，且证书主体信息与合规流程未定）；只发 portable 不发安装包（放弃了开始菜单/自动更新/卸载入口）；改用一个不需要写用户目录的安装位置（`Program Files` 需要管理员，`ProgramData` 需要机器级权限，都不能绕开安全软件对未签名程序的拦截）。
- 理由：构建链路已在 CI 的干净 Windows runner 上验证通过（安装、升级、卸载后数据保留）；本机 0.7.6 安装失败已定位为工作区 Low 完整性标签导致的 Low IL 写入拒绝，与签名无关。签名解决的是“可信来源”问题，需要支出与证书管理，不适合在发布口径尚未稳定时先做。
- 范围：发布与安装说明；不改构建产物内容。
- 重新审视：对外分发（非本人/协作者使用）开始、或安装失败率成为主要反馈、或渠道要求签名时。

## D-026 计划三层与 STATUS 边界：STATUS 只写事实，治理变更写 Plan: none

- 状态：采用（2026-11-15，用户第 3、7 点反馈）；本轮落地。
- 决定：
  - 计划只落在两处：**总规划**在 GitHub Project（能力卡、排序、阶段、状态、版本）；**本轮执行规划**在 `openspec/changes/<name>/`（proposal/design/tasks）。`docs/STATUS.md` 只写当前版本、已验证证据、未交付、已知限制，**不再写「下一步」**，只保留一行指针。
  - 工作流固定为「卡片切口 = change」：选卡 → 卡片 In Progress → 建 change（proposal 写 `Plan: <卡片链接>`，tasks 只拆这一刀）→ 实现与证据 → 卡片贴证据并 Done → 归档 change。不把一个阶段塞进一个 change。
  - 纯机制/文档/展示的治理变更写 `Plan: none`，不占能力卡；`plan:check` 接受该写法并给出提示，`pre-commit` 拒绝治理变更提交 `apps/desktop/src/` 的产品代码（产品行为必须有卡片与规格增量）。
  - 架构图与 README 是该三层的入口：图源、产物与 README 引用由 `figure:check` 校验，架构变化必须同步图（见本轮治理变更）。
- 替代：让 STATUS 继续写「下一步」（与看板、change 重复，三处计划迟早打架）；把治理改动也挂一张能力卡（污染产品路线图）；取消 change 只靠看板 issue（看板不能承载规格增量与验收拆分）。
- 理由：用户指出「一个 changes 也能代表下一次行动」，而 STATUS 的下一步与之重复；同时 OpenSpec 在工作流里被跳过，任务无法按卡片切口拆分。把“事实”和“计划”分到不同载体，才能各自只改一处。
- 范围：工作流、文档边界与门槛；不改产品行为。
- 重新审视：若卡片数量增长到一次交付跨多张卡（切片太碎），把同阶段多张卡合并为一个 change 并在 proposal 里列出，但仍需在卡片侧同步状态。
