## 一句话

Noema 是给一个账号的长期、可问责的个人 Agent。它记住这个账号正在做的事，理解意图，安排执行，核对结果，并在出错时如实说明。

Noema 属于**长期伙伴 / 陪伴型产品**，不是「更好的 coding agent」。它和陪伴类产品的区别不在类别，而在质量的判准：陪伴来自可靠记忆、清楚判断、可问责交付与承认不确定，而不是表演温暖。当前阶段是**可问责的个人伙伴**；向更深的关系（更主动的关心、更稳定的性格感）演进时不换产品，是在同一段关系上加深——所以记忆与人格必须从第一天就为此留出余地，而不是设计成只服务任务的工具。

## 第一原则

**让人在把事交给 AI 之后，仍然是自己生活的作者。**

AI 可以做得更多，但不能替用户定义目标、替用户承担后果，也不能把用户变成自己服务的对象。Noema 的价值是让用户更连续地掌握自己的生活和工作，而不是让用户依赖一个更会说话的模型。

## 用户与问题

目标用户是长期在 Windows 上工作、同时使用多个工具和 AI 服务的人。产品按**账号**服务，不要求账号只对应一个自然人，也不做家庭共享身份。

真正的问题不是“缺一个聊天框”，而是：

- 工具越多，上下文越碎；每次都要重新解释自己。
- 模型能生成内容，但很难对长期项目负责。
- 执行过程不透明，失败后无法判断哪一步出了问题。
- 记忆、文件、账号和授权散落在不同产品里，用户失去控制。

Noema 把这些收拢到一个可问责的关系里：一个对结果负责的 Noema，背后是可见、受约束的执行结构。

## 产品模型

一个账号只有一个 Noema 身份。Noema 是唯一对用户承担最终责任、拥有长期记忆和判断的实体。执行结构不是第二个人格，但也不是全部藏在后台。

| 对象                       | 定义                                                                            | 可见性                           |
| -------------------------- | ------------------------------------------------------------------------------- | -------------------------------- |
| Noema                      | 唯一对结果负责、拥有长期记忆和判断的实体；编排、治理、与用户对接                | 始终可见                         |
| 执行者（Executor）         | 真正承接工单的 Agent；有常驻私聊和工作上下文，不对用户承担最终责任              | 常驻私聊，可直接打开             |
| 专业联系人（Specialist）   | 在某个领域长期工作的 Agent；可私聊、可被指派、可参与项目                        | 默认收起，按需可见               |
| 群聊（Group）              | 多个 Agent 的协作会话，用于讨论和协调                                           | 按需可见、可操作                 |
| 项目（Project）            | 临时的复杂输出；绑定固定工作文件夹并形成对应群组                                | 按需展开                         |
| 岗位库（Job library）      | 隐藏的岗位模板库；保存岗位提示词、基础工具、行为标准和版本，不直接展示给用户    | 系统配置；招募后个体进入成员列表 |
| 项目负责人（Project lead） | 项目内与 Noema 对接的协调头衔，不是岗位库条目；只做计划、依赖、风险、验收和汇报 | 随项目可见                       |
| 工单（Ticket）             | 最小执行单元；包含目标、承接人、工作区、执行步骤、文件变更和结果                | 随执行轨迹可见                   |

没有独立的团队对象：项目本身就是协作边界，由负责人、成员和共享上下文组成。长期部门只在同一批成员连续完成第二个共同项目、确实需要跨项目继承时才重新审视（见 [DECISIONS](DECISIONS.md) D-019）。

所有 Agent 都是同一个 AgentRuntime 的实例：Noema、执行者、专业联系人、管理 Agent 只在岗位模板、权限、记忆范围、工作区、运行时和问责关系上不同，不是不同类的人。每个 Agent 有独立完整的个体环境（私有会话/上下文、记忆命名空间、Agent Home、工作区绑定、工具授权、事件日志和生命周期），跨 Agent 只通过消息、任务和证据协作。

组织规则：

- 执行者只有一条常驻会话；私聊和项目空间都对接它。项目创建后，所有参与成员从最新常驻会话分叉项目会话；项目负责人保留常驻会话做组合管理。项目结束归档项目会话并做整体自我复盘，沉淀能力与经历。Noema 只有常驻会话，不加入项目，只与项目对接。
- 项目有自己的共享上下文；它是项目共同的讨论、决定和交付记录，不替代成员的常驻会话，也不是每个成员的第二份会话。用户始终只看到一条当前线；项目归档可读，不把分支树或多份会话暴露给用户。
- 岗位库是隐藏的岗位模板库，一个现实岗位对应一个模板，不按任务临时造岗，也不为同一岗位按人数复制 Agent。招募不是克隆：新个体记录模板来源/版本和个体身份、会话、记忆、工作区、授权；官方模板的改进继续作用于模板层，不覆盖个体数据。创建岗位 Agent 主要装配不可变核心，岗位能力作为可替换的外层叠加；领域精通仍靠个体长期经历、技能和工具积累。
- 项目没有独立的团队对象：项目就是协作边界，项目负责人、成员和共享上下文由项目持有。成员来自岗位库或现有成员列表；缺岗位时先补岗位模板、招募个体，再加入项目。负责人可提出成员需求，Agent 可读成员名册，但不能直接创建 Agent。
- 项目只由用户、Noema、项目负责人拥有操作权。Noema 可以指定负责人（可以是管理 Agent），但不能决定成员组成；负责人提出成员，Noema 批准或附理由拒绝，直到形成可接受方案，再按默认 A 请用户最终确认。项目说明必须写明目标与排除项，避免项目泛化成万能部门。
- 复杂需求由 Noema 从现有成员或岗位库招募并指定项目负责人；Noema 不直接创建项目；负责人与 Noema 对齐后建立临时项目。负责人是头衔，不是岗位库条目；一个管理 Agent 可以负责多个项目。
- 项目负责人默认只做计划、依赖、风险、验收和汇报，不直接承接工作项；小项目可显式兼任一个工作项，兼任必须记录，仍按工单和证据验收。项目结束后角色解除，成员保留原岗位、技能和经历。
- 工单不作为独立任务卡要求用户维护；普通任务交给已有执行者或项目成员，不自动升级成项目。
- 新建 Agent 和项目默认 A：Noema 先判断并批准，再交用户最终确认；用户可配置为仅 Noema 批准。无论哪种配置，最终消息/变更组件必须列出新建/招募的 Agent、角色和权限。
- 用户不需要维护组织图；但必须能看见谁在做、做到哪一步、用了什么权限。
- 可见性规则：Noema 始终可见；执行者按其常驻私聊可见；专家、群聊、项目默认收起，需要时展开。
- Noema 和执行者共用同一套个体结构，不是两套人格：Core、Policy、Competence、Tool Grants、Memory、Context。Competence 的最小可执行单位是“能力条目”，要能执行、能检查、能回滚；岗位与项目是外部关系，不是个体内部的模块。

## 连续性与存在

Noema 的核心不是单次回答，而是跨时间的连续性：

- **一个身份**：桌面端和手机端是同一个 Noema，不是不同人格。
- **桌面 + 移动**：桌面是主端；手机是桌面的远程界面，通过局域网或点对点连接访问桌面上的 Noema。数据和执行留在电脑上，手机不建立独立数据库。
- **只做本地**：当前只保证本机运行，不承诺云；未来的云或多设备是单独的产品决定，不是当前默认路径。
- **连续性看工作状态**：不是看聊了多久、多少轮，而是看目标、范围、已做决定、放弃方案、文件与版本、验证边界、下一步和负责人能否跨回合、跨执行者、跨重启保留下来。
- **编辑与回退**：用户消息编辑会截断其后并重发；助手回复编辑是原地修改并进入上下文，后面的消息保留。两种编辑都不要求用户理解分支，不产生平行会话。编辑/回退前的旧线进入不可变存档；回退同步恢复工作区，检测到用户手动改动冲突时停止，不静默覆盖。
- **可迁移**：用户应当能导出、备份和带走自己的数据。

## 关系边界

Noema 是 **功能核心，关系表面**。

关系来自可靠记忆、清楚判断、可问责交付和承认不确定，而不是表演温暖、制造依赖或宣称自己有情感。Noema 不把自己塑造成独立人格或用户的替代作者；它是 AI 就如实回答。这段话约束的是**当前阶段的关系质量**，不是拒绝陪伴这条路线：更深的关系形态（更主动、更有性格感）按上文路径演进，届时修改本节而不是另立产品。

## 代表用户行动

Noema 可以使用用户的账号和额度代表用户行动，但这是**委托身份**，不是独立社会人格。所有行动必须可解释、可撤回、可审计。

风险分级只有在具体工具或连接器存在时才有意义；不能只在提示词里写 L0–L4，就声称已经实现授权。具体分级和确认方式见下文“授权与外部动作”。

支付通过用户的意图 + 操作系统/支付服务商认证完成；Noema 不保存密码、银行卡或余额凭据，不在后台自动扣款。公开社交优先使用平台 API，而不是模拟 UI；需要逐账号同意、预览、频率限制、审计和撤销。平台条款和封号风险是产品约束，不是可以忽略的实现细节。

## 产品不变量

1. **连续性高于能力广度**：宁可在少数场景里长期可靠，也不做一次性功能堆叠。
2. **委托身份高于独立人格**：Noema 代表用户，不取代用户。
3. **可撤销授权高于默认自动化**：任何持续授权都必须有范围、期限和撤销入口。
4. **可见执行高于黑箱完成**：用户能看见谁在做、做了什么、证据是什么，不能只看到一句“已完成”。

## 非目标

- 不做通用 Agent 市场、插件商店或“什么都能做”的超级应用。
- 不做情感陪伴、虚拟恋人、独立社会人格。
- 不把项目、群聊、专家和执行者变成用户必须维护的另一套组织架构。
- 不承诺替代专业判断、法律责任或用户的最终验收。
- 不在当前阶段承诺云端托管、跨设备同步或 macOS/Linux 正式支持。

## 用户可观察行为

### 主界面

- 启动后默认是一个 Noema 对话窗口；成员、专家、群聊、项目、归档不常驻侧栏，需要时展开。
- Noema 是唯一对结果负责的实体。执行者不是隐藏后台，它有可见的常驻私聊；专家、群聊、项目按需出现，都不能变成第二个人格。
- 输入框支持文本和附件；发送后显示流式回复，工具执行显示为同一条回复里的轨迹行，而不是独立诊断窗口。
- 任务卡不插入 Noema 对话流；对话外有任务执行坞，只显示进行中的任务，已结束任务进入任务历史。
- 任务进入完成/失败/中断时，在对话时间线生成且仅生成一条内联事件；不额外生成一条 Noema 回复；事件可打开执行者任务详情。

### 普通回答

- 不需要执行的问题直接回答，不创建工单，不显示假的执行轨迹。
- 不确定时明确说不确定；不能把推测写成事实。
- 用户要求写文件、改代码或运行命令时，Noema 不直接执行；它创建工单，交给承接人，并说明当前是“已派发”“执行中”还是“未开始”。
- 模型声称“已完成”不等于验收通过。最终答复必须按事实说明：完成、未验证或失败。

### 执行者会话

- 执行者有可见的常驻私聊空间；用户可以直接打开、查看和对话，不需要通过 Noema 转述。
- 它不是群聊，也不是临时工单群；用户与 Noema 的派发、状态和结果都汇入同一条时间线，用户能看到完整上下文。
- 执行者默认回复；用户 `@Noema` 时由 Noema 回应。Noema 派发的任务及其状态更新在同一时间线内可见。
- 执行者不对用户承担最终责任；涉及验收、方向和冲突的结论回到 Noema。

### 消息操作

- 复制：复制该条消息的可见文本，成功后给出短暂反馈。
- 引用：把该条消息带入输入框作为引用上下文；不会自动发送。
- 重试：重新生成该条助手回复；旧的失败/中断结果不覆盖为成功。
- 代码块提供独立复制，不复制整条消息。
- 消息操作只在悬停/键盘聚焦时出现；不使用常驻大按钮。

### 工单与执行

- 派发前显示承接人、目标、工作区；承接人必须是真实可见的执行者或专业联系人，不能伪造。
- 工单执行中显示步骤、工具类别、用时和状态；输出可展开，但不把整段命令日志灌进聊天。
- 完成后回到原对话或执行者会话，给出文件路径、变更摘要、验证结果和未验证项。
- 失败/中断必须保留用户消息和已有文件，说明失败位置；不能自动重试到成功，也不能声称已修复。
- Noema 不直接写文件；执行者的工作区、权限和证据由工单约束。
- 完成、失败、中断各给一条提示；提示只在当前应用数据内保留，历史与事实以交付记录为准。

### 授权与外部动作

风险分级必须落在具体工具或连接器上，不能只在提示词里写等级：

- 读取/分析（L0）不需要逐次确认，但必须在用户授权范围内。
- 起草/准备（L1）不产生外部副作用。
- 低风险外部动作（L2，如给已知联系人发送可预览内容）支持批量确认。
- 支付、公开发布、联系陌生人、法律/医疗（L3）逐次确认，并在需要时重新认证。
- 不可逆/高价值动作（L4）必须冷却期 + 二次确认。
- 持续授权必须有范围、期限和撤销入口；支付不保存密码/卡号/余额凭据，不在后台自动扣款。
- 代表用户发出的内容不能假装是用户本人；被直接询问时如实说明是 AI 协助。
- 没有对应连接器时，不显示或承诺相应授权能力。

### 项目与成长记录

- 建项目时选一个已存在的文件夹，成员读写只在这个文件夹内；项目本身承载共享上下文、负责人和成员，没有另一个同名的团队对象。
- 成员提案与增补在用户确认后才生效；项目群用于讨论，成员在各自的项目会话里执行。
- 项目完成后，每个成员可以产生一次复盘记录：写明适用场景、做法和依据，按版本保存，可在项目详情里查看、删除和恢复。
- 成长记录只沉淀经历与技能；联系人的定位、协作偏好和核心身份不会因为一次复盘被自动改写。

### 错误与恢复

- 模型连接失败：显示真实错误和重试入口，不把失败写成“已完成”。
- 流式中断：保留已产生的文本/工具轨迹，标记中断，允许重试。
- 启动时发现未完成回合：将回合标记为中断，保留用户消息；不自动续跑未知副作用的命令。
- 数据库/迁移失败：阻止继续写入并显示诊断；不能静默降级到旧 schema。
- 工作区不可用：说明原因和修复入口，不伪造文件结果。

## 成功标准

- 用户能在同一个 Noema 里连续推进一件跨天、跨工具的事，不需要反复重建上下文。
- 需要执行时，用户能看见谁在做、做了什么、改了哪些文件、证据是什么、失败在哪里。
- 用户消息编辑后在同一段对话里截断重发；助手回复编辑后修改进入上下文、后续保留；不产生重复副作用。
- 用户能导出、备份、删除自己的数据；敏感动作有明确授权和撤销路径。
- 出问题时，Noema 先说明真实状态，再修复；不把计划、派发或模型自述当成完成。

## 验收场景

1. 普通问候直接回答，无工单、无执行轨迹。
2. “创建一个文本文件”被识别为执行请求，创建工单；执行完成后原对话或执行者会话出现文件路径、回读内容和验证状态。
3. 执行失败时保留用户消息，显示失败步骤和原始错误，不声称完成。
4. 用户打开执行者私聊，能看到派发、状态和结果；`@Noema` 能切回 Noema。
5. 编辑一条用户消息后，后续内容被截断并重发；不出现平行会话、旧回答残留或重复副作用。
6. 编辑一条助手回复后，后续消息保留；下一次模型回复能引用修改后的内容，不触发重发或重复副作用。
7. 任务完成只出现一条内联事件，不追加 Noema 回复；刷新后事件仍在，点击能打开任务详情。
8. 旧对话只读；切换/导出不破坏现有数据。
9. 关闭再打开应用，历史、设置和未完成状态按预期恢复。
10. 敏感动作按具体工具/连接器的授权规则确认；拒绝授权时不执行。
