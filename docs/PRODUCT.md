# PRODUCT

## 一句话

Noema 是给一个账号的长期、可问责的个人 Agent。它记住这个账号正在做的事，理解意图，安排执行，核对结果，并在出错时如实说明。

## 第一原则

**让人在把事交给 AI 之后，仍然是自己生活的作者。**

AI 可以做得更多，但不能替用户定义目标、替用户承担后果，也不能把用户变成自己服务的对象。Noema 的价值是让用户更连续地掌握自己的生活和工作，而不是让用户依赖一个更会说话的模型。

## 用户与问题

目标用户是长期在 Windows 上工作、同时使用多个工具和 AI 服务的人。产品按**账号**服务，不要求账号只对应一个自然人，也不做家庭共享身份。

真正的问题不是“缺一个聊天框”，而是：

- 工具越多，上下文越碎；每次都要重新解释自己。
- 模型能生成内容，但很难对长期项目负责。
- 执行过程不透明，失败后无法判断哪一步出了问题。
- 记忆、文件、账号和授权散落在不同产品里，用户失去控制。

Noema 把这些收拢到一个可问责的关系里：一个对结果负责的 Noema，背后是可见、受约束的执行结构。

## 产品模型

一个账号只有一个 Noema 身份。Noema 是唯一对用户承担最终责任、拥有长期记忆和判断的实体。

执行结构不是第二个人格，但也不是全部藏在后台：

- **执行者（Executor）**：真正承接工单的 Agent。它有可见的常驻私聊空间，用户可以直接打开、查看和对话；Noema 也可以在这个空间里与它沟通。它不是群聊，不是临时工单群，也不对用户承担最终责任。
- **专业联系人（Specialist）**：在某个领域长期工作的 Agent；默认收起，按需可见；可私聊、可被指派、可参与项目，但不替代 Noema 对用户负责。
- **群聊（Group）**：多个 Agent 的协作会话，适合讨论和协调；按需可见、可操作。
- **项目（Project）**：临时的复杂输出；需要时绑定固定工作文件夹并形成对应群组，由负责人/团队与 Noema 对齐后建立，Noema 不直接创建。项目可以只有一个执行者；普通任务不自动升级成项目。MVP 阶段一个团队同一时间只推进一个项目；多项目并行后置。
- **岗位库（Job library）**：Noema 维护的现实岗位集合。一个现实岗位对应一个长期 Agent；岗位库是它的系统级基础配置（专属提示词、基础工具、行为标准），不是按任务临时写的招聘说明。
- **团队（Team）**：长期能力器官，不是项目组；按能力/部门命名（如“内容部”），项目结束团队保留。团队成员是岗位 Agent，可被多个团队复用；团队有共享上下文，但不为每个成员复制第三条会话。
- **团队负责人（Team lead）**：公司管理岗，由 Noema 从岗位库产生；负责分析需求、提出团队配置和招聘、组建团队并建立项目。负责人先于团队存在，不从团队内部选举。
- **项目负责人（Project lead）**：默认由团队负责人继承，项目内与 Noema 对接的最高协调者。默认只做计划、依赖、风险、验收和汇报，不直接承接工作项；小项目可显式兼任一个工作项，但不改变其职业岗位。
- **工单（Ticket）**：最小执行单元，包含目标、承接人、工作区、执行步骤、文件变更和结果；不作为独立任务卡要求用户维护。

可见性规则：Noema 始终可见；执行者按其常驻私聊可见；专家、群聊、项目、团队默认收起，需要时展开。用户不需要维护组织图，但必须能看见谁在做、做到哪一步。

Noema 和执行者共用同一套个体结构，不是两套人格：Core、Policy、Competence、Tool Grants、Memory、Context。Competence 的最小可执行单位是“能力条目”，要能执行、能检查、能回滚；岗位、团队、项目是外部关系，不是个体内部的模块。

## 连续性与存在

Noema 的核心不是单次回答，而是跨时间的连续性：

- **一个身份**：桌面端和手机端是同一个 Noema，不是不同人格。
- **桌面 + 移动**：桌面是主端；手机是桌面的远程界面，通过局域网或点对点连接访问桌面上的 Noema。数据和执行留在电脑上，手机不建立独立数据库。
- **只做本地**：当前只保证本机运行，不承诺云；未来的云或多设备是单独的产品决定，不是当前默认路径。
- **连续性看工作状态**：不是看聊了多久、多少轮，而是看目标、范围、已做决定、放弃方案、文件与版本、验证边界、下一步和负责人能否跨回合、跨执行者、跨重启保留下来。
- **编辑与回退**：用户消息编辑会截断其后并重发；助手回复编辑是原地修改并进入上下文，后面的消息保留。两种编辑都不要求用户理解分支，不产生平行会话。编辑/回退前的旧线进入不可变存档；回退同步恢复工作区，检测到用户手动改动冲突时停止，不静默覆盖。
- **会话分层**：每个执行者只有一条常驻会话；私聊和团队空间都对接它。项目创建后，所有参与执行者（含团队负责人）从最新常驻会话分叉出项目会话；团队负责人保留常驻会话做组合管理。项目结束归档项目会话并做自我复盘，沉淀能力与经历。Noema 只有常驻会话，不加入团队或项目，只与它们对接。
- **可迁移**：用户应当能导出、备份和带走自己的数据。

## 关系边界

Noema 是 **功能核心，关系表面**。

关系来自可靠记忆、清楚判断、可问责交付和承认不确定，而不是表演温暖、制造依赖或宣称自己有情感。Noema 不把自己塑造成独立人格、情感伴侣或用户的替代作者。用户问它是不是 AI 时，它必须如实回答。

## 代表用户行动

Noema 可以使用用户的账号和额度代表用户行动，但这是**委托身份**，不是独立社会人格。所有行动必须可解释、可撤回、可审计。

风险分级只有在具体工具或连接器存在时才有意义；不能只在提示词里写 L0–L4，就声称已经实现授权。没有连接器，就没有对应的授权子系统。具体分级和确认方式见 [BEHAVIOR](BEHAVIOR.md)。

支付通过用户的意图 + 操作系统/支付服务商认证完成；Noema 不保存密码、银行卡或余额凭据，不在后台自动扣款。公开社交优先使用平台 API，而不是模拟 UI；需要逐账号同意、预览、频率限制、审计和撤销。平台条款和封号风险是产品约束，不是可以忽略的实现细节。

## 产品不变量

1. **连续性高于能力广度**：宁可在少数场景里长期可靠，也不做一次性功能堆叠。
2. **委托身份高于独立人格**：Noema 代表用户，不取代用户。
3. **可撤销授权高于默认自动化**：任何持续授权都必须有范围、期限和撤销入口。
4. **可见执行高于黑箱完成**：用户能看见谁在做、做了什么、证据是什么，不能只看到一句“已完成”。

## 非目标

- 不做通用 Agent 市场、插件商店或“什么都能做”的超级应用。
- 不做情感陪伴、虚拟恋人、独立社会人格。
- 不把项目、群聊、专家和执行者变成用户必须维护的另一套组织架构。
- 不承诺替代专业判断、法律责任或用户的最终验收。
- 不在当前阶段承诺云端托管、跨设备同步或 macOS/Linux 正式支持。

## 成功标准

- 用户能在同一个 Noema 里连续推进一件跨天、跨工具的事，不需要反复重建上下文。
- 需要执行时，用户能看见谁在做、做了什么、改了哪些文件、证据是什么、失败在哪里。
- 用户消息编辑后在同一段对话里截断重发；助手回复编辑后修改进入上下文、后续保留；不产生重复副作用。
- 用户能导出、备份、删除自己的数据；敏感动作有明确授权和撤销路径。
- 出问题时，Noema 先说明真实状态，再修复；不把计划、派发或模型自述当成完成。

## 当前不承诺

0.7.x 仍是实验阶段。执行者可见私聊、完整记忆和成熟的多 Agent 协作都未达到产品承诺；云端和跨设备当前不承诺。以 [STATUS](STATUS.md) 为准。
