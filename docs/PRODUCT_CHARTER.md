# Noema 产品章程

状态：方向基线，不是完整产品规格。用户明确确认的方向与待验证的设计解释分开；后续功能、交互和数据方案仍开放，须通过当前 Issue 与用户共同收敛。

## 已确认的方向

- Noema 是独立的个人 agent 应用；用户希望能把它称为“我的 agent”，而不是某个外部 harness 的插件或外壳。
- 个体化、跨任务/应用的连续性与随使用变化，是它区别于普通执行型 agent 的重要追求；外部 agent 协作是可能能力，不是既定的中心路由架构。
- 设计应从真实使用情境和外部成熟实践出发；用户给出的比喻、初步构想和助手提出的机制，都不能自动升级成已确认规格。

## 当前工作假设

Noema 可能需要保留有来源的经历与可修正的长期理解，并让这些内容影响后续行为，才能呈现个体连续性。这里的对象划分、记忆机制、界面、自动化程度和外部接入次序都尚未定型；本章后续条款是设计护栏与问题框架，不是可直接照单实现的数据模型或功能列表。

## 问题的当前解释（待具体场景校准）

用户在不同 AI 应用、模型与专业 agent 之间切换时，关于“这个人是谁、持续在意什么、经历过什么、哪些工具能力已形成”的连续性分散在不同会话和 harness 中。用户自己不得不充当记忆搬运、能力连接和 agent 成长的协调层。

通用 agent 可以通过 skill 获得一种新工作流，却通常仍处在它所属应用的上下文、身份和运行周期中。Noema 要成为用户拥有的个人 agent 本身，而不是再增加一个可被替换的执行器。

## 产品愿景与设计边界

愿景是让用户可以把 Noema 介绍为“我的 agent”。“从日常对话或外部来源形成有出处的理解，并让它改变后续行为”是当前可能的实现方向之一，尚未作为产品承诺或首版流程确认。

Noema 不承诺模型具有意识或真实情感。产品上的“属于我”必须落实为持续身份、对用户的个体化理解、跨工具连续性、可见的能力变化和用户保有的控制权，而不是人格表演。

## 不应由当前文档预先决定的内容

- 某种“记忆系统”是否是核心实现，及其存储模型、压缩策略和用户可见形态。
- 哪些日常输入会被处理、自动处理到什么程度、是否周期性主动联系用户。
- Agent 社区、跨应用会话同步、任务派发或外部学习是否构成首版体验。
- 具体页面结构、视觉语言、交互模式和技术模块拆分。

这些问题应由可追溯的证据、用户场景和当前决策共同解决，而不是从本章的名词推演出来。

## 核心不是任务路由

主控/派发可以是能力，但不是产品骨架。Noema 的核心对象是一个跨会话、跨工具持续存在的个人 agent 状态：它从经历中形成可修正的理解，再影响后续交流和能力选择。执行 agent 是 Noema 可以调用或连接的专业能力之一。

## 暂行设计护栏（需随场景调整）

1. **身份归用户所有**：Noema 的用户模型和经验不能被某个模型供应商或外部 harness 私有化。
2. **经历与理解分离**：原始经历保留来源；压缩出的印象必须标记为推断，可追溯、可修订。
3. **成长要改变后续行为**：纯粹增加一篇反思文档不算成长；稳定偏好、判断依据或操作能力有可见变化才算。
4. **低风险变化可自主，高影响变化可治理**：不用逐条打断用户确认普通记忆整理；身份/长期规则/权限/外部副作用有清晰边界、记录和撤回路径。
5. **能力可替换且有来源**：外部系统接入要能说明来源、权限、状态和故障边界；接入信息源不等于授予行动权限。
6. **简洁而可扩展**：先支持真实日常循环；不因“元应用”愿景提前实现无差别连接器、通用工作流引擎或 agent 商城。

## 不是目标

- 不是 DSH 插件，也不是给单一 coding harness 做 UI 包装。
- 不是通用 coding agent 的又一个实现。
- 不是以任务看板、agent 派发或公司团队隐喻为中心的产品。
- 不是无条件自动刷取所有个人数据或自动改写自身系统。
- 不是以会话数量、记录总量、技能数量或自动化次数衡量 agent 是否“成长”。

## 如何判断是否在做对方向的工作

每项重大工作至少回答：它减少了用户哪一种实际连续性负担？它改变了 Noema 未来的什么行为？用户怎样知道这个变化来自什么经历？若判断错了，如何修正？如果删掉这项功能，Noema 是否仍能作为“我的 agent”成立？

曾提出的“日常输入 → 有出处的理解 → 后续行为变化”可作为一个待审视的候选闭环，不是已批准的首版定义。当前阶段和产品实现门槛以 `docs/PROJECT_OPERATIONS.md` 与 GitHub Project 的实时状态为准。
