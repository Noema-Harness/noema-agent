# Noema 产品章程

状态：基础 demo 阶段的愿景与约束；具体产品用途、选择理由和品牌尚未形成。用户已委托助手自主设计和推进交付。现有实现不是成熟产品，不能从它的功能清单倒推定位；助手决定、外部事实与用户明确确认分开记录。

2026-10-23 的已确认交互/职责边界集中于 [ADR 0029](decisions/0029-persistent-agents-and-project-sessions.md)：唯一连续 Noema、持久专业成员与隔离项目会话、内部协调和主聊反馈、成员自有资产及归档续接。以下愿景不否定这些已确认选择，也不把它们等同于完整规格或已交付能力。用户保有定位、审美和结果验收；离线期间继续实现的方案标为待评。

## 已确认的方向

- Noema 是独立的个人 agent 应用；用户希望能把它称为“我的 agent”，而不是某个外部 harness 的插件或外壳。
- 个体化、跨任务/应用的连续性与随使用变化是重要追求，不代表差异价值已成立。用户在 2026-10-21 重述的初步构想是：Noema 持续与用户交流，通常将较复杂的工作交给合适的 agent，必要时创建 agent 或组织协作；这些 agent 也可能在经历中发展。它是应认真探索的产品方向，不是完整规格或无条件委派规则。
- 设计应从真实使用情境和外部成熟实践出发；用户给出的比喻、初步构想和助手提出的机制，都不能自动升级成已确认规格。
- 当前更具体的交互方向采用微信/Telegram 类通信习惯，但成熟通信产品的常见布局不构成 Noema 的品牌答案。联系人、私聊和群聊是可用的交流形式，不预设为公开社交网络或专业 agent 网络。旧[好友与聊天空间讨论基线](design/persistent-agent-social-model.md)记录的是阶段性架构假设，不是必须保留的产品叙事。
- 完整前端界面需要重新设计，形成可辨识的品牌语言与审美标准；当前默认生成界面不作为视觉基准。范围和反馈门见[聊天体验重设计基线](design/chat-redesign-brief.md)。

## 当前架构实验及其边界

助手在用户授权范围内采用的当前架构假设：Noema 拥有持续 agent 身份与各自独立的聊天空间；外部模型/harness 是运行时，工具执行是可选能力。身份、房间和能力分别建模，不强制每位联系人经历专业成长或项目工作流程。首轮实现的历史取舍见 [ADR 0015](decisions/0015-agent-friends-and-conversation-rooms.md)；其中以专业好友解释所有联系人的措辞由当前边界修正。尚未发布的后续 ADR 要在取得代码后核对，不能仅凭 Issue 评论认定已合入。

这些实验只界定了当前代码的行为与实现成本，不提供已成立的产品价值。上下文隔离属于基础工程规则，记忆/提示词属于实现手段，agent 列表和转发属于通用能力；不能通过改名升格为 Noema 的定位。曾提出的“情境有边界”与“可持续校准的个人关系”两项核心体验主张均已撤回。后续方向从具体使用问题和替代方案探索，不以挖掘 demo 中的独特性为任务。

经历回忆、用户偏好适配和能力变化是不同问题，不应合并进一份泛化 memory。它们是否需要成为当前产品能力及如何实现，需由具体用途决定；不因愿景提前实现自动提炼系统，也不把既有 agent/room 切片当作产品方向的必经路径。历史材料见[社交好友设计基线](design/persistent-agent-social-model.md)、[经验成长研究](research/experience-to-practice.md)和[个人 Agent 产品版图](research/personal-agent-landscape.md)。

此前的根对话/后台 worker 结构由助手在用户授权范围内选定，遵循主对话不受任务占用、用户可中途介入等要求。它已经形成原型，但不再作为产品目标架构的默认答案；当前社交聊天与持续好友模型要求重新检视身份、上下文、群聊/私聊与任务事件的边界。旧结构是否能被吸收、替换或只作为底层执行能力，待研究后决定。

## 已取得的使用线索与待验证解释

用户以 Noema 开发为实际案例报告：AI 能承担大量执行，人仍须持续做产品、架构、测试等判断，并纠正 AI 的偏差。这是一位用户对一件复杂工作的描述；不证明所有个人任务都如此，也不把 Noema 缩成开发工具。跨应用补背景只是可能负担之一，不能替代对判断、纠偏和交付质量责任的设计。

**整体产品假设（助手提案，尚未定稿）：**Noema 是一个以持续聊天为主要入口、面向广泛个人需求的独立 agent。用户可与同一个 Noema 交流、一起理解和探索问题，也可在需要时借助工具或其他 agent 把事情推进到现实结果；它会随着真实使用逐渐适合用户。聊天关系、个人辅助、行动能力和持续个体化共同构成产品版图，任何一条机制都不等于完整定位。首版应选择能验证整体承诺的少数切片，不必同时实现所有支柱。

目前唯一具体描述较深的使用案例来自 Noema 开发：AI 已能执行工作，人仍承担产品、架构、测试和纠偏等多重判断。这支持把“共同理解、批判、执行和复核”纳入个人 agent 的能力版图，但不足以把整体产品缩成工作委托/协作者管理，也不足以证明这已是 Noema 的选用理由。普通交流、学习探索、生活事务与个人创造等范围仍需按实际用户问题进一步补足；它们是要探索的领域，不是已经确认的需求清单。

对照材料显示，项目内聚合聊天、文件与指令，以及在消息中调用 bot、允许 bot 互相回应，已是现有产品提供的能力；因此它们是可借鉴的交互惯例，不能单独成为 Noema 的卖点。Telegram 的 guest bot 只接收被调用的消息及其回复，官方 bot-to-bot 模式也依赖显式开启与聊天上下文；这不等于长期上下文、交付责任或跨任务复用已经解决。[ChatGPT Projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt) · [Claude Projects](https://support.anthropic.com/en/articles/9517075-what-are-projects) · [Telegram guest bots](https://core.telegram.org/api/bots/guest-mode) · [Telegram bot-to-bot communication](https://core.telegram.org/api/bots/bot-to-bot)。这些是局部能力与交互惯例证据，不能据此把 Noema 的整体比较轴缩为“谁更会委派”。协作者组织与结果把关只是个人 agent 版图中的一个能力支柱。

用户拥有独立个人 agent 是当前愿景，但这不自动证明 Noema 比现有应用、skill 或小工具更值得选择。

## 产品愿景与设计边界

逻辑总览见[Noema 整体核心流程图](design/noema-core-flows.md)。该图明确区分了当前运行路径、已接受但未完整交付的方向，以及尚待评审的假设；它不替代本章程的产品边界或 ADR 的长期取舍。

愿景是用户能自然地说“这是我的 Noema”。持续交流、个体化与可成长的能力需要成为可感知的使用结果；它们尚未指定联系人网络、记忆工作流或某种品牌叙事，也不声称模型具有真实意识或人类情感。

Noema 不承诺模型具有意识或真实情感。产品上的“属于我”必须落实为持续身份、对用户的个体化理解、跨工具连续性、可见的能力变化和用户保有的控制权，而不是人格表演。

## 不应由当前文档预先决定的内容

- 某种“记忆系统”是否是核心实现，及其存储模型、压缩策略和用户可见形态。
- 哪些日常输入会被处理、自动处理到什么程度、是否周期性主动联系用户。
- Agent 社区、跨应用会话同步、任务派发或外部学习是否构成首版体验。
- 具体页面结构、视觉语言、交互模式和技术模块拆分。

这些问题不必全部在首版实现，但也不必等待每个长期机制都研究完才做产品。助手可采用可逆、可运行的切片，以真实运行结果不断修正假设。

## 持续伙伴与协作机制

持续关系是用户体验中心；委派、协作与成长可能是重要实现机制，不能仅因界面不应像编排台就将其边缘化。反之，多 agent 的数量、群聊或自动命名不证明质量和个体化。Noema 不能只转发结果，把所有审查重新交给用户。

用户的“新闻观察者参与后续研究”例子支持角色可以跨任务发展，不要求每次经历都改名、扩大权限或增加永久 agent。稳定身份、当前角色、自我描述、可复用方法与实际能力须分别判断；没有匹配对象时，复用现有协作者、临时执行与长期新建都要比较。经历与成长目前按内部能力机制探索，不预设每项工作后都调用模型生成总结、向用户展示经历时间线，或将自我反思作为独立功能；需先证明后续行为确有改善且维护成本合理。具体创建、学习和身份变化机制尚未接受为生产架构。

## 暂行设计护栏（需随场景调整）

1. **身份归用户所有**：Noema 的用户模型和经验不能被某个模型供应商或外部 harness 私有化。
2. **经历与理解分离**：原始经历保留来源；压缩出的印象必须标记为推断，可追溯、可修订。
3. **成长要改变后续行为**：纯粹增加一篇反思文档不算成长；稳定偏好、判断依据或操作能力有可见变化才算。
4. **低风险变化可自主，高影响变化可治理**：不用逐条打断用户确认普通记忆整理；身份/长期规则/权限/外部副作用有清晰边界、记录和撤回路径。
5. **能力可替换且有来源**：外部系统接入要能说明来源、权限、状态和故障边界；接入信息源不等于授予行动权限。
6. **简洁而可扩展**：先支持真实日常循环；不因“元应用”愿景提前实现无差别连接器、通用工作流引擎或 agent 商城。

## 不是目标

- 不是 DSH 插件，也不是给单一 coding harness 做 UI 包装。
- 不是通用 coding agent 的又一个实现。
- 不要求用户充当 agent 团队的日常调度员；工作群和任务视图可按需要提供，不把公司组织隐喻预设为主界面。
- 不是无条件自动刷取所有个人数据或自动改写自身系统。
- 不是以会话数量、记录总量、技能数量或自动化次数衡量 agent 是否“成长”。

## 如何判断是否在做对方向的工作

每项重大工作至少回答：它减少了用户哪一种实际连续性负担？它改变了 Noema 未来的什么行为？用户怎样知道这个变化来自什么经历？若判断错了，如何修正？如果删掉这项功能，Noema 是否仍能作为“我的 agent”成立？

这些问题用于检查提案，不要求每项基础修复都证明产品差异。探索可以得出“方向尚未形成”，也可以改变或放弃现有方案。实现与验收进度仅在 GitHub Issues / Project 维护；本章程不把某个已实现切片固定为下一阶段产品答案。
