# Noema 产品章程

状态：第一轮产品方向与可迭代护栏；不是最终市场定位。用户已委托助手自主设计、选择技术和推进实现，用户主要在最终产品核验时介入。助手决定、外部事实与用户明确确认继续分开记录。

## 已确认的方向

- Noema 是独立的个人 agent 应用；用户希望能把它称为“我的 agent”，而不是某个外部 harness 的插件或外壳。
- 个体化、跨任务/应用的连续性与随使用变化，是它区别于普通执行型 agent 的重要追求；外部 agent 协作是可能能力，不是既定的中心路由架构。
- 设计应从真实使用情境和外部成熟实践出发；用户给出的比喻、初步构想和助手提出的机制，都不能自动升级成已确认规格。
- 当前更具体的交互方向是社交聊天：Noema 是核心伙伴，专业 agent 是长期、连续、可跨多个聊天空间参与工作的好友。联系人/私聊/群聊是产品交互假设，不意味着公开社交网络；经验如何跨空间演化仍未决。详见[持续型好友与聊天空间讨论基线](design/persistent-agent-social-model.md)。

## 当前工作假设

助手在用户授权范围内选择第一轮架构：Noema 是用户拥有的 agent 好友网络，而非单一“全能管家”或统一工具入口；Noema 本身是核心伙伴，专业好友围绕可累积的手艺长期存在，可以跨私聊、协作和群聊参与。外部模型/harness 是运行时，Noema 拥有 agent identity 和 room/context 边界。该决定和首个真实开发切片写在 [ADR 0015](decisions/0015-agent-friends-and-conversation-rooms.md)。

这是第一轮可逆产品假设，不是已证明的长期差异化。Dots、Muse、Spark、Jo 等已经覆盖个人主 agent、跨应用和后台任务；OpenClaw/Hermes 提供多 agent/session/memory/skills。仅提供“agent 列表”“多模型聊天”或“助手可以委派任务”不足以独立成立。Noema 的差异候选是：同一位用户拥有的专业好友能在不同 room 和可替换 runtime 中保持身份、独立上下文与可追溯的专业实践演化。若现有产品组合已能低成本做到，需调整定位。

研究显示经历回忆、用户偏好适配和专业手艺成长是不同状态，不应合并进一份泛化 memory。第一轮先实现 agent/room 的真实聊天结构，不因“自我成长”愿景提前实现未验证的自动提炼系统；专业实践如何改变是后续通过真实工作使用检验的核心架构问题。材料见[社交好友设计基线](design/persistent-agent-social-model.md)、[经验成长研究](research/experience-to-practice.md)和[个人 Agent 产品版图](research/personal-agent-landscape.md)。

此前的根对话/后台 worker 结构由助手在用户授权范围内选定，遵循主对话不受任务占用、用户可中途介入等要求。它已经形成原型，但不再作为产品目标架构的默认答案；当前社交聊天与持续好友模型要求重新检视身份、上下文、群聊/私聊与任务事件的边界。旧结构是否能被吸收、替换或只作为底层执行能力，待研究后决定。

## 问题的当前解释（待具体场景校准）

用户在不同 AI 应用、模型与专业 agent 之间切换时，关于“这个人是谁、持续在意什么、经历过什么、哪些工具能力已形成”的连续性分散在不同会话和 harness 中。用户自己不得不充当记忆搬运、能力连接和 agent 成长的协调层。

通用 agent 可以通过 skill 获得一种新工作流，却通常仍处在它所属应用的上下文、身份和运行周期中。Noema 要成为用户拥有的个人 agent 本身，而不是再增加一个可被替换的执行器。

## 产品愿景与设计边界

愿景是用户能自然地说“这是我的 Noema”和“这是我长期合作的某位 agent 好友”，并能在不同聊天空间里继续与同一身份互动。如何让好友从经历中变得更专业、更懂用户，是核心研究与产品迭代主题；不声称模型具有真实意识或人类情感。

Noema 不承诺模型具有意识或真实情感。产品上的“属于我”必须落实为持续身份、对用户的个体化理解、跨工具连续性、可见的能力变化和用户保有的控制权，而不是人格表演。

## 不应由当前文档预先决定的内容

- 某种“记忆系统”是否是核心实现，及其存储模型、压缩策略和用户可见形态。
- 哪些日常输入会被处理、自动处理到什么程度、是否周期性主动联系用户。
- Agent 社区、跨应用会话同步、任务派发或外部学习是否构成首版体验。
- 具体页面结构、视觉语言、交互模式和技术模块拆分。

这些问题不必全部在首版实现，但也不必等待每个长期机制都研究完才做产品。助手可采用可逆、可运行的切片，以真实运行结果不断修正假设。

## 核心不是任务路由

任务委派是能力之一，但不是产品骨架。产品骨架先是 Noema 与用户、专业好友、聊天空间之间的长期关系。需要执行时，agent 可使用适合的外部 runtime；Noema 仍对 agent identity、room membership 和用户侧连续性负责。

## 暂行设计护栏（需随场景调整）

1. **身份归用户所有**：Noema 的用户模型和经验不能被某个模型供应商或外部 harness 私有化。
2. **经历与理解分离**：原始经历保留来源；压缩出的印象必须标记为推断，可追溯、可修订。
3. **成长要改变后续行为**：纯粹增加一篇反思文档不算成长；稳定偏好、判断依据或操作能力有可见变化才算。
4. **低风险变化可自主，高影响变化可治理**：不用逐条打断用户确认普通记忆整理；身份/长期规则/权限/外部副作用有清晰边界、记录和撤回路径。
5. **能力可替换且有来源**：外部系统接入要能说明来源、权限、状态和故障边界；接入信息源不等于授予行动权限。
6. **简洁而可扩展**：先支持真实日常循环；不因“元应用”愿景提前实现无差别连接器、通用工作流引擎或 agent 商城。

## 不是目标

- 不是 DSH 插件，也不是给单一 coding harness 做 UI 包装。
- 不是通用 coding agent 的又一个实现。
- 不是以任务看板、agent 派发或公司团队隐喻为中心的产品。
- 不是无条件自动刷取所有个人数据或自动改写自身系统。
- 不是以会话数量、记录总量、技能数量或自动化次数衡量 agent 是否“成长”。

## 如何判断是否在做对方向的工作

每项重大工作至少回答：它减少了用户哪一种实际连续性负担？它改变了 Noema 未来的什么行为？用户怎样知道这个变化来自什么经历？若判断错了，如何修正？如果删掉这项功能，Noema 是否仍能作为“我的 agent”成立？

M1 第一条验证切片是一个 Noema 核心伙伴、至少一位专业好友、彼此独立的私聊/群聊房间以及真实模型/runtime 回复。它要检验好友身份是否比 disposable prompt/session 更自然、能否降低跨工具重复对齐成本；不证明完整产品价值，也不提前断言自动经验学习已解决。当前实施门槛和实际进度以 `docs/PROJECT_OPERATIONS.md` 与 GitHub Issue #2 / Project 实时状态为准。
