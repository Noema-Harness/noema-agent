# Noema 持续型好友与聊天空间：讨论基线

状态：用户确认的产品方向与待研究问题汇总；不是实现规格、完整领域模型或已接受 ADR。
更新：2026-10-18

## 为什么记录

近期讨论已改变 Noema 的核心交互假设。现有原型以一条 Noema 根对话和后台外部 worker 为主要结构；这只能算已实现的实验，不能再默认它就是目标产品架构。后续研究应从本文件记录的方向出发，检查其成立条件、反例和实现先例，不把旧代码或旧 ADR 中的实现边界当成产品结论。

## 用户确认的方向

### 社交聊天是主要交互语法

Noema 应更接近 QQ、微信、Telegram 等持续聊天应用，而不是以“发指令—执行—验收”为主的传统 agent 工作台。Noema 是用户特别关心的核心伙伴；专业 agent 作为用户与 Noema 共同认可、可反复联系的好友。聊天列表、私聊和群聊是产品交互假设，不意味着产品要成为公开社交网络。

用户与 Noema 的私聊，与 Noema 和某位专业好友之间的交流，不是同一个对话窗口。用户可以单独与专业好友私聊；需要三方共同推进时可进入群聊。Noema 与好友之间的原始私聊是否默认不可见、用户如何查看交办和结果，仍需定义透明度边界。

### 好友是持续的专业个体，不是单项任务实例

需要外部专业能力时，Noema 先判断现有好友中是否有人具备适合的专业实践。若没有，不应仅为这次任务临时造一个工具型 agent；Noema 应提出专业缺口，与用户讨论并确认是否邀请一位新好友。用户确认后，该好友进入长期联系人列表。

好友应围绕一门可积累判断力的专业实践诞生，而非单一自动化流程。例如“新闻观察者”不等同于“每天抓新闻并推送”：它可以做日常新闻观察、来源核查、议题追踪，并在其专业判断适用时参与项目调研。范围不能宽到退化为没有辨识度的通用助手。具体专业边界和创建流程尚未定稿。

Codex、DSH、模型、skill 等是好友可使用或替换的执行环境与能力来源，不自动等同于好友身份；外部会话被创建、恢复或替换，不应单独决定这位好友是否还是同一个持续个体。

### 同一好友跨多个聊天空间保持身份连续

用户与好友的私聊、Noema 与好友的交办、以及群聊，可以是同一位好友参与的不同聊天空间；不能因为窗口不同就默认为不同 agent。连续个体不要求单一无限 transcript，也不表示每个房间的全部内容都自动灌进其它房间。

已形成的核心判断是：**一个持续身份、多个彼此有边界的聊天/工作上下文；相关经历能改变好友的专业实践，但原始历史不因身份相同而无差别共享。**如何辨认、提炼、验证、传播这种经验，是当前最重要的未解工程问题。

例如，用户说“你经常从二手来源获取信息，以后请优先看一手来源”，其观察、纠正和理由可能构成一段有来源的专业成长经历；单独说“以后优先看一手来源”则缺少观察背景，不应轻易被当成同等强度的成长证据。该例是设计讨论，不代表已有自动记忆策略。

### Noema 负责在场与分配注意力

对于模型通常擅长、边界清楚、不会占用长时间专注的聊天任务（例如翻译一段话），Noema 可以直接回答。专业判断仍匹配某位好友的短问题（例如核查某条新闻）也可交给该好友，不因任务短就由 Noema 亲自处理。

任务是否委派，不应只看模型“会不会做”；耗时、持续研究、复杂背景或需要长时间执行，也会占用 Noema 与用户交流的注意力。Noema 的核心职责是保持对话可用，判断归属、传递必要背景、跟进并接回结果；它应像用户一样不把精力耗在可委派的长活上，但不能放弃调度责任。

“主动上报/打断用户”目前不作为核心架构前提，暂缓讨论具体行为。专业好友是否拥有受限主动性，之后可在身份、事件流和注意力边界明确后再判断。

## 当前未决研究问题

1. 一段经历如何从某个私聊、Noema 私聊或群聊中的事件，成为好友可跨场景复用的专业经验？如何证明它改变的是可迁移的专业实践，而非只记住了一个任务答案？
2. 好友如何在身份连续的同时保持上下文隔离，避免项目研究、日常新闻和私人对话彼此污染？哪些经历应被共享、以何种粒度、由谁批准或修正？
3. 技能沉淀、记忆文档、长期会话、可编辑 agent 状态、环境交互学习等现有做法各自在哪些任务中有效，实际故障和维护成本是什么？
4. Noema 的新社交聊天与持续好友模型，应如何取代或重构当前根对话/后台 worker 纵向切片；哪些代码可复用，哪些只是旧模型的沉没成本？

单次跨房间查询（如私聊里问工作群的细节）不是产品主轴，也不必自动改变好友的专业实践；但**跨房间证据的读取授权与答复披露边界是核心系统不变量**。近期 MemArena（NeurIPS 2026 Datasets & Benchmarks）在模拟多会话个人助理任务中发现，现有记忆系统经常要么取不回可回答的信息，要么把已取回但不该披露的事实说出来。详见[研究记录](../research/experience-to-practice.md)。因此，未来设计不能仅靠“共享一个好友记忆”或 prompt 要求 agent 保密来处理此事。

用户进一步提出一个边界判断：私聊中偶尔询问工作群里的某个细节，可能只是方便性功能，不应因此扩张成当前产品主轴。但这个例子暴露了更深的长期问题：同一个好友会在不同房间经历事情，哪些经历只应在原房间内可查，哪些能作为短期背景被授权带入，哪些值得改变它之后的专业做法？这些不是同一个“记忆”动作。跨房间事实查询作为产品功能可延后；经历如何被访问、使用、归因、迁移，仍是专业好友架构的核心研究问题。

## 明确不代表什么

- 不声称 agent 具有意识、真实情感或人的连续主观体验；“同一好友”是产品/系统层的身份连续性主张。
- 不等于所有聊天记录共用一个大上下文、所有 agent 共用一份记忆，或每段对话自动写入长期档案。
- 不预设“自动总结成 skill”、定期写 Markdown、dreaming、记忆衰减、主动刷信息流中的任何一种是正确答案。
- 不批准具体 UI、数据库表、agent loop、scheduler、消息可见性、通知机制或自动学习规则。
- 不把当前实现的 Noema 根聊天 + DSH 后台 worker 当作未来目标架构；它的效果应拿来比较，而不是约束重构。

## 下一步研究口径

研究重点不是罗列功能或复述项目宣传，而是追踪实际的状态流转、经验生成条件、跨会话/跨任务调用方式、失败案例、维护者修改轨迹与适用边界。将代码/文档/论文能证实的事实、社区报告的实际使用经验、Noema 的工作假设分开记录。最终需要回答：哪些机制已被成熟项目验证，哪些常见记忆/skill 模式在真实场景失效，Noema 若采用不同的经验成长模型会增加何种独特责任，以及何种更简单替代方案已足够。
