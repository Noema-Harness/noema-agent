# Noema 产品探索与完整界面重设计

当前工作与续接点见 [Issue #104](https://github.com/c3115644151/noema-agent/issues/104)。Noema 当前是基础 demo；产品的具体用途、选择理由与品牌仍需设计，不能从现有功能中倒推出答案。

## 已确认的范围

Noema 是独立的个人 agent 应用，追求与用户持续交流和个体化，也探索由 Noema 组织可持续发展的 agent 协作；具体机制尚未定稿。交互倾向微信、Telegram 类通信习惯，不做 AI 酒馆或工程编排工作台。整个界面都在重设计范围内：信息结构、操作过程、排版、色彩、图形、文案、动效与主要状态。旧界面和现有架构是可修订的原型材料。

## 分别判断、共同设计

**产品探索：**在什么具体日常情境下，用户为什么会需要 Noema？现在怎样解决，现有选择的缺口是什么，拟议体验如何改善结果或降低代价？现有代码用于判断可行性、缺口和复用/删除成本，不是定位依据。记忆、提示词策略、多 agent 和房间只是能力或实现选项；不能通过重新命名使其成为独特价值。方案可以采用成熟方法，不为追求新奇堆功能；没有成立的产品主张时，如实保留未定结论。

**界面与品牌：**在期望使用过程中，如何形成清楚、一致、有辨识度的表达？成熟通信交互可以保留惯例，视觉语言可通过构图、排版、密度、图形、材质、色彩、文案与动效的明确取舍建立。不能要求先找到独特技术机制才做设计，也不能用视觉完成度证明产品价值。需要具体设计参考和有理由的审美判断，不把助手默认模板当作方案。

两类工作需要不同证据，但属于同一个产品设计过程。产品未定时，助手应主动探索用途、缺失能力与期望体验，让这些判断约束布局、信息密度和表达；界面推演暴露出的产品缺口也应反过来修订产品方案。不能把“视觉不必等待独特功能”解释为仅做前端，也不能把“不得从 demo 倒推需求”解释为回避核心产品设计。前端同质化不自动意味着应把某项现有功能升格为核心定位。

## 当前设计任务：功能价值与个人伙伴体验

用户已肯定折面样稿的设计质量，同时判断它不适合 Noema 当前预期：复古潮流气质、大面积身份展示和偏低的信息密度，更像娱乐/情感角色展示，未支撑功能服务型个人 agent 的使用价值。该稿保留为方法实验，不再作为待认可的 Noema 界面候选。

用户明确的产品取向是功能服务与个人专属伙伴可以同时成立；命名的文艺、哲学意味是品牌线索。以下为助手判断：名字不能直接推出字体/配色，高信息密度也不能直接推出更多面板。应先判断用户需要同时掌握哪些内容、进展、成果与可介入动作；温度可以体现在理解、表达、协作节奏和长期相处中，无需由大头像或角色展示区承担。

当前检查的代码仅提供实现证据：普通聊天按房间组织模型回复，`social-chat-store.mjs` 的 `getContext` 提供近期消息与项目任务；`social-work-service.mjs` 的 `startTask` 通过选择目录启动项目文件工作。互动约定、群聊与任务结果已是可用原型材料，但这些主路径尚不能证明日常功能服务、跨日承接或个人伙伴价值已经成立。后续允许增加、删去或重组行为，不以既有房间和项目工作为产品答案。

已核实的外部反例：[Claude Cowork 官方产品说明](https://claude.com/resources/guides/claude-cowork-product-guide/product-overview)已覆盖文件/应用工作、可交付文档、长任务、计划任务和持久项目；[当前帮助说明](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)还描述聊天与工作共享入口、部分账户逐步合并为统一体验。它说明“聊天加执行”“持久项目”本身不足以成为 Noema 的区别，不证明它已满足所有个人用途。这是官方能力说明核查，未完成该产品的实机体验或长期效果测量。

## 当前产品假设：持续伙伴承担更多判断与交付责任

状态：2026-10-21 根据用户实际案例修订的助手提案；不是已实现、已验证优势或用户确认的完整路线。上一版以研究/创作人群和文章修改为首轮中心，缺少真实使用依据，也未充分处理用户原先的协作与成长构想；撤回该优先级。保留“共同形成判断、方向变化后实际更新工作”的有效部分，写作可作为其他情境之一。

### 这次实际知道了什么

用户在 Noema 开发中，除了执行还承担产品、架构、测试和持续纠偏，认为这种负担很重。他希望 AI 能主动补齐判断、质疑想法、探索方案，在重要选择时给出有价值的材料。该案例不等于目标人群研究，也不证明“AI 让所有人的思考量增加”；它足以否定把问题仅理解为补背景、找最新版成果的窄范围。

用户重述的初步构想是：核心 Noema 保持持续对话，较复杂工作通常委派；合适 agent 可以复用，缺少时可以创建，复杂事情可以协作。agent 会有跨事项经历，并可能重新理解自己的角色、方法和名字。这里描述的是可能的产品结构，不是全部功能、固定创建政策或每次结束自动改名的要求。普通聊天、单人处理和日常生活需求仍需完整成立。

**助手推荐的检验主张：Noema 既持续与你交流，也主动承担受托事情中的方案判断、组织与质量把关；协作经验应让之后的工作更合适，而不让你越来越忙于管理 AI。** 它是待证明的用户结果，不声称技术独有，也不承诺消除人类判断。

### 需要补足的产品职责

| 职责 | 应发生的行为 | 不能拿来替代它的东西 |
| --- | --- | --- |
| 理解与判断 | 分清目的、例子、限制与未定内容；质疑影响结果的前提，带方案与依据讨论 | 把用户描述逐字编成全部规格，或每一步都让用户决定 |
| 组织与承接 | 按工作性质选择直接做、复用、临时角色或长期协作；处理依赖、改向、失败与恢复 | 多开 agent、拉群、把消息转发给用户 |
| 质量责任 | 按结果核对来源与成果；发现遗漏、冲突和失败时返工，呈现尚不能确定的部分 | 执行者自称完成；另一个模型说“通过”；用户来收拾所有输出 |
| 经历与成长 | 保留有来源的经历，形成可修订的方法判断，在后续不同情境检验 | 总结数量、改名字、自评分数或不停增加规则 |
| 长期相处 | 可闲聊、暂停、回来继续；保留用户表达与决定的空间，主动性与事情相称 | 每句话都立项，或把“懂你”只做成人设话术 |

这些职责不要求各建一个模块或各养一位 agent。用户目标含糊时可以探索，不要求先填写任务表；授权清楚、可逆且把握足够的事直接推进，需要个人取舍时带着推荐与代价请用户判断。

### 用用户的例子推演，而不照抄为规格

以下是期望行为和故障检查，不是本机运行证据，也不是固定阶段。

**一次 AI 新闻需求。** Noema 先判断用户想掌握什么、覆盖范围和时效要求；能推断的部分自行处理，不为凑流程追问。不因“新闻”二字就断定复杂、必须创建永久 agent。若适合委派，提供明确问题与必要背景；汇报前核对重要结论的原始来源、事件日期和遗漏。争议或无法核实处如实说明，不把多份摘要拼成看似完整的答案。

**一次实际失误。** 若观察者把宣传当成事实，Noema 应尽可能在交付前发现并要求修正。可以从中提出一项局部方法改进，保留原因与适用范围；不能因一次错误把所有二手报道永久禁用。后续新闻核查和不同主题研究能否避免同类问题，才提供方法有效性的证据。复盘也适用于 Noema 自己的选题、分工和把关失败。

**之后做订阅定价跟踪工具。** 先判断用户真正需要比较什么、更新频率与可承担成本，比较现成表格、现有服务和自建工具。研究与实现可分工，但不预设固定人数或公司职位。先前 agent 可担任研究角色；它能否处理地区、套餐、额度和来源差异需看证据，不能因做过新闻就推定已是定价专家。Noema 处理研究结论与实现约束的冲突，检查最终比较是否失真，避免用户亲自重新拼接各方输出。涉及实际订阅支出或对外发布时依授权另行处理。

**角色发展。** “新闻观察者”可能保持名字而扩展研究方法，也可能逐渐改变定位；第二件经历不是必须改名的证明。候选成长机制是：经历留下事实与成败证据，agent 提出对自身方法/能力边界的解释，之后的使用检验或修正它。名字与自我描述可以表达发展，但稳定身份、旧经历、已证实能力和权限不随文案自动改变。不能把这一机制直接当作已选数据库/API。

**超出开发的检查。** 例如为家人安排短途出行，同样要比较需求、时间与限制，发现矛盾并调整安排，而非默认建立“旅行公司”；一次简单问题也不需要长期 agent。普通闲聊可以没有任务或成果。这些是合成的边界情境，不是对用户生活的事实假设，需之后实际使用验证。

### 委派和成长必须接受的反证

多 agent 可能带来独立调查与并行收益，也会引入背景损失、重复工作、共识错误、延迟和费用。分工依据应是信息/工具/并行需求与质量收益，不能把“简单自己做、复杂一定拉群”写死。Noema 的责任不能因委派转移；但它也没有全知的验收能力，不确定性应暴露，不能伪造已检查。

持续 agent 相比临时角色，需要证明可复用经验带来收益。无匹配 agent 时至少比较：现有 agent 能否接任、临时角色是否足够、是否有长期发展价值。创建不一律打断用户，授权、成本和可撤销性决定介入程度；也不默认永久保存每个 worker。过时方法应能修正或退出，不能只积累。

成长至少区分经历记录、可复用方法、当前能力判断与身份表达。反思是解释或改法建议，不是改善证明；模型版本/工具改变、获得更多预算，也可能解释结果提升。应检查之后的行为及旧能力是否退化，不能只比较前后两段自我介绍。

### 对界面、架构和删减的约束

主界面仍以熟悉的持续通信为入口；用户需要掌握的是有意义的内容、当前结论及依据、可用成果、必要介入点。密度来自让相关信息同时可见和容易回到，而非小字号、角色卡或常驻监控面板。需要协作时可进入工作群和查看过程，正常交流不强制观看所有内部发言，也不隐藏重要失败。具体导航与品牌仍待设计，不从这些职责直接推出固定三栏或新的复古皮肤。

### 结构方案比较与当前建议

以同一段跨日情境比较界面结构：用户先请 Noema 关注本周 AI 新闻；几天后又要做 AI 平台定价跟踪工具，Noema 需要判断是否复用此前的研究协作者、是否召集其他人，以及如何向用户交付可靠结果。这来自用户举例，只用于检验结构，不规定任务数量、agent 数量或固定流程。

| 结构 | 这个情境里的体验 | 主要代价 |
| --- | --- | --- |
| **agent 通讯录优先**：用户先选 agent，再在私聊或群聊里安排事情 | agent 身份清楚、可以直接回访，外观接近熟悉的聊天软件 | 把“找谁做”变成用户工作，用户容易承担编排；把 agent roster 做成主导航会让普通聊天变成管理团队 |
| **Noema 单聊优先**：所有委托、协作和交付都折叠在与 Noema 的单一对话里 | 入口最简单，Noema 始终对用户负责 | 长期协作者变成看不见的后台工具，难以建立跨事项连续性；复杂工作难以介入和追溯 |
| **对话优先、工作空间按需展开**：用户始终从 Noema 对话开始；单人委托留在该对话的任务脉络中，只有真实的并行协作或跨日共同工作才展开群聊/工作空间 | 普通交流不变成项目管理；确有协作时能看到参与者、进展与成果，也可重新联系协作者 | 需要明确普通消息、委托任务、持续项目和临时协作的关系，不能把每个委托都做成新房间 |

**当前推荐第三种结构。** 它保留通信应用的直接性，同时让多 agent 协作在确有价值时成为可进入、可返回的真实空间；Noema 作为持续对话对象，对分工与最终交付负责。最强替代是第二种：若真实使用证明用户不需要识别或回访协作者，或展开工作空间带来的认知负担高于可追溯收益，就应收敛为单聊。该建议是助手的可撤回工作决策，不是用户确认，也不授权立即改生产架构。

按第三种结构，情境的生命周期是：第一次请求由 Noema 判断直接处理还是委托；若确有必要，可把新协作者作为持续身份创建，但不要求用户先在通讯录中挑人。单一协作者的委托与其产出保留在 Noema 对话的工作脉络中；多个执行方需要并行或用户需要介入时，再展开群聊/工作空间。Noema 汇总、核查并把可交付结果带回原对话。只有工作确实跨日延续或用户要求继续共同操作时，空间才持续存在；否则不为一次工作永久新增会话入口。

**经历与成长先作为内部能力机制处理。** 每次已有的任务/执行事件可以记录参与者、输入引用、产出和结果，不因此额外调用模型总结；后续委派时再按任务相关性检索这些来源。只有重复出现且有后续效果证据的方法，才值得提炼为可修订的能力；若提炼需额外推理，应在同一阶段已有的规划/复核调用中计算其 token 成本，无法合并时再评估批量或按需处理。角色身份、当前任务角色、可复用方法、能力判断和权限分开存放；单次经历不自动改名、扩权或重写提示词。界面不新增“经历线索”消息卡，除非用户确实需要据此理解或控制结果。

视觉上，推荐方案要求的重点不是 agent 卡片或任务仪表盘，而是紧凑易读的交谈、可追溯的贡献以及清楚的下一责任人。候选表达为两层而非固定三栏：高密度的会话/联系人导航与主对话构成日常界面；来源、执行细节和交付物仅在相关消息或按需详情中出现。群聊打开时参与者以紧凑文字身份呈现，不使用大头像或人格展示墙；消息流中区别“用户交流”“Noema 的判断/回报”“协作者贡献”“可操作成果”，但不把模型内部推理展示为对话。品牌气质暂定为“有分寸的工作往来”：通过可靠的文字层级、引用标记、清晰时间与克制而有辨识度的图形系统表达 Noema；不采用紫蓝渐变、堆叠卡片、常驻检查器等默认 AI 工作台语汇。视觉规则仍是候选，需在真实高密度场景中验证，再决定构图、字体、色彩与图形。

状态所有权继续由 Noema 掌握，执行 runtime 可替换，保留模块化单体。现有 agent/room/message、引用、停止/重试和任务事件可以评估复用；近期消息窗口与目录工作入口不证明长期判断和质量把关已经成立。新增长期状态、自动行为与迁移要在生产实现前作适用 ADR；本提案不改 schema、权限或共享执行代码。

优先考虑删除强迫用户选择工程模式、暴露调试细节、无意义的内部讨论、每次反思都增加永久规则等负担；不因前台不应像编排台就先删掉委派/联系人/群聊。默认服务好一人直接处理、单次委托、持续协作与普通聊天，避免为成长机制把所有需求变成长期项目。

### 已撤回的行为样稿

`agent-continuity-study.html` 已从候选中撤回。它把用户描述的 agent 经历直接做成侧栏时间线和聊天内“带入经历”卡片，却没有说明经历由谁产生、何时更新、是否需要额外模型调用、如何计入成本，也没有判断这是用户可见功能还是内部机制。用户还指出其聊天列表、主聊天、右侧信息栏的构图常规且同质。样稿确实验证了静态页面的切换与来源跳转，但不证明背后的行为成立；该原型不再作为产品或视觉方向，源文件已删除。

这次批评是对该稿及设计过程的具体反馈，不等于“经历应完全藏在内部”或其他相反方案已成立。下一轮先研究界面同质化的可观察成因，并在现有界面 Skill 中修正探索顺序；产品机制需把生命周期、触发、状态归属、模型/工具成本、纠错与用户可见性的选择分开处理。完成这一步前不围绕这条经历假设再画一张高保真界面。

### AI 界面同质化：本轮复盘

对已撤回样稿的直接检查发现：

- 构图采用窄图标栏、聊天列表、中央消息流、右侧详情栏的成熟默认拼法，却没有说明为什么这个故事需要四个并列区域；颜色与衬线字的调整没改变基本结构，因此观感仍像通用 AI 工作台。
- “经历线索”“方法状态”“带入一条经历”等标签，把尚未定义的数据生命周期做成已存在的产品对象；虚构的状态、审核清单和解释性文字让交互显得完整，却掩盖了谁生成经历、何时调用模型、成本由谁承担、用户是否需要看见这些机制都未决定。
- 我先从用户举例中挑出一种机制，再一口气做高保真、单路径样稿；随后只验证了点击和切换。交互可操作被误当成产品逻辑成立，视觉细节也提前锚定了结构。问题的核心不是用了哪种颜色，而是未经产品与状态生命周期判断便进入组件布局。

外部研究只能支持方法判断，不能给 Noema 决定品牌或功能：[Chen 等人的 GenUI 研究](https://arxiv.org/abs/2606.13843)以一家大型软件公司的 24 位产品经理和 UX 设计师做早期探索任务；宽搜方式更能挑战先入假设，但多屏方案更难预览，参与者仍偏好高保真。它支持“先打开设计空间再收敛”，不意味着低保真必然更好。另一项[生成式 AI 同质化元分析](https://www.tandfonline.com/doi/full/10.1080/0144929X.2026.2726451)汇总 19 项研究、61 个效应量，报告总体效应较小但显著，且受任务约束程度影响；它不是界面研究，不能证明具体哪种 UI 会显得 AI。

对应改动已落入 `.codex/skills/noema-interface-quality/SKILL.md`：在界面表达新机制前，先明确来源/责任、触发与更新、持久化、模型和工具成本、失败纠正及用户需要的可见性；开放式重设计或收到“同质”反馈后，先区分问题层次并比较少量结构不同的低成本构图，再进入细节稿。它是流程改进，不是固定的 Noema 版式，也不替代后续行为检验。

## 可直接改进的基础质量

已保存的数据可恢复且不串房；身份/上下文/能力边界清楚；发送、生成、停止、失败、重试状态真实且可恢复；引用有来源；键盘、焦点、缩放与窄窗可用。这些是质量底线，不是差异化卖点。具体上下文策略仍可重设，但变化必须显式且保留既有数据。

基础质量修复可依据真实缺陷独立推进；它们的检查结果不证明产品定位、自然感或品牌已经成立。真实运行检查覆盖主要、空、加载、失败及恢复状态后，才可报告视觉交付。

## 已撤回的提案

A/B 聊天皮肤原型已删除。“关系延续、情境不混合”及“用户纠正—保存约定—未来带入”均不再作为候选核心体验或待用户批准方案：前者将工程边界升格为叙事，后者将基础记忆/提示词策略重新包装，二者还被错误地放在同一比较层级。保留已有功能不等于保留这些定位主张；本次不据此删除应用数据或源码。撤回依据与后续工作在 Issue #104，旧版本仅作为 Git 历史保留。

## 已结束的视觉方法实验：交谈对象与折面图形

[可操作样稿](prototypes/conversation-study.html)、[桌面截图](prototypes/conversation-study-desktop.jpg)、[窄窗失败状态](prototypes/conversation-study-narrow.jpg)。这是设计方法实验的证据，已退出 Noema 界面候选；用户肯定设计质量，但明确指出气质、密度和角色展示倾向不适配功能服务型个人 agent。旧双栏稿仅留 Git 历史。此稿未进入生产应用，输入仅在页面内存，联系人、消息及回复全部合成。

### 为什么改变构造方法

旧稿在构图前已预设双栏导航壳子，随后以浅色侧栏、大字标、分隔线和留白修饰。删除工程控件并没有形成新的视觉组织；“文字主导”只说明消息排版，不能证明整屏具有辨识度。用户明确否定该结果，本轮不沿其壳子细化，也不先将失败归纳为永久规则。

本轮先确定视觉重心，再安排控件：当前交谈对象占据桌面左侧，聊天成为右侧连续阅读面；列表收进明确标注“聊天”的抽屉，以 Ctrl K 搜索、Alt ↑/↓ 顺序切换补充。原创折面轮廓同时用于大图形、窄窗身份标记和小尺寸应用符号；不同合成身份使用不同轮廓，不混用 Noema 标记。砖红、纸色、硬边阴影和不对称曲面共同构成这一轮的表达。只有模拟回复正在进行时才有轻微图形运动，并尊重减少动效偏好；不借此暗示 agent 情绪、意识或真实在线状态。

这是助手提出的视觉假设，不从 demo 推导独特功能，不代表用户已接受品牌。现有联系人/群聊样例只供检查状态，不构成产品数量或流程规格。此次反馈支持整套改法改善了观感；多个变量同时变化，不能据此断言收起列表、某种颜色或大图形单独造成成功。可迁移的方法是重审过早锁定的结构、让视觉选择相互支持，并分别验证审美质量与产品适配；具体风格不升格为后续模板。

### 取舍与失败条件

大图形占用约三成至四成桌面宽度，列表收起增加一次展开操作。长回复和高频跨会话使用可能更适合常驻列表、较小身份区；这仍是最强替代。窄视口去掉大图形，保留身份轮廓、色面与阅读面的转折。不能把装饰差异或可用性检查当成审美成功；若画面仍只有新鲜外观、长期使用负担明显，需重审这项构图，而非继续换颜色。

### 本轮实际验证

此前样稿曾在本机浏览器 1360×900 检查聊天切换和经历来源返回；这只验证静态模拟交互。用户随后明确否定其结构及未定义的经历机制，故已从活动候选中撤回。没有在生产应用中实现或验证该机制。修改后的 Skill 尚待下一次真实界面任务检验是否能改变起手方式。

本机浏览器实际检查 1280×720、390×844、320×640 视口；页面及聊天区域无横向溢出，长达 20 行的输入仍可滚动，发送可达。已操作：列表/信息面板的键盘焦点限制与 Escape 返回、空搜索结果、Ctrl K、Alt ↑/↓、切换后的独立草稿恢复、发送多行消息、停止后保留下一条草稿、失败重试在原会话完成、群回应者及输入身份同步。运行日志未发现错误；无重复 DOM ID；四组关键文本配色最低对比度为 4.68:1。

JS 语法、文档本地链接、JPEG 文件格式及差异空白检查另在 PR 记录。中文输入法实机、高 DPI、200% 缩放、减少动效偏好的实际切换、Electron 真应用与全应用其他页面尚未验收。样稿状态检查不能证明生产应用的草稿问题已修复；审美改善依据本轮用户反馈，产品适配仍未确认。
