# 聊天体验与完整界面重设计基线

本文件记录用户已确认方向和设计验收原则；当前范围、进度及续接点在 [Issue #104](https://github.com/c3115644151/noema-agent/issues/104)。它不是已定稿的视觉方案。

## 方向与尚未证明的部分

用户确认：Noema 是独立个人 agent 应用；借鉴微信、Telegram 等通信应用的使用惯例；不做 AI 酒馆，不以工程编排或任务看板组织日常体验。现有默认生成界面不被接受，整个前端呈现必须重新设计。信息结构、会话与联系人交互、阅读与编辑、视觉系统、文案和主要状态均在范围内，不以保留旧结构再换色作为完成。

同一 agent 身份、房间边界和可替换执行能力是当前产品机制；其能否形成值得长期使用的独特价值，仍需真实使用验证。不能用“多 agent”“有记忆”或一套新皮肤宣称品牌成立。联系人可以有专业倾向，但职业、工具和任务模板不定义身份。

## 三种不同的决定

| 类别 | 应怎样判断 | 例子 |
| --- | --- | --- |
| 可靠性与可用性底线 | 可观察、可测试；缺陷可直接修复 | 已承诺持久化的数据重启可恢复；消息不串房；状态不伪报成功；键盘焦点可见；窄窗主要操作可达 |
| 产品策略 | 明确情境、取舍、状态所有权和重审条件 | 草稿如何保存、群聊由谁回应、跨房间带入哪些理解、发送/停止/重试语义 |
| 品牌与审美假设 | 以具体内容与运行尺度比较，再获取用户反馈 | 阅读密度、色彩/字形/头像语言、动效气质、边栏与对话的视觉关系 |

“消息不丢”和“必须有云同步”不是同一个要求；“群聊清楚可控”和“所有 agent 自动同时发言”也不是同一个要求。先选简单且符合情境的产品策略，再验证其承诺。

## 首轮必须讲清楚的使用过程

用一条非编程的日常讨论作为主场景：用户与 Noema 持续聊一件事，中途切到另一位联系人，再回来继续；若邀请一位或多位联系人入群，应清楚自己在哪个空间、谁会回应，以及其他房间内容是否被带入。切换不能靠工程术语解释。该场景是审查工具，不强制用户必须建立多个联系人或群聊。

覆盖输入草稿、长消息、历史阅读、生成中、取消/失败/重试、重开应用、空联系人/空会话、长名称和较多成员。能力不可用时如实说明并允许继续正常交流。哪些行为已经存在、哪些是拟议补足，须由审计区分。

## 参考方法

通信应用用于研究导航、阅读节奏、上下文定位、输入/发送习惯与恢复；SillyTavern 只作对话和上下文机制参考。参考成熟实践不意味着照搬其视觉品牌、基础设施或功能总量。记录具体来源与观察条件，未亲自运行的界面只算文档/源码证据。

先从用户活动和 Noema 的真实机制推导视觉层级，再检查成熟设计系统与可访问性。避免把某种反默认风格、模板或罕见配色当作品牌。特色必须在实际会话内容和重复使用中成立，而不只存在于宣传空屏。

## 首次设计反馈门

在大面积实现前提供少量可比较的方向：同一真实尺度、同一合成但明确标注的日常对话，含桌面/窄窗和失败恢复示意。说明推荐方向如何表达持续身份、房间边界、阅读密度与能力入口，也说明代价。用户反馈前只是候选；不将静态预览写成真实模型行为或产品交付。

方向明确后以纵向切片落入真实应用，逐步贯通必要后端。最终检查运行中的主要、空、加载、失败、恢复状态、键盘路径、焦点、缩放、溢出和减少动效设置。测试、视觉检查与用户体验反馈分别记录；通过技术检查不能代替用户认为它好用、好看。

## 首轮可评审产物

[交互预览](prototypes/chat-directions.html)使用同一组合成日常对话比较两个候选。可直接在浏览器打开，或在该文件目录运行 `python -m http.server 4080 --bind 127.0.0.1` 后访问。它不调用模型，不读取真实用户数据，草稿仅在本次预览内存中保存；标为示意的入口没有实际功能。候选应在方向被替换时移除，避免累积无用原型。

- **A：日常通信（助手推荐）**。常驻聊天列表，清楚显示持续身份与房间；用克制的墨蓝和紧凑阅读节奏，减少多联系人切换成本。代价是占用横向空间，视觉特色仍需在真实交互中继续发展。
- **B：沉浸对话**。默认收起列表，温暖纸色与更舒展的阅读列，强调与同一个体持续交流。代价是房间定位多一次操作，也更接近长文对话应用，可能偏离用户希望的通信习惯。

本轮比较的是信息结构与阅读感，不宣称两套候选已经建立独特品牌，也不请求用户批准每个颜色或组件。后续应吸收反馈并继续打磨，而不是把其中一页原样铺满应用。
