# Noema 产品探索与完整界面重设计

当前工作与续接点见 [Issue #104](https://github.com/c3115644151/noema-agent/issues/104)。Noema 当前是基础 demo；产品的具体用途、选择理由与品牌仍需设计，不能从现有功能中倒推出答案。

## 已确认的范围

Noema 是独立的个人 agent 应用，追求与用户持续交流和个体化；外部 agent 协作是可选能力。交互倾向微信、Telegram 类通信习惯，不做 AI 酒馆或工程编排工作台。整个界面都在重设计范围内：信息结构、操作过程、排版、色彩、图形、文案、动效与主要状态。旧界面和现有架构是可修订的原型材料。

## 分开回答两类问题

**产品探索：**在什么具体日常情境下，用户为什么会需要 Noema？现在怎样解决，现有选择的缺口是什么，拟议体验如何改善结果或降低代价？现有代码用于判断可行性、缺口和复用/删除成本，不是定位依据。记忆、提示词策略、多 agent 和房间只是能力或实现选项；不能通过重新命名使其成为独特价值。方案可以采用成熟方法，不为追求新奇堆功能；没有成立的产品主张时，如实保留未定结论。

**界面与品牌：**在期望使用过程中，如何形成清楚、一致、有辨识度的表达？成熟通信交互可以保留惯例，视觉语言可通过构图、排版、密度、图形、材质、色彩、文案与动效的明确取舍建立。不能要求先找到独特技术机制才做设计，也不能用视觉完成度证明产品价值。需要具体设计参考和有理由的审美判断，不把助手默认模板当作方案。

两类工作相互约束，但不能互相替代。前端同质化不自动意味着应把某项现有功能升格为核心定位。

## 下一项方向提案应具备的依据

- 具体使用问题、发生情境、当前替代及代价；区分观察、外部资料和助手假设。
- 针对同一问题比较拟议体验与最强替代，解释用户结果的变化；工程规范、实现策略和产品价值不跨层比较。
- 可评审的使用过程或原型，以及它增加的认知/操作负担、最可能不成立的原因。
- 最后核对 demo 可复用、需新增、应删除的部分；不让沉没实现决定方向，也不默认全面重写。

方向证据不足时先完善研究或方案，不把每个现成能力包装成问题交给用户选择。用户的方向性反馈门保留，但前提检查和方案判断由助手先完成。反馈推翻前提时，撤销依赖它的提案及任务。

## 可直接改进的基础质量

已保存的数据可恢复且不串房；身份/上下文/能力边界清楚；发送、生成、停止、失败、重试状态真实且可恢复；引用有来源；键盘、焦点、缩放与窄窗可用。这些是质量底线，不是差异化卖点。具体上下文策略仍可重设，但变化必须显式且保留既有数据。

基础质量修复可依据真实缺陷独立推进；它们的检查结果不证明产品定位、自然感或品牌已经成立。真实运行检查覆盖主要、空、加载、失败及恢复状态后，才可报告视觉交付。

## 已撤回的提案

A/B 聊天皮肤原型已删除。“关系延续、情境不混合”及“用户纠正—保存约定—未来带入”均不再作为候选核心体验或待用户批准方案：前者将工程边界升格为叙事，后者将基础记忆/提示词策略重新包装，二者还被错误地放在同一比较层级。保留已有功能不等于保留这些定位主张；本次不据此删除应用数据或源码。撤回依据与后续工作在 Issue #104，旧版本仅作为 Git 历史保留。

## 当前界面研究稿：文字主导的通信界面

[可操作样稿](prototypes/conversation-study.html)、[桌面截图](prototypes/conversation-study-desktop.jpg)、[窄窗失败状态](prototypes/conversation-study-narrow.jpg)。这是主聊天画面的视觉与交互候选，不是已接受品牌或 Noema 产品定位；联系人、数量和内容都是合成样例，不规定默认联系人或房间结构。回复为定时生成的示意文字，不调用模型；输入只保留在该页面的内存里。

本轮设计判断是优先照顾阅读长回复，同时保留会话列表、输入、返回等通信习惯。会话列表用字重、分隔线和缩进组织，减少头像/徽章的视觉负担；消息按发言人/时间侧栏、正文和留白分组，agent 长回复不放入气泡；用户发言用独立缩进和浅底区分。大字标、浅黄绿索引区、深色正文与单一赭红操作色构成一个可评审的视觉判断，而不是从记忆功能推导的隐喻。

代价也明确：这比双侧气泡更偏阅读，短促来回不如传统通信界面紧凑；减少头像会降低相似姓名的快速辨认。最强替代仍是成熟的气泡布局，识别成本更低，但长 agent 回复容易形成大面积容器。此稿用于比较实际阅读感和审美取舍，不宣称哪一种布局本身更有产品价值。

参考边界：查阅了 [Telegram Desktop 输入区源码](https://github.com/telegramdesktop/tdesktop/blob/0e645b8f507d366cc4083490f3b9d631390bd52b/Telegram/SourceFiles/history/view/controls/history_view_compose_controls.cpp#L1494)，其切换历史时注册对应草稿源、读取草稿及光标并应用，作为分会话输入状态的成熟实践；[GOV.UK 字号与行高方法](https://design-system.service.gov.uk/styles/type-scale/)用于检查阅读层级与响应式节奏，不作为视觉品牌模板。外部网站的浏览器访问超时，未完成微信/Telegram/Beeper 客户端的实机操作或截图研究；上述是源码/官方资料证据，不能写成广泛竞品实机拆解。

本地浏览器实际检查了 1236px 桌面容器及 440px 窄窗：无横向溢出、输入可达；分会话草稿、生成时切换/停止后保留下一条草稿、失败重试、引用、多行输入、搜索/空会话、群回应者与信息面板焦点返回已操作检查。修复了窄窗名字拆行、信息面板背景焦点与不实暂存措辞。浏览器缩放快捷键未改变缩放，200% 未验；真实中文输入法、高 DPI、减少动效偏好和 Electron 实际应用尚未完成该方案验收。这里的草稿隔离不代表生产应用的草稿问题已修复。

打开方式：直接用浏览器打开 HTML，或在仓库根运行 `python -m http.server 4080 --bind 127.0.0.1 --directory docs/design/prototypes` 后访问 `http://127.0.0.1:4080/conversation-study.html`。样稿不依赖外部字体或服务。下一次反馈只判断这个视觉/阅读方向是否值得继续，不请求用户认可新的产品核心功能。
