# Noema 产品与界面探索基线

当前推进与续接点见 [Issue #104](https://github.com/c3115644151/noema-agent/issues/104)。本文件只保留仍有效的产品和设计边界；已撤回样稿与阶段性推理不作为当前方案，历史证据以 Git 记录为准。

## 已确认的产品边界

- Noema 是独立的聊天型个人 agent。主要交互应符合用户熟悉的通信习惯，微信、Telegram 是交互参照，不是页面模板。
- 用户希望持续与同一个核心 Noema 交流；Noema 可自行处理简单需求，必要时使用工具、复用或创建协作 agent。协作者可能随经历发展身份与方法。这是产品构想的起点，不是完整规格或既定架构。
- 功能服务与个人专属伙伴体验可以并存。产品不应变成 AI 酒馆，也不应把用户长期放进任务编排或工程工作台。
- 用户明确要求重做整个用户界面，建立有专业判断、区别于常规 AI 界面的品牌表达。已有 demo、样稿和代码只提供成本与实现线索，不构成审美或产品基准。

## 尚未解决的产品问题

Noema 的具体日常用途、用户为何选择它、首个高价值使用循环和品牌表达仍未确定。不能把“聊天型个人 agent”误当成完整价值主张，也不能把某个最近容易实现的机制——如委托、记忆、agent 成长或上下文隔离——提升为全产品答案。当前产品候选与现有替代比较见[个人 Agent 产品探索](../research/personal-agent-landscape.md)；其中的总体承诺仍是助手假设。

目前最具体的真实使用线索来自 Noema 开发过程：用户认为 AI 执行能力提高后，人仍要承担产品、架构、测试、纠偏和协调等判断负担。这证明了一个高复杂协作情境值得探索，不证明 Noema 应成为开发工具，也不代表广泛个人需求。

接下来的产品探索须并列考虑日常交流、理解和探索、计划与行动、个人创造、持续个体化，以及必要的协作者组织；这些是寻找问题的观察面，不是承诺实现的功能清单。对每个候选问题，比较用户现在如何处理、替代方式的实际效果和代价、Noema 可以改善的用户结果及其信任/运行成本。竞品有该能力不代表做得完美或 Noema 不能做；新颖也不是必要条件，但选择理由必须成立。

成熟通信产品可作为发送、回复、转发、多人交流、草稿、搜索和回访等交互惯例的来源。竞品宣传仅说明产品声称什么；讨论其设计质量时，区分可实际观察的界面与生命周期、官方描述、用户反馈和未经验证的推断。

## 当前界面审计

生产界面目前以“聊天列表 + 当前聊天”两栏构成。联系人列表把 Noema 与工程搭档并列；用户可手动创建专业联系人、建群、选每轮回复者，再单独切换项目工作。这忠实呈现了现有实现，却把 Noema 作为核心 agent 的理解、分工与组队工作交给用户，视觉上也更接近带 agent 标签的通用聊天模板。

顶部常驻模型选择和网关状态，多个说明文案直接解释 DSH、FreeLLMAPI、文件夹和数据流；这些对排错/授权有用，但不能长期占据所有普通交流的主视线。浅色卡片、圆角面板、字母头像与绿灰配色整洁可读，却没有形成与 Noema 名称、长期关系或协作者成长有关的品牌表达。问题既在信息优先级和职责分配，也在视觉语言，不能只替换配色和字体。

本机在隔离数据库上运行了社交 agent E2E，未调用模型。实际桌面截图确认联系人、群聊和聊天界面运行；测试在窄窗互动约定编辑器的可见性断言处失败。PR #106 正在修同一组件的分数像素滚动，当前分支尚未集成；在确认该修复后再做完整窄窗基线，避免重叠实现。这个已知局部缺陷不阻止继续审计整体结构，但不能报告当前界面状态检查全绿。

## 全产品体验模型（工作假设）

Noema 的入口仍是与同一位个人 agent 的持续交流；交流本身可以就是结果，也可以逐渐变成理解一个问题、形成计划、制作内容/工具或采取行动。产品不应把这些用途预先分割成“聊天 agent”“项目 agent”“生活 agent”，也不应把用户先送进任务或 agent 管理界面。这里描述的是候选体验连续性，不是承诺每种用途首版都实现。

从同一条典型序列检查功能范围：用户先问“这周 AI 行业有什么值得看的”，Noema 通过对话回答并展示可追溯来源；用户追问时能继续讨论，不因一次问答自动创建长期任务。几天后用户提出“持续比较各平台 AI 订阅价格”，Noema 与用户澄清目标和约束；如果这件事确实需要跨日继续，才给它一条可从原对话返回的专属脉络。Noema 可直接研究或调用工具；只有工作需要不同能力并行、长时间执行或交付核验时，才考虑复用/创建协作者。用户回到 Noema 后，能自然接续、修改范围、暂停或结束；无须理解 agent 路由，也不承担逐步检查流水账的工作。类似方式应能覆盖学习探索、个人计划、写作和创作，而不是只为软件项目服务。

这条序列引出一个整体候选承诺：用户可把问题、想法和正在推进的个人事项带给同一个 agent，它能陪用户从理解走到产出或行动，并在能力需要时组织帮助。它仍然可能太宽或缺乏选择理由；协作、连续性、个体化分别是待论证的能力支柱，不是其中任一项单独代表整个产品。卖点可以来自熟悉能力的更好组合或执行质量，不要求前所未有；下一轮须比较用户现在如何完成同类事情、替代方案实际做到什么、还留下哪些责任与成本。

体验边界：

- 普通聊天不因为系统能创建任务就自动变成任务；讨论、求证与决定可以停留在对话里。
- 当用户明确要求跨时段继续，或 Noema 判断事情有真实的等待/后续依赖时，可提议开一条与当前对话关联的 Noema 延续聊天；提议须说明后续会做什么，由用户接受后创建。普通追问、暂时搁置或单次任务不触发。
- 延续脉络应是 Noema 私聊中的主题线程，而不是一位新联系人或工程项目房间：原始对话继续保有起点，线程保存此后原始往来；开立时把用户选定的关键消息作为可见、可回源的引用带入。后续模型只通过当前线程中这份可见引用获得起点，不隐式读取另一 room transcript。聊天原文是事实来源，不另生成每次都要维护的模型总结。用户能继续、改范围、暂停或结束；结束后可从历史重新打开。
- “记住这个事项”与“自动按时执行”是两项不同承诺。延续聊天默认只保存上下文并等待用户回来；定时检查、外部监控或自动行动只有在执行能力、频率/成本、权限与失败通知都有真实方案时才单独开启，不能由“持续”二字暗示已经运行。
- 现有 `social_work_tasks` 代表有明确 workspace、runtime、结果和核验状态的工程执行，不代表通用持续事项；不要为了覆盖个人计划、研究或创作而复用它。当前消息转发已经保存来源 room/message ID、时间与内容快照，并在当前线程上下文中作为可见引用；但卡片没有跳回原消息的动作，侧栏也只搜聊天名、成员和最新预览。因而它提供了消息来源和上下文的复用起点，尚未提供主题线程、回源、跨日检索或结束语义。实现前需检验这些缺口，不直接新增通用事项表、状态面板或后台 worker。
- Noema 按实际能力选择直接回答、工具或协作者；执行身份和来源在影响用户理解、责任、质量或需要用户介入时可见。单次后台路由不必都变成群聊或消息组件。
- 持续事项要呈现真实可采取的控制（修改、暂停、停止、恢复、核验结果）；文件写入、外部发送等副作用须遵循明确授权。进度更新要有实质变化，不用合成消息填满聊天。
- Noema 与协作者的长期实践可能改变后续工作，但“成长”只有能改善后续相关工作、来源可追溯且用户能纠正时才有产品意义；不假设每个任务后需要一次模型总结，也不默认展示成长日记。
- 个人连续性不能借口跨房间灌入历史或越权披露。对话上下文、持久偏好、具体经历和协作者实践仍是不同责任边界。

## 交互结构候选

用上面同一序列评估，而非只比较漂亮布局：

| 结构 | 用户如何使用 | 收益 | 主要代价 |
| --- | --- | --- | --- |
| 所有事都留在一条 Noema 长对话 | 提问、追问、持续事项与协作更新全在主 transcript。 | 连续感强，切换少。 | 长期工作和日常交流混在一起；进度/协作者可能淹没普通对话，回访较难。 |
| **对话为入口，持续事项按需分出可恢复脉络（当前推荐继续评估）** | 普通问答与共同思考留在对话；确需跨日接续时，经用户同意开一条与原对话互相可达的 Noema 延续聊天。执行和协作只按需成为实际工作/群聊。 | 保留熟悉聊天习惯；用聊天历史而非额外总结保存来龙去脉；为多日事项提供回访位置。 | 延续聊天可能重复上下文或碎片化；必须让两边来源清楚、可互返，并避免把上下文保存误说成定期执行。 |
| 以事项/项目为首页 | 先找目标，再进入其聊天、工具、协作者和产出。 | 多个长期目标容易整理和比较。 | 普通交流被工作空间化，产品更像项目控制台；可能让用户总要先分类。 |
| 联系人/agent 房间为首页 | 先选择 Noema 或某位协作者/群聊，再发起消息。 | 交流对象、历史和群聊成员直观；贴近传统 messenger。 | 用户必须知道该找谁、何时组队；会把 Noema 的理解和编排职责推给用户。 |

继续评估“对话为入口，持续事项按需分出可恢复脉络”，但不将其宣告为最终导航或数据模型。当前最小体验建议是把确需跨日接续的事项开成 Noema 私聊中的主题线程：聊天原文是记录，用户同意才开立；开立时显式引用选定的原对话消息并保留回源，不触发模型总结、后台轮询或工程任务。它保留普通聊天入口，又为持续主题提供独立历史；相比另建通用事项对象，不维护第二种成果/状态记录。代价是线程易碎片化、来源引用会有内容快照重复，且必须解决搜索回访、结束/重开和删除含义。现有转发只解决可见快照与模型上下文，不解决回源和线程关系；现有侧栏只搜聊天名/成员/预览。现有 room 模型可以容纳多个同成员房间，但没有父消息或线程关联，也无独立归档语义。任何实现前先做架构审查，明确最小关系与删除级联；当前只确立体验假设，不新增 schema。其余结构保留为真实备选，不以一次原型反馈或现有 demo 的实现成本定案。

## 界面与品牌工作方式

产品判断和视觉判断相互影响，但各自需要证据。先形成足以解释用户在真实情境中做什么、看到什么、能怎样介入的体验模型，再设计信息结构和视觉表达；不要先选一个熟悉的聊天壳子，再用新颜色、字体或组件装饰。也不要因为品牌未定就只修前端样式。

每一轮设计应明确：所服务的情境和用户结果、主要信息层级与密度、关键操作及状态、视觉主张、与熟悉方案的实质差异、主要取舍和失败条件。结构方案应有理由地比较，而不是反复抽取配色或在同一布局上换皮。探索中的静态原型不能制造尚无生命周期、触发条件、责任归属、成本和撤回方式的产品对象。

落地前调用 [界面质量 Skill](../../.codex/skills/noema-interface-quality/SKILL.md) 检查构图、可用性、可访问性和真实状态。只有在生产应用里检查了主要、空、加载、失败、恢复和窄窗状态后，才报告界面交付完成；样稿反馈、静态截图和测试通过分别说明，不互相替代。

## 不随品牌探索变化的质量底线

- 对话历史、身份与房间上下文不因切换而丢失或意外串用；用户能找到并继续正确的对话。
- 发送、生成、停止、失败、重试与恢复有真实、持久且可理解的状态。
- 行动或委托的权限、成本、进度、结果和失败责任清楚；不能把所有核验负担交还给用户。
- 键盘、焦点、缩放、长消息输入和窄窗口可用；信息密度由真实使用需要决定，不靠堆叠面板假装专业。

这些是可直接修复和验证的产品质量要求，不自动构成 Noema 的卖点。后端结构、长期状态和 agent 成长机制应由具体体验需求决定，保持可撤回；无独立生命周期证据时，不先新增表、worker、记忆层或编排框架。

## 下一阶段

下一步把这条链写成可逐步实现的对话流程：普通交流 → 用户/Noema 提出延续 → 用户接受 → 从原消息创建可回源的主题线程 → 用户回来继续或显式开启有授权的执行 → 返回真实结果 → 暂停、结束、重开或删除。对照 Telegram 群组 [Topics](https://telegram.org/blog/topics-in-groups-collectible-usernames)（独立话题历史）与 [Saved Messages](https://telegram.org/blog/new-saved-messages-and-9-more)（消息收集、标签和搜索）等成熟通信交互，只借其交互证据，不照搬群组实现到个人聊天。沿这个流程检查联系人、房间、消息与项目工作的保留/合并/删除；定时监控的授权、成本、失败与取消单独定义。逻辑闭合后才制作有品牌表达的真实界面方案。
