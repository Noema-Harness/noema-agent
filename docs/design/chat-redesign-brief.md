# Noema 聊天体验重设计：机制先于造型

当前范围与交接点见 [Issue #104](https://github.com/c3115644151/noema-agent/issues/104)。本文件是设计研究的工作假设，不是品牌定稿，也不把助手的审美偏好当作产品证据。

## 设计问题

只把联系人列表、消息气泡和输入框换一种风格，仍然是通用聊天壳。Noema 不能靠“AI 做得更有创意”来解决同质化；界面必须由产品实际拥有、且用户能理解和控制的行为推导出来。若现有机制不能支撑有意义的不同体验，应先质疑产品主张，而不是用视觉效果掩盖它。

## 当前可核实的机制与限制

- 一位稳定身份可以参与多个独立房间；房间分别保存消息上下文。依据：ADR 0015 与当前社交聊天实现。
- 房间历史不会仅因成员身份相同而自动合并。用户可显式把消息转发到另一房间，目标消息保留来源关系。依据：ADR 0015 与消息转发实现。
- 用户明确提出的互动调整有来源、作用范围和撤回状态；它不是整段历史，也不等同于自动学习。依据：ADR 0024 与聊天实现。
- 这些机制只证明产品边界已被设计/实现，不证明用户喜欢、容易理解，或比别的 agent 产品更有价值。Noema 的市场差异和品牌叙事仍未验证。

## 设计假设（待反证）

“关系可以延续，情境不应被悄悄混在一起。”一个身份可能在不同聊天中和用户交流，但每个房间只带入经过定义的连续状态；需要把某句话带到别处时，用户可以看见它的来源与去向。潜在设计结果不是给聊天列表换皮，而是让用户能轻松辨认：现在和谁、在哪个情境交流；哪些约定跨房间有效；当前回答是否使用了别处的内容；怎样纠正或撤回这种使用。

这是从现有机制推导的候选，不是已接受的功能规格。交互不能把每次聊天变成权限面板或要求用户持续管理“上下文”。如果必要的边界信息无法低干扰地理解，或真实用户很少需要跨房间携带内容，该设计主张应收窄。

## 差异性反证与当前界面审计

房间隔离和记忆可审阅本身不是差异点。ChatGPT Projects 已提供项目内共享上下文及 project-only memory；ChatGPT Memory 也可以展示影响个性化的来源，并允许用户纠正、移除或停止使用部分信息。Claude Projects 在多个对话间复用项目知识与指令。因此，“上下文有边界”“记忆有来源”“用户能控制”都属于已有成熟产品空间，不能直接当作 Noema 的品牌主张。参考：[ChatGPT Projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)、[ChatGPT Memory](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)、[Claude Projects](https://support.claude.com/en/articles/9517075-what-are-projects)（官方帮助材料，2026-10-21 查阅）。

现有代码表明，Noema 的候选差别更具体也更难证明：**用户拥有一个跨模型/执行环境仍保持同一产品身份的 agent，同时把它放进多个有独立上下文的关系空间；这位 agent 的行为约定由用户明确塑造，并可追溯和撤回。** 这是“身份连续性与可替换运行环境”的产品假设，不等同于“多个聊天房间”。它是否给用户带来比通用项目/记忆功能更好的稳定感，尚无实证；若不能感受到，也不应把技术可移植性包装成品牌价值。

界面实现的源码审阅还显示：当前侧栏以“最近聊天”、创建专业联系人/群聊和本机保存说明组织；跨房间转发与保存互动约定都在消息操作中，桌面上操作按钮默认透明，只有悬停或键盘聚焦时出现，触摸设备则常显。由此可作有限推断：产品当前把关系/房间当作普通聊天列表，却把最有产品意义的机制放在次级消息操作里；这可能解释了为何它读起来仍像通用个人 agent。该推断来自源代码，尚未完成真实运行视觉审查或用户观察。

## 首个交互模型：从纠正到有据可查的约定

本轮建议优先验证“被纠正之后，下一次能不能看出 Noema 吸收了什么”这条关系循环，而非先展示多 agent/房间导航。它使用 Noema 已有的身份和状态，不主张保存整个房间历史：

1. 用户在和 Noema 的普通聊天里纠正它，例如“先给一个实际可行的建议，再说备选”。
2. 由用户决定要不要把这条纠正变成约定，并确认原话、想要的行为和适用范围。不同意保存时，聊天照常继续。
3. 目前 `conversation` / `both` 范围的活动约定会被组装进每次 Noema 对话请求；模型被告知只在适用情境参考它们，但应用层并不会先筛选“这轮匹配了哪条”。房间的其余历史仍各自隔离。
4. 回复附近可查看这次请求实际带入了哪些约定及其来源，并从源消息编辑或撤回。产品只说明“约定已带入请求”，不声称模型必然遵循或人格已经成长。未来设计应考虑怎样暴露“带入”与“实际相关/被遵循”的差别。

当前实现已具备明确保存、作用范围、来源原话、可编辑/撤回和每次请求的约定快照；可展开的“本轮带入互动约定”记录同时明确不保证模型遵循。它按 scope 组装，不会先按情境筛选。当前界面的关键弱点是动作藏在消息操作区，桌面默认只在悬停/聚焦时显示；未来带入记录又是折叠内容。因此这个产品承诺虽然在数据链路里，却没有成为自然交流中清楚可感知的一环。

产品假设：Noema 的个人连续性也许不体现在“它记住很多事”，而体现在用户能够逐步塑造、检查和撤回它与自己协作的方式。这个方向比“身份跨房间”更接近日常对话，也能避开把多个 agent 当作主叙事；但显式管理可能打断对话，而且记忆/来源管理已有成熟产品实践，所以它不是已验证的唯一卖点。

推荐评审的单一模型是：一条日常对话、一处用户纠正、一次明确选择保留/适用范围，再到另一条对话中看见该约定被带入并可追溯/撤回。要回答的取舍是：让未来应用更像“能被持续校准的个人 agent”，是否值得为此引入这次显式保存及后续提示；低频用户是否仍能忽略该机制，正常聊天不受打扰。若此循环不自然或用户不在乎，就删掉或收窄这项状态，不另造一层“记忆中心”。

## 首个研究切片

围绕三个日常过程做代码与运行体验对照：

1. 用户在一个持续中的主题里切换到别的房间，之后回来。身份、当前房间和草稿是否清楚且不串用？
2. 用户希望在另一房间提及一段先前对话。转发的来源、目标、接收者和后续引用是否自然、可追溯？是否有更轻的真实需求，还是这本来就少见？
3. 用户纠正 agent 的交流方式。用户能否看出此约定适用于哪里、何时生效，且能随时编辑或撤回？它是否产生了可感知的连续性，还是额外配置负担？

对照维度是任务是否顺畅、上下文是否被理解、错误是否可恢复、用户是否明白状态边界。通信产品用于验证导航和消息交互惯例；它们的视觉造型不构成 Noema 的设计答案。任何示例只作研究场景，不自动成为固定人数、房间类型或交互规格。

## 不变的质量底线与可变设计

需持续成立的底线：身份/房间/运行能力不混淆；已保存内容可恢复且不串房；发送、生成、失败、停止、重试如实；跨房间引用保留来源；键盘与窄窗可用。布局、联系人密度、颜色、字体、动效、主动性和跨房间携带规则均可调整，须有使用证据和代价说明。

## 反馈门与交付

当前不提供颜色或皮肤选项。下一次反馈门应展示一个从上述机制和真实任务推导出的交互模型，并标出哪些部分是当前行为、哪些是提议、哪些假设仍可能被推翻。只有当方案能解释它改变了什么用户行为、如何降低成本、引入什么新负担时，才进入真实应用的纵向实现。品牌成熟度最终需在真实消息内容、重复使用和主要状态中检查；原型截图或技术测试不能代替用户体验证据。

## 可靠性说明

当前源码可见单一内存草稿状态和房间切换逻辑，存在草稿归属/发送竞态风险；这是待复现的源码线索，不是已确认缺陷或已修复结果。先针对真实切换情境观察并复现，再决定应在组件状态还是存储层修复。旧的 A/B 静态预览已经撤下，因为它们只比较常见聊天结构的视觉变体，不能回答产品如何形成不同体验。
