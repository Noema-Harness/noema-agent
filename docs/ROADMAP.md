# Noema 阶段总览

这里维护阶段目标与退出条件；只在阶段取舍或交付重点改变时更新。细任务与证据留在 OpenSpec change，避免再维护一套任务看板。

## 产品交付顺序

| 阶段 | 用户结果 | 转入下一阶段的依据 |
| --- | --- | --- |
| R0 个人 agent 闭环 | 自然交流可过渡到必要澄清、研究、判断与真实委托 | 在真实客户端理解进度、成果、失败与反馈；团队贡献和使用价值得到评审 |
| R1 可信聊天入口 | 能找到成员、项目、消息和来源 | 搜索范围、定位、键盘及空错状态实际可用 |
| R2 可控行动 | 工具行动可授权、停止、核验与恢复 | 多步执行、来源、数字、断流和重启不制造错误完成状态 |
| R3 持续委托与成长 | 成员资产、经历、归档与续接可靠 | 写入、报告、恢复和成长在持续使用中形成闭环 |
| R4 日常连续性 | 工作之外也能持续帮助用户 | 一个日常情境可用，并能纠错、删除、暂停与控制通知 |
| R5 可恢复发行 | 陌生机器可安装、升级与回退 | 干净安装、旧数据迁移、备份恢复和发行诊断有证据 |

## 当前交付重点

R0 的真实使用闭环尚未完成价值验收；共享计划、协作、搜索与工具等已有实现和服务验证，但不能据此宣告全阶段通过。真实 AI 价格追踪项目中，Noema 能读取用户提供的 OpenAI 定价页，也能在群聊里调用 `manage_project_plan`；工具结果后的续答多次遇到 `provider_unavailable` / `ERR_CONNECTION_CLOSED`。直连下普通短答曾成功，当前证据不足以把断流归因于单一代理或网络原因。执行链曾在隔离工作区产出代码；外部运行发现 `selftest.py` 第 97 行语法错误，何程已在隔离工作区修复该行，但执行在完整自测与提交前被本地请求预算中断。检查 revision 32 时还发现 w3 的负责人与阻塞说明不一致，且依赖已完成；Noema 在隔离数据库将 w3 更新至 revision 33 的 `in_progress`，保留验收范围，未触碰生产数据。续接时应先在现有隔离工作区完成自测并读取执行结果，再处理真实来源核验与提交；不要重建已生成的代码，也不要把该隔离计划状态当作生产项目变更。项目协作测试入口已修复恢复模式和 `projectStore` 注入，真实运行已覆盖该入口；最终仍需核对代码提交证据、验收、主聊反馈及工具后续答稳定性，不以读到网页或写出文件宣告 R0 通过。

在恢复 DeepSeek 真实协作调用前，先完成成本专项第一阶段：应用已接入本地 SQLite 表 `model_usage_records`，由 `ModelUsageStore.getSummary()` 按主聊、群聊/专业委托、项目执行和成长等场景汇总 usage/cache 数量与完成、失败、中断状态；只保存元数据，不保存消息内容。新版本还没有真实请求数据，因此缓存命中率尚无结论。先用正常使用产生的少量记录取得按场景的实际数据，再选择一项有证据的成本优化；不要把 R0 的隔离运行数据或用户账户显示余额当成 token 账单。

源码结构维护已在提交 `395858f` 完成并推送，依赖边界由 `npm run source:check` 持续检查；这只改善了后续维护起点，不代表 R0 价值验收。当前回到 R0：基于已有真实项目验证 Noema 如何接收成员报告、推进工作、识别阻塞并请求必要评审。下一项跨模块实现前先从具体失败或缺失的用户结果建立 OpenSpec change；不要再为源码整理单独开一条并行主线。
