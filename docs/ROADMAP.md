# Noema 阶段总览

这里维护阶段目标与退出条件；只在阶段取舍或交付重点改变时更新。细任务与证据留在 OpenSpec change，避免再维护一套任务看板。

## 产品交付顺序

| 阶段               | 用户结果                                       | 转入下一阶段的依据                                                 |
| ------------------ | ---------------------------------------------- | ------------------------------------------------------------------ |
| R0 个人 agent 闭环 | 自然交流可过渡到必要澄清、研究、判断与真实委托 | 在真实客户端理解进度、成果、失败与反馈；团队贡献和使用价值得到评审 |
| R1 可信聊天入口    | 能找到成员、项目、消息和来源                   | 搜索范围、定位、键盘及空错状态实际可用                             |
| R2 可控行动        | 工具行动可授权、停止、核验与恢复               | 多步执行、来源、数字、断流和重启不制造错误完成状态                 |
| R3 持续委托与成长  | 成员资产、经历、归档与续接可靠                 | 写入、报告、恢复和成长在持续使用中形成闭环                         |
| R4 日常连续性      | 工作之外也能持续帮助用户                       | 一个日常情境可用，并能纠错、删除、暂停与控制通知                   |
| R5 可恢复发行      | 陌生机器可安装、升级与回退                     | 干净安装、旧数据迁移、备份恢复和发行诊断有证据                     |

## 当前交付重点

R0 的真实使用闭环尚未完成价值验收；共享计划、协作、搜索与工具等已有实现和服务验证，但不能据此宣告全阶段通过。真实 AI 价格追踪项目中，Noema 能读取用户提供的 OpenAI 定价页，也能在群聊里调用 `manage_project_plan`；工具结果后的续答遇到 `provider_unavailable` / `ERR_CONNECTION_CLOSED`，现有证据不能把断流归因于单一网络原因。真实自测 T3「同一来源下插入第二条价格样例」仍触发 `source_registry(platform,url,retrieved_at)` 唯一键冲突。派单修复 `cd56365` 的两项针对性服务测试通过；修复后客户端尝试在模型回复阶段以 `provider_unavailable` 结束，只读数据库未出现新派单记录或工作任务，因此真实路由闭环仍未验证。当前不修改用户生成的 `NoemaPriceTracker` 工作区，也不重复发送付费请求来撞同一故障。成本专项先行；恢复稳定模型调用后，再回到安全副本完成真实派单、执行与 T1–T4 自测，并核对来源、提交证据、主聊反馈及工具续答。

成本工作分为识别成本与减少成本，避免把“加了埋点”误当成“已经省钱”。用量表现有 7 次 DeepSeek 社交/项目请求，其中 6 次收到完整 usage：输入 110,619 token、缓存命中 44,416（40.1%）、未命中 66,203，输出 2,274；另有一次失败请求没有 usage，费用未知。六次成功请求中，普通社交回合 4 次共 58,193 输入 token，项目工具续答 2 次共 52,426 输入 token；续答每次约 25–27K 输入 token，表明同一委托内的多轮上下文重复是值得检查的成本杠杆。按 DeepSeek 当前非高峰公示价做粗算，这六次约 $0.0114，其中缓存命中约 $0.00013、未命中输入约 $0.00993、输出约 $0.00136；仅为公开价估算，不是账户账单，不含失败请求及搜索/抓取费用。

最近一次可见的请求记录中，8 个工具定义共 17,551 字符，对应 14,491 输入 token；一次项目续答请求字符 44,083–45,918、消息数 21–23、工具数 4，输入 25,812–26,614 token。工具定义中 `manage_project_plan` 单项约 9,667 字符。现已按协调者/成员权限生成不同 schema：协调者工具减少 39.8%，成员工具减少 72.0%；其余工具不变时，对样例整组 schema 的字符估算分别减少 21.9% 与 39.7%。这些都是可复现的载荷字符变化，不能替代 tokenizer 或账单证据。代码已把变化的项目/成员/工作项值从 schema 移入请求上下文，服务端权限校验保留；稳定 schema 的实际缓存与费用收益尚待更新客户端自然请求验证。成本专项新增可空 `interaction_id`，将同一主聊 turn、社交回复/专家交办、项目执行任务与后台任务中的 API 和 DSH 请求归组，并从权威对话/任务表读取当前状态；文件核验及后台回复单独呈现，旧行保留未知，不采集正文。Tavily 每次搜索的 credits 与 request ID 现单独按交互记录；请求失败且没有 usage 时仍记为未知，网页直连读取没有另计服务费。Tavily credit 的货币成本取决于用户账户计划，当前只记 credits，不冒充统一账单金额。

源码结构维护已在提交 `395858f` 完成并推送，依赖边界由 `npm run source:check` 持续检查；这只改善后续维护起点，不代表 R0 价值验收。成本专项已建立按交互归组的模型 usage 和外部搜索 credits 账本，并完成多项低风险优化：协调者计划 schema 字符数减少 39.8%，成员版减少 72.0%，普通主聊闲聊时省略无关的既有项目计划/群聊工具、项目清单及对应行动提示；服务端授权校验保持不变。闲聊 fixture 的项目 schema 从 11,712 降到 3,254 字符（−72.2%），行动提示另减少 195 字符；字符变化不代表同等 token/费用降幅。Tavily per-call credits 也已单独记录。6 条有 usage 的 DeepSeek 请求缓存命中率为 40.1%，按操作聚合的普通社交回合为 23.8%，项目工具续答为 58.4%。这些实际费用收益仍待自然使用核验，不造付费样本。最近的重试审计还发现 RootAgent 曾在 `provider_error` 后自动重发模型请求，包括已有部分输出的轮次；现在仅对“上游明确不可用且尚无输出”保留一次自动恢复，其余由用户显式重试。下一阶段成本工作由 [#124](https://github.com/c3115644151/noema-agent/issues/124) 承接：先观察当前版本自然调用的 provider usage，再按 operation 找重复输入、无效工具和失败重试成本；可复核的优化完成后回到 R0 安全副本继续真实协作闭环。
