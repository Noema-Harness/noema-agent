| ------------------ | ---------------------------------------------- | ------------------------------------------------------------------ |
| R0 个人 agent 闭环 | 自然交流可过渡到必要澄清、研究、判断与真实委托 | 在真实客户端理解进度、成果、失败与反馈；团队贡献和使用价值得到评审 |

| R3 持续委托与成长  | 成员资产、经历、归档与续接可靠                 | 写入、报告、恢复和成长在持续使用中形成闭环                         |

## 当前交付重点

R0 的真实使用闭环尚未完成价值验收；共享计划、协作、搜索与工具等已有实现和服务验证，但不能据此宣告全阶段通过。真实 AI 价格追踪项目中，Noema 能读取用户提供的 OpenAI 定价页，也能在群聊里调用 `manage_project_plan`；工具结果后的续答多次遇到 `provider_unavailable` / `ERR_CONNECTION_CLOSED`，直连下普通短答曾成功，当前证据不足以把断流归因于单一代理或网络原因。真实自测目前在 T3「同一来源下插入第二条价格样例」触发 `source_registry(platform,url,retrieved_at)` 唯一键冲突。Noema 的团队派单虽已到达执行成员，但成员启动文件任务时将群聊房间与成员会话中的来源消息配对，导致 `project_work_start_failed`；已修正为从成员项目会话启动，并以协作服务 27/27 测试通过验证，仍待真实客户端重新派工、执行修复并完成 T1–T4 自测。当前不修改用户生成的 `NoemaPriceTracker` 工作区；不能以修复 Noema 内部路由或单元测试通过代替外部项目的真实交付。随后再核对实际来源核验、提交证据、主聊反馈及工具后续答稳定性。

成本工作分为两个节点，避免把“加了埋点”误当成“已经省钱”。`model-cost-efficiency` 已覆盖直连 API 和 DSH 后台 worker 的 usage/cache 记录。当前账本有 5 次 `deepseek-flash` 请求，共 96,128 输入 token、44,160 缓存命中 token，按 token 加权命中率约 45.9%；单次命中率从 0.8% 到 99.1% 不等。样本来自少量近期协作调用，足以支持检查提示前缀稳定性，但不足以推断长期整体命中率；本地记录也没有服务端费用字段，不能据此推算实际余额。当前派单路由修复通过协作回归检查后，下一项单独工作就是成本优化：先盘点所有模型调用来源（包括 Noema 直连、项目执行、后台任务及外部 DSH 子进程），再结合现有账本、主流 agent 应用源码级实现和近期实践，找出调用次数、上下文规模、缓存前缀、重试/压缩及模型路由中的主要成本杠杆；完成前不进行新的 DeepSeek 付费实测。不得为制造基线额外消耗余额；外部调用若无法通过稳定接口计量，应明确覆盖缺口，不能把未记录当成零成本或低缓存命中。

源码结构维护已在提交 `395858f` 完成并推送，依赖边界由 `npm run source:check` 持续检查；这只改善了后续维护起点，不代表 R0 价值验收。当前回到 R0：基于已有真实项目验证 Noema 如何接收成员报告、推进工作、识别阻塞并请求必要评审。下一项跨模块实现前先从具体失败或缺失的用户结果建立 OpenSpec change；不要再为源码整理单独开一条并行主线。
