# Noema 开发路线

## 当前状态

2026-11-02：此前从 Noema 当前代码和局部待办推导的 R0–R5 顺序及测试清单已退出当前规划。它们没有覆盖个人 agent 应有的完整能力面，也容易把开发继续收窄到现有功能的邻近修补。历史 OpenSpec 归档、决策记录和用户待测承诺仍可追溯，但不再代表当前开发顺序。

当前不预先指定下一个产品功能。先完成基于成熟 agent 应用源码的领域盘点，再据此确定完整能力范围、缺口和阶段顺序。

## 规划形成顺序

1. **建立领域能力图。** 选取仍在维护、实现可读且覆盖不同产品形态的 agent 应用。逐个检查源码、测试、状态生命周期和失败恢复，列出产品能力面及成熟度证据。闭源产品可用于核对公开体验和官方契约，不把它们称作源码参考。
2. **对照 Noema 找完整缺口。** 按相同能力维度核查现有实现、用户可见闭环、持久状态、失败路径和自动化证据；区分已覆盖、部分覆盖、缺失和不适用。不能仅从现有目录、旧 issue 或最近做过的功能反推范围。
3. **形成分阶段路线。** 按真实依赖和可交付闭环组织模块。每阶段说明用户结果、范围、前置依赖、完成条件和验证证据；同时给出总览，防止单个模块长期占满开发注意力。
4. **逐模块实现。** 每个模块先对照最接近的成熟实现，再决定复用、适配或自研。优先使用成熟依赖、协议与已验证实现；复制代码前核实许可证和技术兼容性。模块达到可用闭环后转场，不以无限微调代替整体推进。

## 计划与维护边界

- 本文件是项目阶段与完整范围的唯一当前入口；完成领域盘点后，在此呈现全局模块和阶段，不另建平行的本地路线图。
- OpenSpec 管行为规格和当前变更的设计、任务与验证；稳定实现归入 specs。它记录变更，不替代领域盘点和阶段路线。
- `.work/` 收纳研究工作底稿、临时对照表和交接材料；被采用的结论进入本路线、产品文档或 OpenSpec，临时材料不长期并列成权威来源。
- GitHub 用于源码、PR、发行和外部协作问题；项目内部阶段、任务状态和测试清单留在本地维护体系，不用 Issue 或 Project 复制。
- 既有 ADR、OpenSpec archive 与代码测试是历史证据。读取时核对当前实现，不因材料详尽就把旧规划恢复为现行路线。

## 重新规划的退出条件

- 覆盖主流 agent 应用共同能力及 Noema 所需的特殊能力，说明每一项的纳入依据或排除理由。
- 源码比较能定位到具体仓库版本、代码路径、行为契约、状态边界和对应测试；仅列功能名或文档宣传不算完成。
- 能从完整能力图看清 Noema 当前的真实覆盖面，再拆出依赖清楚、范围平衡的开发阶段。
- 计划明确哪些验证由助手做短测，哪些真实长测由用户在整体可用后完成；待用户测试的事项只在本文件维护一份。
- 下一位项目负责人完成上述盘点与路线重建后，再更新本页并开始选择正式开发模块。
