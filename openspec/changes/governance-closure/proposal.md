## 为什么

`D-20261118-decision-dialog-flow` 被退回执行中，理由是「验收项只覆盖 E24–E26，E12/E19/E21/E23 未落地；验收项与已定项没有映射；决议与执行计划未闭合」。同时本轮暴露出三类入口缺口：条目字段只能靠一次性脚本改、日期前缀无法区分同日条目、讨论议题无法用命令标记暂停。

## 改什么

组一（补齐入口，防绕过）：
1. `decision -- edit`：待裁增删、要定、阻塞、结论，一次写盘，写前校验、失败不落盘、`--dry-run`。
2. ID 保护：日期前缀匹配多条时列出候选并拒绝。
3. `decision -- pause / --resume`：讨论期标记暂停（写阻塞行 + 轮次说明），恢复时覆盖。
4. 规则包：`discussion.md` 补暂停/恢复只走命令；命令缺能力时停下登记缺口，禁止一次性脚本与顺手立 change。

组二（把验收与已定项闭合）：
5. 阶段事件规范化：`退回`/`转待验收` 成对、倒序、不重复；写入时整理，`docs:check` 校验成对与重复。
6. `decision -- coverage --entry <id>`：逐条列 E 的归属（归档 change task / 条目切片 / 「不在本批：原因」）。
7. `advance --stage 待验收` 要求覆盖率 100%，错误列出缺项。
8. `npm run acceptance --entry <id>`（E12）：按 E 编号生成验收页（`[用户]/[机制]/[未验证]` + 证据指针）到 `.work/review/`。

组三（补未落地校验与产物）：
9. `advance --design <path>`（E21）：设计稿「待确认项：- 无」+ 用户批准原话与日期，否则拒转执行中。
10. `advance` 校验 proposal 引用了本条目（E23）。
11. `transition -- handoff|report` 生成骨架（E19）。

执行段落规则补一条（回工）：回工范围由退回原因定义，清单可直接落进 change tasks，不单独成文档。

## 目标

1. 条目字段、阶段事件、暂停/恢复、ID 指向都有唯一命令入口，不再需要一次性脚本。
2. 进「待验收」前能机器判断「已定项是否全部有归属」，缺项拒绝并列出。
3. 验收页由命令按 E 编号生成，取代手写。
4. 设计稿校验、proposal 引用校验、交接/报告生成补齐 E21/E23/E19。

## 非目标

- 不改条目四态与门的判定口径（本批只补「已定项覆盖」这一条新校验）。
- 不做界面对 DECISIONS 的编辑（L1 入口 + 结构门，不做 L2）。

## 取舍

- **一个 change 装十项而不是三个小 change**：这十项都服务同一个目标（入口与验收闭合），且互相引用（coverage 要 edit、验收页要 coverage）；拆开会产生跨 change 依赖与多次计划批准。
- **回工不单独写开工文档**：范围由退回原因 + 缺口表定义，直接落 change tasks；首次开工清单仍需用户批准，深度随范围大小，不按阶段类型另立两种文档。
- **阶段事件行保留历史但成对倒序**：既留审计，又能让门判断「有转段无退回」这类非法状态。
- **ID 保护只做前缀拒绝不做自动补全**：自动补全会让 agent 猜错条目；拒绝并列举候选更安全。
