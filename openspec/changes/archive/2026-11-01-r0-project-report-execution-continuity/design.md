# Design

## Context

见 proposal。主聊收到项目内部报告时，`start_project_work` 已可能存在，但工具说明把它限制在用户本轮明确提出本地执行请求。运行时已验证项目成员、能力和可选工作包，却没有把内部报告与活动计划授权绑定。

## Goals / Non-Goals

**Goals:**

- 让已授权的进行中工作包可以跨越成员报告边界继续执行。
- 用运行时校验确保内部报告不能转授权到别的项目、负责人或计划项。
- 保留工作区选择和现有文件执行权限边界，不增加额外模型轮次。

**Non-Goals:**

- 不自动重开 `blocked` 工作包、不改变计划状态、不绕过待用户评审。
- 不改变用户直接发起本地工作时的既有授权流程。
- 不代表工作区选择已完成；执行器只在选择器确认后接受任务。

## Decisions

1. **已有计划状态是唯一续接凭据。** 内部报告中的自由文本不构成新的用户命令。仅 `in_progress` 工作包能授权续接；工具调用必须携带匹配的 `project_id`、`plan_item_id` 和该项 `ownerAgentId`。现有运行时校验负责执行者资格与工作包状态。
2. **执行范围取自工作包。** Noema 的指导要求新任务落在验收范围内。若报告说明阻塞未解除或需要用户决定，先保留项目停顿，不调用文件执行器。
3. **工作区仍由用户选择。** 选择器承担具体本地目录授权与数据流披露；调用工具不等于任务已建立。完成或取消均沿用现有任务卡片和状态处理。
4. **不增加编排调用。** 将计划作为已有委托的连续依据传入报告轮次，使用当前模型轮次直接判断是否应续接。
5. **项目续接工具循环读取新状态。** Noema 在主聊为明确续接的项目增补执行成员后，把该项目作为本轮临时执行上下文；后续工具轮次按最新项目成员和计划重建执行工具。文件任务只在对应工作包已改派给合格负责人并进入 `in_progress` 后启动，记录同一工作包 ID。

## Risks / Trade-offs

- [模型可能把计划工作包范围解释过宽] → 工具调用必须绑定确切的进行中工作包和负责人，系统拒绝缺失或不匹配的绑定；指导明确不允许扩展验收范围。
- [工作包状态可能因旧数据不准确] → 仅依据当前计划投影；阻塞或等待评审时不启动，先由 Noema 核实计划状态。

## Migration Plan

无需数据库迁移。内部项目报告改用新增的运行时边界；现存 `blocked`、`pending` 和 `submitted` 项不会改变状态。
