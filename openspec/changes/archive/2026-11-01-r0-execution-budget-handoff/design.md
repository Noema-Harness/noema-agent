# Design

## Context

参见 proposal 与 `project-execution` 规格。当前执行器把工具调用数和模型轮数绑定在同一检查点上；达到边界后，续接可能沿用已耗尽的累计计数，不能稳定开始新的工作片段。

## Goals / Non-Goals

**Goals:**

- 让工具预算成为单段上限，而不是整项任务的永久上限。
- 到预算边界时先产生一段只读上下文的进度摘要，再交还给 Noema/用户决定是否继续。
- 续接时保留累计工具数与幂等账本，并从新的片段轮次开始。

**Non-Goals:**

- 不自动无限续接；每次续接仍由 Noema 或用户发起，避免无界成本。
- 不放宽工作区权限、单次工具批次大小、命令超时或上下文容量限制。
- 不把预算摘要当成计划工作项的提交或验收。

## Decisions

1. **预算按片段计算，统计按任务累计。** 执行器内部另记本片段的工具调用数；检查点继续保留累计调用数。每次安全续接重置轮次和片段计数，但不清空操作历史或幂等账本。
2. **预算边界使用无工具的模型轮次交接。** 到达上限后禁用工具，要求模型说明已完成、未完成与续接点，并明确不能宣称任务完成。模型请求的超额批次整体不执行，先将拒绝原因作为工具结果写入上下文，再进入只读交接。
3. **复用现有恢复状态。** 使用现有 `tool_round_limit` 可恢复错误码与检查点，不增加数据库状态枚举；卡片改为说明“本段预算已用完，进度已保存”，仍展示从检查点继续。上下文损坏、未决副作用或非完整工具边界继续禁止续接。
4. **用户续接明确，成本可控。** 不因为额度边界自动再发一段工具任务；用户或 Noema 查看摘要后显式继续。每次交接均展示任务累计调用数。

## Risks / Trade-offs

- [模型的摘要可能错误判断完成度] → 交接文本由系统固定标注为“预算摘要，不代表验收”；计划提交/验收仍沿用独立流程。
- [多次续接会增加总成本] → 每段仍有硬上限；每次预算摘要交还给协调者/用户决定下一步。
- [旧版本检查点使用累计轮次] → 只对安全且完整的预算检查点归零片段轮次；保留累计工具调用数和已执行调用账本。

## Migration Plan

无需数据库迁移。旧的 `tool_round_limit` 检查点继续沿现有兼容条件恢复；恢复时将模型轮次作为新片段从零开始，累计工具统计不变。
