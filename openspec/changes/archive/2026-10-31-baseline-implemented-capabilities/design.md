# Design

## Context

OpenSpec 当前没有基线规格；已有 `docs/PRODUCT_CHARTER.md` 记录产品方向，`docs/ROADMAP.md` 管阶段顺序，`docs/ARCHITECTURE.md` 提供代码导航，核心流程图展示机制全景。见 proposal 的 Why。

## Goals / Non-Goals

**Goals:**
- 将已实现且有自动化证据的核心聊天、专业成员和项目协作行为写为可追踪规格。
- 保持方向、阶段计划、代码导航、逻辑流程和行为契约各自只有一个权威入口。
- 让工作区检查能够发现规格目录被留空。

**Non-Goals:**
- 不把未实现规划补写成规格，不将整份路线图或流程图复制进 OpenSpec。
- 不追溯重写归档变更或 ADR，也不在本次补齐未审计的所有工具、存储和平台能力。
- 不改动产品行为。

## Decisions

1. **以实际行为测试与当前代码确定首批规格。** OpenSpec 基线仅覆盖已验证的聊天连续性、专业成员生命周期与委派、项目协作与成果验收。未被这些证据覆盖的领域在后续对应变更中补齐；不为追求规格数量而臆造覆盖面。
2. **文档与规格各司其职。** 产品章程保存方向及已接受的高层边界；路线图保存阶段目标与退出条件；架构文档保存模块导航；逻辑流程图保存跨角色的流程全景并标注已实现程度。`openspec/specs` 是当前可观察行为契约；活动 change 记录将发生的差异，归档 change 只作历史证据。
3. **根目录文件按读者和触发条件读取。** `AGENTS.md` 是自动加载的短协作契约与路由入口；README 面向用户安装/导航，CONTRIBUTING 面向外部贡献者。它们不充当行为规格，工作恢复按 `.codex/workspace.json` 选择所需当前文档，而非把根目录所有文件都当成最新上下文。
4. **维护检查只防止结构性遗漏。** `workspace:check` 确认规格目录至少含有一个 OpenSpec `spec.md`，并继续检查当前文档路径与链接。它不能证明规格与代码语义一致；行为变更仍须在同一 OpenSpec change 中更新规格并通过相称行为测试。

## Risks / Trade-offs

- 基线由部分核心闭环开始，不能代表整个应用已经完整规格化 → 明确列出范围，后续行为变更沿模块增量补齐。
- 规格可能随代码变化而失真 → 强制行为变更通过 OpenSpec 表达并配测试；结构检查不冒充语义新鲜度校验。
- 规格和流程图可能重复 → 流程图只呈现逻辑关系与节点状态，输入/输出、错误和验收条件以规格为准。

## Migration Plan

先以变更差异建立三份行为基线，再归档将其合并为当前规格；更新文档职责说明、README 导航和工作区检查；最后运行严格 OpenSpec 校验与相关维护检查。
