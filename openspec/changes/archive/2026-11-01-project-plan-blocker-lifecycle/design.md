# Design

## Context

计划修订是追加式保存，`get()` 将最新修订投影为当前计划。工作项的 `blocker` 字段既保存在历史快照，也会直接提供给成员和 Noema。当前更新逻辑只在特定的 `submitted → in_progress` 转换时清空它；其他离开 `blocked` 的路径会沿用旧值。

## Goals / Non-Goals

**Goals:** 当前计划状态与阻塞说明保持一致；保留历史修订原貌；让审阅退回原因继续可追溯。

**Non-Goals:** 不做批量改写用户数据库、不改计划结构、不把所有旧历史改成新语义。

## Decisions

- 在当前计划投影中，只有 `status === 'blocked'` 的工作项暴露阻塞说明。这样已有旧快照在不迁移数据的情况下也不会继续误导当前读取者；历史修订 API 仍可查看原始记录。
- 状态更新后，若结果状态不是 `blocked`，持久化的当前修订清空 `blocker`。仍为 `blocked` 时沿用原说明或保存新说明。
- 审阅要求修改属于提交审阅记录，不继续复用当前阻塞字段；退回后状态恢复为 `in_progress`，当前阻塞为空，审阅原因保留在 `evidenceReviews`。

## Risks / Trade-offs

- 旧修订中的阻塞文字仍可在历史中出现，这是有意保留的审计证据；当前计划读取会隐藏它。
- 个别调用方可能依赖非阻塞状态携带 blocker 作为一般备注；全仓代码与测试需要核对，若存在此用法应迁移到 evidence 或 review reason。
