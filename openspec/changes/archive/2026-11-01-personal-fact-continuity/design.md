# Design

## 取舍

### 个人记忆由 Noema 的主聊持有

现有 `memory.md` 是每位专业成员自己的资产，写入影响成员未来会话；把用户信息塞进该文件会混淆身份、权限和生命周期。个人记忆只属于用户与 Noema 主聊，项目成员默认看不到。需要把某条信息带入项目时，由 Noema 在具体委托中有目的地转述，而不是共享整份档案。

### 显式保存，主聊按需读取

当前切片不做后台自动抽取：这既避免每轮或后台多一次模型调用，也避免把闲聊和敏感内容静默固化。用户可以在聊天中明确要求记住/修改/忘记，或在设置中手动维护。主聊提供小型记忆管理工具，在现有工具循环内完成请求；纯检索仅在相关时发生。

记忆管理工具只接收最少字段：条目 ID、用户明确给出的文字和来源消息 ID。模型不得从整个历史或成员报告推断新个人事实。搜索是只读操作；写入需落在用户请求范围内。设置关闭后，不提供读取工具，也不将任何条目注入上下文。

### 数据模型和上下文

在现有 SQLite 社交数据库中增加独立 `social_user_memories` 表，内容、来源类型、来源房间/消息 ID、创建和更新时间分别存储。来源消息删除时以外键 `SET NULL` 保留条目，并在界面显示来源已不可用；删除记忆则硬删除正文。修改原位更新，不保存已删除的旧正文。

检索沿用本机数据库，不引入向量服务或新依赖。搜索由 Noema 在需要个人背景时通过只读工具发起；每次只返回少量匹配条目，并带回 ID 和来源时间。不会把完整记忆集放进系统提示或每轮历史。记忆作为资料块进入上下文，明确不是系统规则。

### 用户控制与界面

在现有 Noema 设置中添加“个人记忆”入口，打开独立管理视图。视图可看到开关、条目、来源时间与编辑/删除操作；空状态直接允许手动新增。删除确认明确说明原聊天仍会保留。成功、保存失败和暂停状态都用设置界面现有反馈模式呈现，不在主聊额外插入管理卡片。

### 成熟实现参照

- ChatGPT 将 saved memories 与原聊天区分，提供查看、修正、来源和删除控制；删除记忆本身不等于删除聊天：[OpenAI Memory](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)。Noema 采用同样的状态区分，并在本地明确来源边界。
- Claude 将历史聊天搜索与跨聊天 memory 区分，并支持记忆开关与单次不使用：[Claude search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)。Noema 不把检索旧聊天伪装成个人记忆。
- Letta 将始终驻留的 core memory 和按需搜索的 archival/recall 分开：[Letta memory concepts](https://docs.letta.com/guides/agents/memory/)。Noema 此切片只采用“独立持久条目 + 按需检索”的职责边界，不迁入它的服务端向量与 agent runtime。
- Cursor 的记忆按项目范围，并允许用户审阅保存：[Cursor Memories](https://docs.cursor.com/en/context/memories)。Noema 因个人记忆作用于主聊，采用用户级范围，同时隔离专业成员会话。

## 生命周期

- 应用迁移前已有消息无需扫描或迁移为个人记忆。
- 每条记录始终可由用户检视和直接纠正；不存在自动过期推断或不可见的自动合并。
- 来源消息不可用时保留来源类型与记录，不丢失记忆内容。
- 暂停只影响未来主聊请求；不会改写旧答复，也不会删除条目。
- 删除永久移除条目正文和所有索引，不触碰聊天原文。

## 成本与限制

无后台提取模型调用，无外部 API 请求。按需搜索可能为单次主聊增加一次工具往返；通过工具按实际需要调用，不因每条聊天自动搜索。存储正文在当前切片限制为 2,000 字符，单次搜索至多返回 5 条，所有附加内容合计限制为 4,000 字符。后续可根据真实使用再评估语义检索，不为假想规模先引入向量数据库。

## 不在此变更内

- 从历史聊天批量生成记忆或后台自动总结。
- 个人记忆共享给项目成员或其他模型会话。
- 主动回访、日程、通知和跨设备同步。
- 对话删除与记忆删除的级联删除；两者在 UI 中清楚区分。
