## 2. 从真实 usage 找到并实施最大成本杠杆

- [x] 2.1 对照官方 DeepSeek 缓存文档、OpenCode、Goose 与当前 DSH headless/token-meter 源码，形成覆盖 Noema 请求路径的短对照记录；确认缓存字段与稳定前缀边界，不复制造成额外维护的外围机制。
- [x] 2.2 根据 5 次近期 `deepseek-flash` 真实请求和源码追踪选择首个低风险优化：96,128 输入 token 中命中 44,160，token 加权命中率 45.9%，单次 0.8%–99.1%；请求均为社交/项目协作场景，不含 `root_chat`，不能代表全部调用。根对话中按请求增加的网页引用/历史检索系统消息原先位于历史之前，现移至稳定历史之后、当前用户消息之前，以保留更长的可复用前缀。用量账本同时补记工具定义 JSON 字符数（不含工具正文），便于以后区分上下文和工具负载；不新增付费基线调用。
- [x] 2.3 源码审计显示社交工具 schema 会嵌入项目、成员、工作项与来源 URL，导致这些运行时值随请求改变工具定义。将动态名单移到单条项目工具上下文，schema 保持稳定；所有真实 ID、URL 和工作项仍在服务端原有执行入口校验。一次 fixture 对照中，8 个工具定义共 17,578 字符，单个 `manage_project_plan` 定义 9,667 字符；动态上下文为 503 字符。该测量只描述字符大小，不是 token 或费用。68 项聊天、计划、协作、评审用例通过；没有为此发送新模型请求。
- [ ] 2.4 在更新后的客户端自然使用中读取 `tool_definition_characters`、cache hit/miss 与完整输入用量，确认稳定 schema 是否延长了可复用前缀，以及调用场景中的实际收益。只有自然流量，不造付费测试；若无足够重复请求，就保留为未验证，不凭字符数宣称节省金额。

- [x] 3.3 排序后优先处理重复注入的项目计划工具 schema：历史请求中工具定义达 17,551 字符，完整计划 schema 单项达 9,667 字符；成员会话实际只需读取证据、提交本人工作和执行受指派评审。相较全量 schema，按成员权限收窄并移除冗余 project_id 后，总 schema 字符下降 72.0%；协调者 schema 精简重复说明后下降 39.8%。这是可复现的请求载荷下降，模型 token 与费用收益待真实调用确认。
- [x] 3.4 为协调者与普通成员生成各自所需的计划工具 schema；继续由服务端验证角色、权限、任务归属与计划状态，不以模型可见字段代替授权校验。没有改变工具操作结果或触发额外模型请求。
- [x] 3.5 用现有账本和可复现的本地请求构造/计数验证结构性收益；本地验证只报告 schema/请求字符数，不替代 provider token 或账单。实际 usage 核验留给自然流量任务，不造付费样本。

## 4. 面向 DeepSeek 余额的下一段成本降低

- [x] 4.1 结合 Noema 真实调用样本及 Codex、OpenCode 源码和近期 TokenEconomizer 研究，区分缓存、重复上下文、工具 schema、循环调用与多 agent 交接等成本杠杆；记录哪些协议实现不可直接移植，见 design.md「下一段：降低每个有效结果的成本」。
- [x] 4.2 用离线 fixture 对照无项目主聊与持有项目的普通闲聊：后者旧路径在无关对话中携带 6 个项目能力工具、11,712 schema 字符；无项目主聊为 2 个通用委托工具、3,254 字符。选择常驻项目工具作为第一项重复负载，不生成付费请求。
- [x] 4.3 普通主聊只在当前或最近可见上下文明确涉及既有项目/软件执行时才发送项目工具及对象列表；继续保留新团队和专家委托工具。项目绑定群聊、成员会话、自动报告、评审和已进入的工具续答仍保留完整项目能力；路由依据由确定性本地文字/会话上下文判断，不增加模型路由调用。
- [x] 4.4 服务级用例验证普通闲聊移除既有项目工具和对象名单、显式项目问题及随后省略主语的续接仍重新加载计划/群聊工具；项目群、成员执行和项目复盘用例继续通过。离线 fixture 中项目闲聊 schema 从 11,712 降到 3,254 字符（−72.2%）；字符变化不当作实际 token 或账单结论。
- [ ] 4.5 在自然使用中观察实际 DeepSeek cache hit/miss、请求数及每交互最终状态；没有足量自然样本时保留“实际费用收益未确认”，不为测试主动消耗余额。后续专项由 GitHub Issue [#124](https://github.com/c3115644151/noema-agent/issues/124) 跟踪。
- [x] 4.6 当项目工具未暴露时，省略与项目续接/文件执行及计算器无关的常驻提示；按本轮工具集恢复必要指引。用普通交流与显式项目问题回归验证；同一能力 fixture 的行动指导减少 195 字符，仍不折算成 token/费用。
- [x] 4.7 将按轮变化的行动指导、转发说明和历史检索结果放到既有聊天历史之后、当前用户消息之前；回归验证内容保留且顺序正确，避免动态片段提前截断可复用前缀。只验证请求构造顺序，不把它当作缓存命中或账单改善证据。

- [x] 4.9 将原先合并记录为 `social_turn` 的模型调用按主聊、主聊项目工具模式、成员私聊、项目私聊、普通群聊、项目群和成长回合区分。标签仅记录固定场景，不含房间 ID、消息或项目数据；用服务测试核对分类，避免把普通主聊和项目工具 schema 混成同一缓存样本。无需数据库迁移，也不发模型请求。
- [x] 4.10 源码追踪社交请求的完整历史构造，将每轮变化的项目计划/研究权限、成员资产快照、经历简报及评审指令移出稳定 system 前缀，放到历史之后、当前消息之前；保留全部内容、角色和授权。定向服务测试确认项目快照与成员资产快照顺序，26 项社交聊天用例通过；未发模型请求。真实缓存收益留给自然 usage 样本确认。

- [x] 4.13 DeepSeek 项目工具续答在动态对象名单变化时，将最新 system 快照追加到工具结果之后，避免每步重写用户消息前的历史前缀；名单未变不重复注入，名单清空时追加空快照。定向服务测试确认成员增补/计划更新后原请求消息前缀逐项不变、最新快照可见；其他兼容服务维持原实现。此项改善缓存前缀结构的机会，不代表服务端已命中或节省费用；待自然 usage 确认。
