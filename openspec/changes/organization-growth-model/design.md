# Design

## Context

`proposal.md` 描述了现状：团队由项目创建时顺带生成，成长由复盘回合直接写资产。本设计只回答“下一阶段按哪种模型改”，不预设实现细节；`## 待用户决定` 的三项回答后再补规格增量和任务拆分。

当前实现的准确边界（用于判断改动成本）：

- 团队表：schema 42 新增 `social_teams`（id/title/brief/status/lead_agent_id/group_room_id）与 `social_team_members`（team_id/agent_id/role/joined_at/removed_at），`social_projects` 增加 `team_id`；迁移把每个旧项目回填成 `team-<projectId>`。
- 创建路径：`SocialProjectStore.createProject` 在同一事务里同时写项目、团队、群聊房间、成员和系统消息，团队标题 = 项目标题，团队负责人 = 项目负责人。
- 成员规则：至少一位专业成员；没有“团队至少几人”的下限，也没有独立于项目的团队创建入口。
- 成长：`finalize_project` 触发 `ProjectGrowthBatchScheduler`，按成员逐个跑一次复盘回合；成员在回合里调用资产工具写 `social_agent_asset_revisions`（path/revision/content/reason/sourceTurnId/sourceProjectId），写入即生效并注入后续提示词；可删除、可恢复、同回合同路径只写一次。
- 规格缺口：`openspec/specs` 中 `project-collaboration` 只覆盖项目空间、计划、验收、归档，`specialist-agents` 只覆盖身份、资料、能力和委派；团队提案、岗位模板、成员资产、成长批次都没有 requirement。

## Goals / Non-Goals

**Goals:**

- 用一句话说清“团队”和“项目”各自存在的原因与生命周期，且能在数据库和界面上对应上。
- 让“成长”有可核对的证据链：一条能力从哪次经历来、经过什么证据、什么时候开始影响行为、用户如何撤回。
- 改动范围可分批交付：先对象模型与规格，再实现与界面，不用一次改完。

**Non-Goals:**

- 不重做岗位库模板机制，也不在本次引入 Guild/部门管理界面（取决于决定 1 的答案）。
- 不改变项目执行、工作区、验收、任务证据链路。
- 不改对话历史与存档（D-018）。
- 不为了“更像真实公司”增加组织层级（公司/部门/小组）；层级只有在有可观察需求时才加。

## 方案与建议

### 决定 1：团队与项目的关系

**A. 团队是长期部门（独立对象）**
团队先于项目存在，有名称、章程、成员池和负责人；项目从团队借人并指定项目负责人；项目结束后团队继续存在并保留经历。
- 成本：新增团队管理入口、成员归属、加入/退出、跨项目复用；schemas 与权限都要分两层；UI 需要把“团队（长期）”和“项目（临时）”明显区分。
- 收益：现实公司模型，长期资产（默契、章程、领域积累）有落脚点。

**B. 取消独立团队对象**
只保留“项目 + 负责人 + 成员”。团队是项目成员集合的视图名，不再有独立表、独立生命周期或独立命名。
- 成本：schema 42 的两张表降级为只读/迁移，IPC 与界面去掉团队入口；已有 `team-<projectId>` 记录需要迁移说明。
- 收益：语义与数据一致，不会出现“同名两个对象”；跨项目复用由成员本人和岗位库承担。

**C. 团队是成员组合模板**
团队是可复用的成员组合（谁和谁擅长一起做什么），项目实例化一个团队并承担目标；团队不带项目目标，也不长期保留项目经历。
- 成本：介于 A/B 之间，需要组合管理入口；收益是复用“成型的小组”，但经历仍记在成员身上。

**建议：B。** 现在没有任何跨项目复用团队的需求，独立团队会立刻产生第二套成员归属与权限，而“长期资产”真正该累积在成员本人和岗位库里。若以后出现“同一个小组连续做多个项目”，再按 A 升级，触发点明确（同一批成员第二次共同立项）。这只是工程建议，产品取舍由用户定。

### 决定 2：成长的证据门槛

**A. 保持现状**：复盘回合里模型写资产，写完即生效。
- 成本最低；问题是被用户直接质疑为“总结一条反思就算成长”，且没有跨项目证据，容易把一次性偶然写进长期行为。

**B. 候选 → 证据 → 启用（D-014 的轻量落实）**
复盘只产出 `draft` 资产；同一路径在第二个项目被再次确认（或用户手动确认）才升为 `active`；只有 `active` 注入提示词；界面能看到每份资产的状态、来源项目/回合和修订历史，可手动提升、丢弃、回滚。
- 成本：资产表加状态与证据计数，提示词只取 active，复盘工具区分 draft/active，界面加状态。
- 收益：成长有证据链，符合 D-014；失败或偶然的教训不会自动污染长期行为。

**C. 不做自动成长**
复盘回合只产出项目总结与候选建议，资产只有用户显式要求“沉淀经验”时才写。
- 成本最低、最可控；代价是成长依赖用户主动，长期看成员不会自己变强。

**建议：B。** 它保留了现有资产机制（版本、来源、可删除恢复），只加一层状态门槛，改动可控，也直接回答“什么算成长”。

### 决定 3：维护门槛的强度

已实现（本轮）：`docs:check` + `plan:check` 进入 `npm run check`；`.githooks/pre-commit` 拒绝“只改代码不带计划/状态”的提交；活动变更里 `## 待用户决定` 未答时拒绝提交代码。

**A. 保持阻塞**（推荐）：三个门槛都阻塞，绕过只能 `--no-verify`。
**B. 只警告**：不阻塞，回到靠自觉，等于放弃本轮机制。
**C. 阻塞但给维护工具例外**：`scripts/maintenance.mjs`、`.githooks`、文档本身的小修不触发“必须带计划更新”的规则。

**建议：A。** 当前门槛正是为了对抗“0.7.4–0.7.6 零文档更新”这种行为；如果第一周就加例外，例外会变成常态。若实际使用中频繁卡在“只想修一行代码”，再考虑 C。

## 决定后的实现顺序

本变更只到决定与文档为止；实现按下面的顺序另立变更（同一时间只允许一个活动变更，因此要先归档本变更）：

1. 本变更内：把三项答案写进 `docs/DECISIONS.md`，更新 `docs/ARCHITECTURE.md` 组织对象、`docs/PRODUCT.md` 可观察行为、`docs/STATUS.md` 下一步，然后归档。
2. 实现变更 A（对象模型）：按决定 1 迁移 schema 与 store，补 `project-collaboration` 规格增量。
3. 实现变更 B（成长门槛）：按决定 2 给资产加状态/证据字段，改提示词注入与复盘工具，补 `specialist-agents` 规格增量。
4. 实现变更 C（界面）：把“团队/项目/成员”的关系和成长状态显示正确，再做视觉。
5. 每个实现变更都要有单测与 E2E 证据，`npm run check` 通过后才归档。

## 风险

- 决定 1 选 A 或 C 时，schema 42 的表会从“项目副产物”变为“长期对象”，需要迁移已有 `team-<projectId>` 记录并保留可读性；不能直接删表。
- 决定 2 选 B 时，已有资产全部是“已生效”状态，迁移默认要把它们标成 active 还是 draft 需要明确；建议保留 active（不追溯降级），新写入从 draft 开始。
- 任何一个决定都可能推翻 0.7.6 的一部分行为（成长记录、团队列表），因此本变更归档前不改这些行为。
