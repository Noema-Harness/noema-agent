# Design

## Context

See proposal.md - Why. D1 selected a Noema-owned runner derived from the fixed Codex Windows sandbox source. D2 produces `windows-command-policy` v2 with main-process volume/file identities, but it does not validate Windows handles or enforce policy. The current project command adapter rejects Windows before any helper is invoked.

The Codex crate manifest is a workspace package, not an independent dependency. Its declared dependency set includes Codex HTTP, telemetry, protocol, absolute-path, string, process, and PTY crates. The fixed source tree also places the command runner across `bin/command_runner/win.rs`, `process.rs`, token/identity modules, framed IPC, desktop launch, and setup/provisioning modules. Directly adding this crate would import a broad Codex workspace closure and its unrelated behavior.

## Goals / Non-Goals

**Goals:**

- Build a versioned Noema runner contract over the existing D2 policy and D1 backend identity.
- Keep Noema as owner of user grants, tool ledger, SocialWork state, and recovery decisions; the native helper owns OS handles and child-process mechanics.
- Make policy/setup/process preparation fail closed and preserve unknown side effects if cleanup cannot be confirmed.
- Trace command lifecycle using existing request/tool/task identity and privacy allowlists.

**Non-Goals:**

- Do not add interactive terminal/ConPTY behavior to the current foreground `run_command` contract.
- Do not add background jobs, a host-shell fallback, automatic retry, durable command replay, or Codex app/session behavior. Preserve the existing Windows adapter's `cmd.exe` command-string semantics by running the shell itself inside the isolated child policy.
- Do not install or mutate local accounts, ACLs, firewall/WFP rules, or ESU settings in this source implementation change.
- Do not claim OS isolation from mapper, compile, packaging, or simulated runner results; target-machine enforcement remains an explicit gate.

## Decisions

### Revised execution identity decision (2026-11-03)

The initial restricted-token/separate-account path below is superseded by decisions 21–25 at the end of this section. After the user confirmed the all-root hard-link rule, source review established that the current path cannot bootstrap `cmd.exe` on this host without violating that rule and does not prove the separate sandbox account's normal workspace ACL check. The user had already authorized unanswered design questions to default to the assistant's recommendation; after the AppContainer source review and a read-only host API check, the recommended ordinary AppContainer path is the active implementation direction. No command gate is opened by this design decision.

1. **Use a Noema-owned native boundary, not the Codex crate API.** Retain per-file fixed-source provenance for any copied/adapted Windows enforcement code. Replace Codex policy/protocol types with the already-owned Noema policy v2 and a narrow versioned IPC schema. The crate's declared workspace dependencies are too broad to import as a product dependency; copying its whole workspace would also pull unrelated protocol, telemetry, HTTP, and terminal surfaces.

2. **Split orchestration from OS enforcement.** Electron main validates the renderer/tool request, compiles D2 policy, assigns execution identity, and records business outcomes. A native Windows helper performs capability/setup checks and owns restricted token, process, Job, pipe, and cancellation handles. The helper cannot write SocialChatStore state or decide task recovery.

3. **Do not resume a child until its controls are attached.** The native launch sequence must keep the process suspended while applying the restricted identity and Job/process-tree control. It may resume only after policy and all mandatory launch controls succeed. Any gap or partial failure terminates the child and returns a typed stage/reason; uncertain termination maps to `outcome_unknown`.

4. **Use bounded pipe IO for the current command tool.** The current tool is a bounded foreground command with captured stdout/stderr and no interactive input contract. Its current Windows adapter wraps command text with `cmd.exe`; preserve that shell interpretation inside the sandbox and include the shell/runtime files only through trusted read roots. Preserve separate stdout/stderr, bounded buffering, explicit truncation, and deterministic close/exit handling. PTY, interactive stdin, and terminal resize are excluded until a user-visible product requirement needs them.

5. **Treat persistent network setup as part of readiness.** The Codex ordinary setup path attempts WFP installation best-effort; Noema must wrap setup so a WFP or proxy-rule failure keeps the sandbox identity disabled/unusable and rejects spawn. Setup repair must verify all required filters before identity becomes eligible. Never retry setup by launching under the current user.

6. **Diagnostics are observational and best-effort.** Record only allowlisted IDs, backend/policy versions, stage/reason enums, elapsed time, bounded byte counts, local PID, exit and cleanup outcome. Do not persist command, argv, paths, env values, raw stdout/stderr, hostnames, or credential material. A diagnostics sink failure does not affect the runner's enforcement decision.

7. **Reject ambiguous Win32 path syntax before handle resolution.** The JS policy compiler and native schema validator reject alternate-stream colons, Win32 forbidden characters, reserved DOS device components (including superscript COM/LPT digits), dot traversal components, and trailing ASCII spaces/periods. Microsoft documents that path prefixes select namespaces, colons designate streams, several device names remain reserved, and trailing spaces/periods are normalized by common Win32 handling ([path naming rules](https://learn.microsoft.com/en-us/windows/desktop/fileio/naming-a-file), [file streams](https://learn.microsoft.com/en-us/windows/win32/fileio/file-streams)). This lexical gate reduces aliases but does not prove filesystem object identity; native handle/reparse/hard-link checks remain mandatory.

8. **Treat readiness as a typed prerequisite, never as the launch proof.** Protocol/request identity, helper/policy versions, Windows build/UBR/architecture, setup/filter status, blockers, and required capabilities must all validate against the current release floor. The current floor is Windows build 19045 with UBR 7807; update it with the Noema release baseline rather than creating per-release implementation branches. The native scaffold continues to report setup incomplete, filters unverified, capabilities disabled, and `ready=false`; even a complete static probe fixture cannot enable execution until later restricted-launch and process-tree controls are implemented and verified. Electron independently validates the helper resource/version and the same OS baseline; its command transport runs a read-only capability probe before it sends an execute request. Native execute admission probes again to close a readiness-change window between parent preflight and child creation.
9. **Bind native IPC to the D2 policy and task identities.** Main/native helper execute IPC is protocol v3; the internal runner pipe is protocol v2. Decode only the bounded strict JSON schema, require the fixed `noema-codex-windows` backend ID and helper package version, and carry request, execution, task, and tool-call IDs through both process boundaries. Revalidate these bounded ASCII identities, workspace, environment, network, and every root's serialized volume/file identity before setup or child creation. Policy v2 identities originate from main-process bigint `stat` and must match native `OBJ_DONT_REPARSE` handle metadata; native handle checks remain authoritative. A schema-valid policy still proceeds through readiness and later launch gates; it never authorizes execution by itself.
10. **Resolve admission paths through pinned native handles.** Adapt the fixed Codex `no_reparse_dir.rs` NT path translation and `OBJ_DONT_REPARSE` open so Windows policy roots map to local disk volumes and existing file-system objects; compare native volume/file identity to policy v2 and keep handles alive across the readiness gate. Workspace root and working directory must be directories; explicit read/write grant roots may be a single file or directory. Every read root is scanned because it receives a capability ACL. Build one effective grant per normalized root: if that root is also in write roots, issue its write-mode SID/mask; otherwise issue its read-mode SID/mask. The mode-keyed SID store gives a changed mode a distinct SID so stale grants cannot silently widen access. A single-file root is checked directly for a single link; a directory is recursively scanned. Until enforcement is implemented and verified, capabilities stay false and execution stays disabled.

11. **Scan every filesystem capability root immediately before ACL changes.** For each single-file read/write root, query type, reparse status, and link count from its verified handle. For every read/write directory root, enumerate from its verified directory handle using `GetFileInformationByHandleEx(FileIdBothDirectoryInfo)`; open each child relative to its verified parent with reparse traversal disabled; query each regular file's link count from its handle. Reject any link count above one, any reparse point, unsupported/changed entry, more than 1,000,000 entries, depth beyond 256 directories, or API error. The user confirmed the host user account and its processes are trusted in v1; scanning all roots prevents the Noema agent from obtaining unintended access through pre-existing hard links, including read-only capability aliases. Run the scan directly before each ACL transaction and fail closed on any scan/ACL error; do not lock every file exclusively across the entire scan. This boundary does not protect against a malicious process running as the same Windows user. The native scanner and ACL reconciliation handle directory roots and single-file roots: each batch validates unique mode-specific capability SIDs against exact policy identities, rescans each root immediately before ACL access, applies and re-reads each object DACL from no-reparse handles, grants read-only or read/write masks according to the root mode, validates future-child inheritance, and emits object-count/SHA-256 evidence shaped for the main journal. `reconcile_filesystem_root_acls` and `verify_filesystem_root_acls` strict IPC operations dispatch to these methods only when the caller token has no restricting SIDs; `execute` has the same restricted-caller gate. The Electron journal coordinator invokes the bounded native helper adapter; packaging/resource resolution and command-readiness wiring remain later D4 work. No real ACL mutation has been executed.

12. **Make sandbox identity setup a recoverable state machine.** The fixed Codex reference separates a versioned setup marker, DPAPI-protected account credentials, elevated account/network setup, policy-selected capability SIDs, restricted-token construction, and per-invocation filesystem ACL refresh. Its parent application owns the persisted identity records and invokes elevated setup before runner launch. Noema assigns its durable state to one main-process `WindowsRunnerSetupService` under Electron `userData`; the elevated/native helper performs OS mutations under a named cross-process setup mutex and returns typed outcomes, but does not own or commit Noema's durable state. The main service persists `repair_required` before invoking mutations and commits `ready` only after a fresh helper probe confirms live OS state. Each Windows logon user receives one internal low-privilege sandbox identity; this is an operating-system execution identity, not a Noema application account or sign-in feature. Credential persistence uses current-user DPAPI scope and an encrypted payload bound to the sandbox account SID; only ciphertext is stored, and plaintext is held in a zeroizing owner. Keep credentials out of renderer, agent environment, command payloads, and diagnostics. During elevation, transfer the one-shot setup password only over an owner/Admin/SYSTEM-scoped local named pipe; never place it in arguments, environment, or disk. The parent validates the connecting worker PID, and both sides enforce bounded frames and explicit cancellation/failure results. Bind one mode-specific capability SID to every verified read root: a root also present in write roots receives its write-mode SID/mask, while all other read roots receive read-only SIDs/masks; include exactly these current effective grants in the restricted token. Every setup/ACL management operation must reject a caller token with restricting SIDs before acquiring a setup lock or touching OS state, so the agent cannot relaunch the helper to manage its own sandbox. Noema must hard-fail WFP errors, even where ordinary Codex provisioning is best-effort. See `.work/planning/research/noema/D3_SANDBOX_IDENTITY_LIFECYCLE.md` for the source trace and constraints. No real account, ACL, or WFP mutation is part of development verification.

13. **Journal each ACL batch before mutation and require whole-tree evidence to recover.** The main process serializes a bounded batch containing each root path, verified volume/file identity, read/write access mode, capability SID, and file-versus-directory kind before it calls the native helper. Any missing/corrupt journal or pending batch denies command readiness. The helper must reopen each root without following reparses, compare identities and root types, rerun hard-link preflight, then apply and verify the mode-specific ACE on each current object's handle while also verifying future-child inheritance for directory roots. Typed completion evidence includes exact root/SID/mode tuples, object and verified counts, an SHA-256 digest of the verified object identity set, and inheritance status. After restart, the main process must obtain fresh helper evidence for the persisted batch before clearing a pending journal. If read-only evidence exactly matches the persisted verified snapshot, it may clear; if the tree or ACL state changed, it must idempotently reconcile the persisted grants, refresh the verified snapshot, and perform another read-only verification before clearing. Any ACL, scan, or verification error leaves the journal pending. `windows-runner-acl-journal.mjs` owns the main-process sidecar, and `windows-runner-acl-transaction.mjs` enforces journal-before-helper sequencing, serial in-process batches, restart recovery, changed-tree refresh, and post-transition read-only verification using an injected helper interface. Strict native ACL IPC accepts only journaled grant roots, their verified identities, access modes, and capability SIDs. `windows-runner-native-helper.mjs` provides the main-process shell-free, allowlisted-environment, bounded one-shot transport with strict response/evidence validation; tests compose it with the durable ACL transaction service using a fake process; a real release helper was also reached through the Node transport using only the read-only verify operation on a temporary directory, which returned the expected missing-grant denial without changing ACLs. Electron package resource resolution and command-readiness wiring remain later D4 integration work. Do not treat a journal transition or test fixture as proof that Windows ACLs were changed or enforced.

14. **Scope sandbox identity per Windows logon user, not per Noema account.** The current usable network policy is `deny`; `prompt-per-destination` is rejected until Noema's identity-bound broker capability is implemented and proven. One low-privilege sandbox account per Windows logon user is therefore sufficient for this release. Do not import Codex's offline/online account pair without matching Noema policy semantics; revisit account count when broker-backed network access becomes executable.

15. **Keep setup storage rooted in the main process' Electron `userData`.** The main process passes that exact absolute path in the strict setup request so the native helper can access the current-user DPAPI credential store. Do not infer it from a broad environment variable or accept a renderer/agent-selected path. Validate the native path as a bounded local drive path and reject UNC, device namespaces, and traversal components before setup I/O. The parent remains the only durable setup-state owner.

16. **Create and recover only the exact pending sandbox account.** Generate a random `Noema`-prefixed local account name and strong password; persist both under current-user DPAPI before any OS mutation. This follows the shape of fixed Codex `setup_provisioning/sandbox_users.rs` but narrows its recovery behavior: elevated setup uses `NetUserAdd` with `USER_PRIV_USER`; if a pending record exists and the account was already created, accept it only after `LogonUserW` verifies the pending password; never reset an existing account after a generic create failure. Once a record has a bound SID, require the named local account to resolve to that exact SID and authenticate successfully; do not silently recreate a deleted/replaced account. Resolve the local `.<\\>name` SID and bind it to the DPAPI record only after the elevated worker returns the matching typed result. The worker owns the machine-wide setup mutex across the OS mutation. DPAPI protection follows the fixed Codex `dpapi.rs` API family but intentionally omits machine scope. Development tests exercise framing, validation and state persistence only; they must not call UAC or create an account. Setup remains incomplete until an independent live probe verifies account state and the remaining token, filesystem and network controls.

## Risks / Trade-offs

- [Restricted-token bootstrap conflicts with the confirmed all-root hard-link gate] → The old restricted-token path is retired from the v1 target: `System32\cmd.exe` is hard-linked to a WinSxS path on this host, and the separately-owned workspace account's first ACL check was not established. Use the ordinary AppContainer candidate; do not weaken hard-link/default-deny behavior. Keep command readiness false until AppContainer/ACL/network/process controls are implemented and accepted.
- [Codex enforcement code is tightly coupled across token, ACL, network, provisioning, and process modules] → Extract only after mapping actual call/dependency edges; keep provenance/diff and license notices next to each copied module; do not substitute a handwritten permissive shim.
- [Elevated setup, sandbox identity and WFP behavior cannot be proven on the current host update level] → Keep runtime command gate closed until the confirmed Win10 22H2 + current ESU baseline is installed and the user completes target-machine enforcement acceptance.
- [Suspended creation or Job assignment can fail after a process handle exists] → Ensure every pre-resume failure terminates and awaits the child; preserve `cleanup_unknown` if termination cannot be confirmed.
- [Output volume or a stuck pipe can delay shutdown] → Bound retained bytes, continue draining/discarding after truncation, and use bounded cancellation/cleanup deadlines.
- [A copied source file can drift from the fixed upstream behavior] → Record source SHA/path and local delta in the source ledger; re-audit changes before updating the pinned source.

## Migration Plan

1. Add the native crate and typed IPC contract while the Windows execution gate remains closed.
2. Implement capability/setup readiness and policy admission; expose a readiness report but do not enable commands until every required capability is backed by runtime evidence.
3. Implement AppContainer launch, Job binding, bounded pipes and cancellation; integrate results into the existing executor/tool lifecycle.
4. Package the helper as a single versioned Forge resource and verify missing/mismatched-resource rejection.
5. Keep command execution disabled until D4 packaging and the user-authorized target-machine OS enforcement gate pass. Rollback removes the resource/wiring and leaves the Windows gate closed; it must not restore SRT or host execution.

## Open Questions

- The exact minimal Codex source subset and its dependency/license closure must be confirmed during implementation. This can change file selection and build configuration, but not the chosen Noema-owned boundary or the fail-closed contract.

17. **Probe account state independently before setup readiness.** A bound DPAPI record is not proof that the OS account still exists, remains the same identity, is a standard non-administrator user, is enabled and unlocked, or accepts the stored credential. The native read-only probe resolves the account name back to the exact bound local SID, reads `USER_INFO_1`, rejects disabled/locked/password-expired accounts and any direct or indirect membership in the localized built-in Administrators group (whose name is resolved from well-known SID `S-1-5-32-544`), then verifies the current-user stored password with `LogonUserW`. Account and credential evidence are reported independently from restricted-token, filesystem and network evidence; those remain false until their own live checks exist. Any query failure is fail-closed. The probe performs no mutation and does not constitute end-to-end host acceptance.

18. **Construct a fresh command token from the sandbox runner's own logon token and current filesystem grants.** The host helper first probes the persisted account and credentials, then launches the packaged runner using `CreateProcessWithLogonW`; the runner verifies its `TokenUser` equals the bound local SID and that its primary token is not already restricted. It duplicates/restricts this caller primary token, rather than calling `LogonUserW` or reading the host user's DPAPI credential file in the runner. The fixed Codex source uses `WRITE_RESTRICTED` and includes the user SID and Everyone; Microsoft documents that this applies the second SID access check only to writes, so it does not satisfy Noema filesystem read-allowlist semantics. Noema omits `WRITE_RESTRICTED`, sandbox user SID and Everyone: its restricting SID set must contain only the current request's verified read/write-root capability SIDs plus the new logon SID, so both read and write access require a matching current capability. Verify the resulting `TokenRestrictedSids` set and enabled attributes, token user identity, restricted status, and default DACL. Set default DACL to the logon SID plus Owner Rights `READ_CONTROL`, then enable and verify `SeChangeNotifyPrivilege`. Only the runner may call this constructor with capability SIDs supplied in an authenticated parent request after the host helper completes ACL journal verification; never expose a base token, password, or SID-selection operation to the agent or command child. The constructor currently remains dormant and does not launch a process; parent/runner request binding and child launch integration remain open.

19. **Separate host-authorized ACL work from sandbox-account process launch.** The main-process native helper remains under the interactive Windows user's identity for verified path scanning, ACL journal operations, and setup orchestration. It must not directly create a process with a different sandbox account's token: Microsoft documents that `CreateProcessAsUserW` commonly requires privileges unavailable to a standard desktop user. Instead, the trusted helper starts the packaged Noema runner as the stored low-privilege account with `CreateProcessWithLogonW`, using a per-launch unpredictable, local-only named-pipe pair and bounded versioned frames; it verifies both connected pipe client PIDs against the spawned runner PID before sending the request. The runner validates its own account SID and an unrestricted primary token, then creates a restricted child token from that caller token using only main-process-compiled, current-request capability SIDs. It starts the command suspended, assigns it to a kill-on-close Job Object, and resumes only after assignment succeeds. This split follows the fixed Codex call path (`elevated/runner_client.rs` → `CreateProcessWithLogonW`/PID-checked pipes → `bin/command_runner/win.rs` → current-token restricted spawn); the suspended-create/assign/resume ordering is an additional Noema requirement and is not claimed as Codex behavior. No command runs until parent policy/path/ACL checks and all live readiness gates pass. A runner startup, identity, pipe, token, ACL evidence, process assignment, or resume failure denies execution; no host-shell fallback is permitted.
20. **Apply environment allowlists at the command boundary.** `inherit=false` with the exact D2 `allowNames` is enforced when the trusted helper starts the AppContainer command child. The process receives a sorted Unicode environment block containing only those named values; a missing `SystemRoot`, duplicate case-insensitive key, malformed block, or oversized block is a denial. Never pass a null environment pointer to process creation, because that would delegate inheritance behavior to Windows rather than enforce D2 policy. No environment values are copied into diagnostics or result IPC.

21. **Use an ordinary AppContainer for the command child.** Create the child directly from the trusted native helper running as the current Windows desktop user, using `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`. Windows checks both the ordinary user's access and the AppContainer package/capability access; the effective permission is their intersection. This removes the separate sandbox account, its password/DPAPI lifecycle, UAC worker, runner logon, and restricted-token constructor. Keep the command child untrusted and the helper trusted; the renderer and agent must never choose the AppContainer SID or capability list. This is a Windows execution identity, not a Noema login/account feature.

22. **Use only current-request capability SIDs for filesystem roots.** Derive each capability SID from a stable Noema-owned name bound to `(volumeSerialNumber, fileIndex, read|write)`, using `DeriveCapabilitySidsFromName`. Persist/verify the name-to-object binding in the current-user capability store. At launch include exactly the deduplicated current-request read/write SIDs, plus the fixed Noema AppContainer package SID; never ACL-grant the package SID to workspace roots. Existing random `S-1-5-21-*` SIDs are not reusable as AppContainer capability SIDs. Every actual filesystem grant still uses the verified handle ACL journal and all-root hard-link scan; inability to derive/verify a SID denies launch. A read-only host probe verified deterministic name derivation and distinct read/write SIDs, but not DACL enforcement.

23. **Create and inspect a per-Windows-user AppContainer profile without elevation.** Use a fixed product-owned profile moniker, resolve its package SID through the Windows API, and keep profile state under the current Windows user's OS-managed AppContainer mapping. Make profile setup idempotent and record `repair_required` before any profile/ACL mutation; only a fresh read-only probe can commit `ready`. Do not create, elevate, or persist a separate local account or password. Do not delete the profile during normal runs; cleanup must revoke only Noema's current-request capability ACEs and preserve recoverable state if any grant cleanup is uncertain.

24. **Keep network denied unless an explicit supported policy enables it.** The AppContainer process receives no network capability by default. If a future/effective D2 policy permits network access, the exact network capabilities and Noema WFP rules must both be established and verified; any mismatch or WFP failure denies spawn. Do not treat the AppContainer package profile's default behavior as proof that a requested host/domain policy is enforced.

25. **Preserve suspended launch and full child-tree control.** Prepare explicit standard-handle inheritance, bounded stdout/stderr pipes, the exact environment block, AppContainer SID/capabilities, and child-process policy before launch. Create `cmd.exe` suspended, bind it to a kill-on-close Job Object, then resume. Shell descendants must inherit the same AppContainer restrictions and remain in the Job. Any create, Job bind, resume, stream, cancel, timeout, or cleanup failure terminates and waits for the whole tree; uncertain cleanup remains `outcome_unknown`. Ordinary AppContainer system-file access is a documented basis for investigating the `System32` bootstrap, not proof that every runtime/executable will launch.

26. **Keep durable execution authority in Electron main.** Electron main owns D2 user grants, stable request/task identities, ACL journal, setup state, diagnostics, and final task outcome. The packaged helper performs handle-bound path/ACL work and creates only the policy-compiled AppContainer child. The child gets no helper/base-token credential, pipe to an unrestricted owner, or direct route to change ACLs. Native capability/setup probe, AppContainer profile probe, ACL evidence, network evidence, Job/pipe/cleanup controls all remain required readiness gates.
