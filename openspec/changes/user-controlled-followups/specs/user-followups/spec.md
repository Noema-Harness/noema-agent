# user-followups Specification

## Purpose
让用户在明确知情和同意下安排一次个人回访；Noema 在约定时间通过本机通知提醒用户，并让用户可以持续查看、修改、暂停或取消。

## ADDED Requirements

### Requirement: 用户明确授权后才创建回访
系统 SHALL 只在用户明确安排一次回访或明确接受 Noema 提议后创建回访。系统 SHALL 将聊天发起的回访绑定到当前 Noema 主聊用户消息，不接受模型指定任意来源或从历史内容自行推断时间。

#### Scenario: 用户安排具体回访
- **WHEN** 用户在 Noema 主聊给出清晰的未来时间和回访内容
- **THEN** 系统保存一次性回访并记录当前用户消息来源

#### Scenario: 回访时间不清楚
- **WHEN** 用户表达的时间含糊或已过去
- **THEN** Noema 先澄清，不创建回访

#### Scenario: 非主聊尝试创建
- **WHEN** 专业成员或项目会话请求创建个人回访
- **THEN** 系统拒绝写入，且不创建模型或后台任务

### Requirement: 用户能持续管理回访
系统 SHALL 在设置中列出回访，并允许用户手动新增、修改待处理时间/内容、暂停或恢复通知、取消待处理回访。状态为 `canceled` 或 `delivered` 的记录 SHALL 不会被调度器重新领取；只有 `pending` 及租约过期的 `delivering` 记录可领取。

#### Scenario: 用户暂停提醒
- **WHEN** 用户关闭回访通知
- **THEN** 到期回访保留为待处理，重新开启后可继续投递

#### Scenario: 用户取消回访
- **WHEN** 用户取消一条待处理回访
- **THEN** 系统持久标记已取消，后续扫描不再投递

### Requirement: 到期通知可恢复且不产生模型费用
系统 SHALL 在 Noema 运行时扫描到期回访并通过桌面通知 API 提交通知。设备睡眠或应用关闭造成的错过项 SHALL 在恢复运行后补发。通知发送 SHALL 不触发模型调用或网络请求，不得把系统通知伪装成用户聊天消息。状态表示通知 API 已接受请求，不宣称操作系统实际展示或用户已读。

#### Scenario: 回访到期
- **WHEN** 一条已授权回访到期且通知开启
- **THEN** 系统提交其保存的回访文字并持久记录通知 API 接受状态

#### Scenario: 通知暂不可用
- **WHEN** 操作系统通知 API 不可用或调用失败
- **THEN** 系统保留回访为待处理并在之后重试，不报告通知 API 已接受

#### Scenario: Noema 重启后有到期项
- **WHEN** Noema 启动并发现过期但未投递的回访
- **THEN** 系统补发一次本机通知，不调用模型且不重复新建回访
