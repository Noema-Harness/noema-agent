# Noema Project Work

1. Read `docs/PROJECT_OPERATIONS.md`. At task start or resumption, inspect `git status`, branch/recent commit, the live Issue and its latest comments, Project status, blockers, and linked decisions. Use those records—not compressed chat summaries or remembered status—to reconstruct what is true now.
2. Separate authority by subject: current user direction determines whether the work still applies; Issue text/comments describe the current deliverable and checkpoint; Project fields show live workflow state; ADRs record durable decisions. Decide routine implementation details within the delegated lifecycle scope. Record user-confirmed decisions separately from assistant decisions. At an agreed product/visual feedback gate, bring a concrete proposal with a sound premise, recommendation and tradeoffs; do not use a gate to outsource unfinished reasoning. Pause the long-term goal at the gate as requested; silence does not clear it. Also ask when user-specific facts, outside authority or materially irreversible effects require it.
3. An Issue scopes its present deliverable; check upstream gaps against the delegated product outcome instead of freezing the scope around the latest request. When a method failure recurs or threatens product/architecture judgment, apply the review principles in `AGENTS.md` before treating a revised task as the remedy. Keep confirmed mistakes, causal hypotheses and the next behavioral check in the existing checkpoint; a bounded experiment may precede permanent guidance. Revise issues and dependencies when evidence or explicit direction changes the premise, without treating every criticism as established fact. For substantial work without an issue, create one with `gh issue create -R c3115644151/noema-agent`; do not create an issue for every small edit.
4. For multi-stage work, keep one latest compact checkpoint in the Issue: completed evidence, unresolved decision, next concrete action. Include branch/base SHA/PR, unpublished changes and check versions when needed for takeover. Update at a milestone, direction change, blocker, or handoff; avoid progress narration and duplicate local TODO/status files. Follow the concurrent-development protocol in `docs/PROJECT_OPERATIONS.md`: distinguish reported work from published commits and agree ownership before overlapping edits.
5. Auto-add is configured for open issues/PRs, but API-created Issue #5 did not appear automatically during setup. Always verify the item exists on Project #6; add it with `gh project item-add 6 --owner c3115644151 --url <issue-url>` if missing, then query the resulting item. If `gh project` reports `unknown owner type`, use GraphQL `addProjectV2ItemById` with the project's ID and the issue/PR node ID. Query fields with `gh project field-list 6 --owner c3115644151 --format json` before editing custom values.
6. Use the actual lifecycle: Inbox → Backlog → Todo → In Progress → In Review → Done, with Blocked/Canceled as explicit branches. Newly added items start in Inbox; move to Todo only after Definition of Ready. Set Blocked only with a native `blocked by` relationship and a named blocker, not a `status:blocked` label.
7. On completion, run only relevant checks and record exact results and remaining gaps. Set Status to Done only after acceptance; this automatically closes the issue, and GitHub issue closure also maps to Done. For canceled work, close with the `not planned` reason, then reset Project Status to Canceled.
8. Never claim that an issue, board update, test, or external operation succeeded unless the command returned success and the resulting state was checked.
