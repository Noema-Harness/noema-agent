# Noema 架构判断

先明确当前问题和预期改善，区分探索方向与实施已接受的决定。原型和竞品功能是实现线索，不能替代使用理由；源码比较关注同一结果的实际质量、代价和失败恢复。

新增职责先看已有代码、平台或外部工具能否承担。Noema 需要拥有它时，明确状态来源、责任方、生命周期、权限、失败和移除方式。优先选择简单可替换的边界，保持模块化单体。

将关键选择、替代方案、后果和重审条件写入当前 change 的 design.md。仅当取舍会跨多个变更长期约束架构时才写或更新 ADR，并从 design 链接，避免同一决定维护两份正文。小而可逆的选择留在实现，不额外建立评审流程。
